# 提案:add-case-background-conditions

> **狀態：可以開工。** 原本擋住實作的五個問題開發者都已經裁決，結論折進〈已定案〉，該節不再有待答的題目。`tasks.md` 的 26 項全部未完成，`src/` 裡沒有任何對應的實作——這份文件描述的是要做什麼，不是已經有什麼。

## 這份提案剛剛縮小了一半

原本的名字是 `add-tone-and-case-background`，主軸是開發者定案的一條規則:「母語含台灣華語 AND 聽力正常 AND 有聲調錯誤 → 警示」。母語與聽力兩個欄位當初是為了寫得出這條規則才要做的。

開發者後來推翻了那條規則，理由是他沒有遇過需要介入的聲調錯誤個案，而且教育部持續修訂讀音，所謂「錯」的標準本身在移動。

規則沒了，但兩個欄位活了下來，而且各自換了一個更清楚的理由（見〈已定案〉決定五、決定六）。所以整份提案改名重寫，聲調從主角變成一段殘留:格子表照樣記，系統照樣不判斷。

哪些東西跟著那條規則一起走、哪些東西自己站得住，逐項的判定寫在 `design.md` 第一節——**不是靠關鍵字刪的**，有幾項的理由跟聲調完全無關，反而在聲調規則消失之後才變得清楚。

## 為什麼要做

`Case` 身上只有暱稱、生日、出生週數、生理性別、備註。**個案的語言背景與聽力狀態都不存在**，而這兩件事都會改變一筆構音錯誤該怎麼讀。

開發者對母語的說明是:孩子由祖父母帶大而有不捲舌或台灣國語的特徵，不算明顯異常，但系統照樣要跳出錯誤，並附註孩子的語言背景包含台語。

對聽力的說明是:左右耳各自標記正常／異常;「整體算正常還是異常」看優耳，依據是身心障礙鑑定採優耳認定。畫面上要註明這一點。

兩件事有一個共同點:它們都不是「多一個備註欄」就算做完的。母語那句話要求的是**照樣觸發、外加一條附註**，附註本身得是規則寫得出來的東西;聽力那句話要求的是**兩耳分開記、整體看優耳**，優耳是一個要算出來的事實。所以這是規則引擎的事，不只是個案表單的事。

`add-articulation-process-tracker` 當初就把「母語為國語 AND ⋯⋯」列成後續 change 的候選，`add-articulation-rule-conditions` 明寫「不做母語欄位，等真的要用再開」——現在真的要用了。

## 要做什麼

- **個案新增母語（多選）**:內建清單 ＋ 治療師自行輸入的「其他」。清單上的語言有英文 id，自行輸入的沒有——型別怎麼切見 `design.md` 第三節。
- **個案新增聽力狀態，分左右耳**:左耳、右耳各一個欄位，可填的值是未填／正常／異常／配戴聽覺輔具（助聽器或人工電子耳）四種，**都沒有預設值**。第四個值的來由與它在優耳判定裡怎麼算，見〈已定案〉決定四與決定五。
- **出貨一條示範的附註規則，連帶把儲存整組升版**:讓治療師開啟 app 就看得到決定六那種「照樣觸發 ＋ 一條提示」長什麼樣，示範內容以台灣國語為例。代價是既有資料歸零，見〈已定案〉決定十一。
- **四個新事實**:`case.nativeLanguages`、`case.hearing.leftNormal`、`case.hearing.rightNormal`，以及**合起來的 `case.hearing.betterEarNormal`**，都掛在 `case.` 命名空間底下。優耳這一項推翻了本提案原本「不做合成事實」的決定，理由與代價見 `design.md` 第四節與〈已定案〉決定六。
- **條件列新增兩種對象**:「構音錯誤的類別」（聲母／介音／韻母／聲調）與「母語」。兩者都沿用既有的 `some`／`in` 形狀，不自訂 operator。
- **未填欄位的守門延伸到母語列**:母語沒填跟母語不含某個語言是兩件事，不能都靜靜地不觸發而不留痕跡。
- **「整體聽力正常」看的是優耳，這件事一定要在畫面上**:它是猜不到的工具行為，猜錯了會無聲地產生錯判斷。開發者要求的 tooltip 留著，但 tooltip 不能是唯一的載體，理由見 `design.md` 第四節。
- **聲調列的錯音解析看目標音的類別**:今天在聲調列寫「ㄆㄠˊ」，記下來的錯音是 ㄆ。系統不判斷聲調之後，聲調列唯一的讀者就是人，記錯了沒有任何機制會發現——所以這一項是**因為**不判斷才更該修，不是因為要判斷才要修。
- **條件編輯器的聲調選項要有名字**:目前選項標籤用 `symbol`，聲調那一組就是五個沒有名字的 `ˉ ˊ ˇ ˋ ˙`。

## 這次不做的事（範圍外）

- **不做聲調的任何自動判斷。** 沒有規則、沒有推導、沒有為聲調另外做的條件對象或衍生事實。格子表的〈聲調〉區留著給治療師記錄。見〈已定案〉決定一。
- **不做「完全不含某個語言」這種全稱否定的條件。** 母語列只提供「包含」。原本的聲調規則需要「母語不含台灣華語」，那是全稱否定;而開發者實際要的附註是「母語**含**台語」，是存在型的包含，現成的形狀就寫得出來。這兩件事的差別是這次最容易踩到的坑，寫在 `design.md` 第三節。
- **不做純音聽力檢查評估表。** 開發者已裁定這一項延到下一個 change，這次只做左右耳那兩個欄位，不記各頻率的實際分貝數。理由有三個，寫在 `design.md` 第四節，最短的版本是:那張表上的每一格都是這裡沒有的臨床內容（測哪些頻率、dB 怎麼記、氣導骨導差多少算傳導性、哪一組門檻算正常），而 `FormBody` 多一個 `kind` 是程式碼不是資料（`docs/ARCHITECTURE.md` 第二節），照範圍紀律本來就該是它自己的 change。
- **不分辨戴的是助聽器還是人工電子耳。** 第四個值把兩者合成同一個狀態。要分開是另一件事，而且分開之後才會有「兩者在優耳判定裡算不算同一回事」這種要問臨床的問題;現在沒有規則需要分。
- **不新增以「錯成哪個音」為對象的條件列。** 條件列今天問得出「目標音是哪些」與「屬於哪一類」，問不出「從哪個音替代成哪個音」。決定十一那條示範規則因此只指名三個目標音，替代的方向寫在規則的訊息文字裡而不是條件裡——這個界線很重要，見決定十一。
- **不由聽檢資料推導那兩個欄位。** 這次的欄位是治療師直接填的，是聽力事實的唯一來源。將來那張表要不要覆寫它們、兩邊不一致時聽誰的，留給那個 change 決定——先做欄位不會擋住它，先猜一個關係才會。
- **不改 `articulation.errors` 裝的東西。** 聲調錯誤今天在裡面，這次之後還在裡面。已經匯出、已經在治療師之間傳過的規則檔讀的就是這個清單，靜靜改掉它裝什麼，等於靜靜改掉那些規則的意思。要讓某條規則不理聲調，是在那條規則的條件上寫清楚（這次新增的「構音錯誤類別」正好讓它寫得出來），不是動事實。
- **不做警示頁「有規則因為缺資料而根本沒判斷」的分辨。** 那是 `docs/screen-text-policy.md` 6.4 記的缺口，本案會讓它多幾個入口（母語、左耳、右耳），但補那個機制是它自己的 change。這次只把個案頁既有的那一行揭露從「生日」改成講機制本身。
- **不做「主要母語／次要母語」的區分**，也不排序。多選就是一個集合。
- **不動前置化／後置化、邊音化、介音省略**——`references/open-questions.md` 裡那幾條各自有各自的狀態，這次不碰。

## 對既有規格的影響

`add-articulation-rule-conditions` 的「不做『只算聲母錯誤』的判定」是這次要收掉的:那份 proposal 說「構音事實裡會帶著目標音的類別欄位，之後要收斂成只看聲母不用改資料結構」。這次做的正是那個收斂。`ArticulationErrorFact.targetCategory` 已經存在（那份 change 的 2.2 已經做完並打勾），不用改資料結構，只要讓條件列指得到它。

出貨示範規則會把 `storage.ts` 的儲存 key 整組從 `:v7` 升到 `:v8`（已核對過程式碼，十個 key 目前一致停在 `:v7`）。升版是作廢不是遷移，這是 `docs/ARCHITECTURE.md` 第五節既有的取捨，本案沒有改它，只是引用它。誰會失去什麼，寫在決定十一。既有規格〈純本機儲存〉寫著版號「目前為 `v7`」，所以本案以 `MODIFIED` 明改它，順便把「所有 key 一起升」這條原本只寫在架構文件裡的規矩補進規格。

另外一條要用 `MODIFIED` 明改的是〈沒有記錄的欄位不觸發規則〉。它現在寫著「適用條件列 SHALL 一律可判定，空清單即代表沒有記錄到任何一筆」，而母語列必須是這條的例外。這個推翻原本被寫成一條新增的需求，那樣等於靜靜地在旁邊放一條相反的話;改成 `MODIFIED` 之後，讀規格的人在同一個地方就看得到原則與例外。

本提案自己原本寫著「**不做**把兩耳合起來的聽力正常事實」，這次**推翻**。推翻的理由與原本的理由為什麼不再成立，寫在 `design.md` 第四節與〈已定案〉決定六;因為那個決定從來沒有實作過，它只存在於本 change 的 spec delta 裡，所以是直接改寫，不是對已出貨規格的 `MODIFIED`。

## 技術方向

不引入新套件。兩種新條件列都只用 `some`／`in`／`!` 這些 JsonLogic 原生運算子，匯出的 JSON 對其他 JsonLogic 實作照樣有意義。新事實一律掛在 `case.` 底下，項目 id 在事實物件最上層平鋪的不變量不受影響。

## 已定案

開發者已經回答、不再重開的決定。寫在這裡是為了讓下一個讀這份提案的人不要把它們當成還沒決定的事。

### 決定一:聲調只記錄，不判斷

開發者的理由有兩半。第一半是臨床上的:他沒有遇過需要介入的聲調錯誤個案，而且教育部持續修訂讀音，所謂「錯」的標準本身在移動——標準會動，正是不該讓系統自動判斷的理由。

第二半是「要做也做不好」:真的要判斷，得記得下「什麼情境下、從哪一個聲調變成哪一個聲調」，而格子表一格只比一個符號對一個符號，表達不了。

**所以系統對聲調不做任何自動判斷**:不推導音韻歷程、手動歷程清單不提供任何一條、不出貨任何以聲調為判準的規則、也不為聲調另外做條件對象或衍生事實。格子表的〈聲調〉區留著——治療師想記就記，那是紀錄不是判斷。

第一半（推導）**已經實作並提交**（commit `94665c6`，`deriveProcessIds()` 對聲調目標音一律回空清單），所以 `tasks.md` 上沒有它的任務，只有規格上的記載。

這一條有一個看起來像例外、其實不是的地方:新增的「構音錯誤類別」對象涵蓋四類，其中一類就是聲調，所以治療師**寫得出**「有聲調錯誤」這種條件。那不違反這一條——這一條管的是**系統**做不做判斷，不是治療師能不能。理由見 `design.md` 第一節。

### 決定二:聲調留在構音評估表

開發者定案:「先留在構音評估表沒關係。」

這一條值得寫下來，因為他同時說了「聲調其實比較偏語言／音韻」——也就是**分類上聲調不屬於構音，但記錄的位置暫時不動**。兩件事不衝突:格子表是輸入介面，不是分類主張。真的要把聲調搬去語言類的表，是等那張表存在之後的事，不是這次。

### 決定三:那條轉介規則維持原樣，純聲調錯誤照樣觸發

問的是「一個孩子如果**只有**聲調錯誤、其他音都對，`rule-articulation-therapy-referral`（四歲以上仍有捲舌音以外的構音錯誤）今天會觸發，要不要讓構音類的規則不理聲調」。

開發者判定保留，理由有兩個:不是來做構音評估的個案根本不會掛上這張表，所以實務上碰不到;而且就算跳了警示，那個警示本身是正確的，要不要介入是治療師的判斷。

**所以規則不改、條件不改、訊息文字不改。**

這一條跟決定一併在一起讀才完整:決定一說的是系統不主動去判斷聲調，決定三說的是一條寫給「構音錯誤」的通則規則掃到聲調錯誤時**不必特別閃開**。兩者都成立，而中間需要一個出口——治療師如果**要**讓自己那條規則閃開聲調，得有辦法寫。「構音錯誤類別，排除 聲調」就是那個出口（存在型的「排除」在這裡剛好讀作「有聲調以外的構音錯誤」，正是要的意思）。

`tasks.md` 因此有一則回歸測試把這個決定釘住:純聲調錯誤的個案仍然觸發那條規則。沒有那則測試的話，下一個人讀到「聲調只記錄不判斷」很可能會順手把它改掉。

### 決定四:聽力分左右耳記錄，每一耳有四個狀態

問的是「治療師自己填一個正常／異常的開關夠不夠」。開發者判定夠，但必須分左右耳。

每一耳可填的值，開發者定案是四個:**未填、正常、異常，以及配戴助聽器或人工電子耳**。第四個值是後來補上的——原本規劃只有前三個，開發者裁定戴輔具是一個要看得出來的獨立狀態，不能塞進「異常」裡。

助聽器與人工電子耳**共用同一個值**，不再細分是哪一種:今天沒有任何規則需要分辨，而分開之後會連帶問出「兩者算不算同一回事」這類要臨床回答的問題。

所以個案身上是**兩個**欄位，每個欄位四態，而且都沒有預設值。

### 決定五:整體聽力狀態看優耳

開發者定案:左右耳各自標記正常／異常;「整體算正常還是異常」看優耳，依據是身心障礙鑑定採優耳認定。畫面上要註明這一點。

**這一條推翻了本提案原本「不做把兩耳合起來的聽力正常事實」的決定。** 原本的理由是:合起來就得決定單側異常算不算正常，那是臨床判斷，藏進事實層之後規則長得跟原來一模一樣、看不出指的是哪一種。

那個理由現在不成立了，兩個原因:

1. **判斷不再是我們做的。** 原本的問題是「不是我能替開發者決定的」——現在開發者決定了，而且說出了依據（身障判定看優耳）。合成的那一行不是一個被藏起來的猜測，是一個有名字、有出處的決定。
2. **「看不出是哪一種」是可以修的，而且修在對的地方。** 事實的路徑就叫 `case.hearing.betterEarNormal`、欄位名就叫「整體聽力正常（優耳）」——匯出的 JSON 裡讀到的也是這個字。原本的反對其實是在反對一個**沒有名字**的合成，不是在反對合成本身。

跟「實齡／矯正齡不自動挑一個」的類比也在這裡斷掉:那兩個年齡沒有任何外部慣例指定該用哪一個，選錯是無聲的;優耳有一個可以指名的外部慣例。

左右耳兩個事實**照樣保留**——合成是加上去的，不是取代。要寫「兩耳都正常」的人照樣寫得出兩列 AND。

「用 tooltip 註明」這句照做，但 PM 這邊多一個要求:**tooltip 不能是唯一的載體**。理由見 `design.md` 第四節（一句話版本:hover 才看得到的字，掃視時不存在、觸控時不存在，而且匯出成檔案之後完全不存在）。

**配戴輔具在優耳判定裡算異常。** 這是開發者跟第四個值一起裁定的:一隻戴著助聽器或人工電子耳的耳朵，在「整體聽力正常嗎」這一題上不投正常票。所以合成的算法變成——任一耳為正常就是正常;兩耳都是已填而非正常（異常或配戴輔具，兩者任意搭配）才是異常;其餘仍然是未知。真值表見 `design.md` 第四節。

有一件**推導出來、不是開發者直接說的**事必須寫明:開發者裁的是優耳那一項，而同一個值在 `leftNormal`／`rightNormal` 兩個單耳事實上也只能一樣算作「非正常」。理由是內部一致——若單耳事實把配戴輔具算成正常，就會出現「左耳聽力正常 ＝ 是」與「整體聽力正常 ＝ 否」在同一個個案身上同時成立，任何讀規則的人都無法解釋。如果開發者其實要的是「戴上輔具之後單耳聽得到，所以單耳算正常」，那是另一種讀法，說一聲，那會是一行程式碼與一則測試的事。

### 決定六:母語的用途是方言變異的附註，形狀是「照樣觸發 ＋ 一條提示」

開發者描述的情境是:孩子由祖父母帶大，因而有不捲舌或台灣國語的特徵。這不算明顯異常，但系統照樣要跳出錯誤，並附註孩子的語言背景包含台語。

早先他對聲調給過兩個選項——照樣觸發但附註，或者乾脆不觸發。這個情境把它定下來:**照樣觸發，外加一條附註**，不是靜靜地不觸發。

這件事不需要在模型裡新增「附註」這個概念，用現成的東西就寫得出來:**兩條規則，靠嚴重度分開**。原本的規則照舊觸發警示;另一條規則的條件是「母語包含台語 AND（同一組構音錯誤）」，等級是提示，訊息文字就是那句附註。`RuleSeverity` 已經有 `info`（畫面上顯示「提示」），一個新概念都不用加。

**這裡有一個一定要講清楚的坑。** 集合列的「排除」是**存在型**:「排除台灣華語」編出來的 JsonLogic 讀作「母語裡有某一個不是台灣華語」，對一個華語＋台語的雙語孩子**成立**——而那正是台灣最常見的情況。真的要「完全不含」得用全稱否定，是另一種形狀。

而開發者要的附註**不需要那個形狀**:他要的是「母語**有**台語」，這是存在型的包含，現成的「包含」模式一列就寫完了。所以這次**不做**第三種 mode。詳細的對照表在 `design.md` 第三節。

至於一位治療師實際要讓這條附註涵蓋哪些錯誤、哪些語言，是他自己在規則編輯器裡下的臨床判斷，本案不代填。本案出貨的是**一條可以照著改的示範**，內容由開發者指定，見決定十一。

`references/open-questions.md` 已經記著:不捲舌與空韻圓唇化（石頭→俗頭）是**刻意不列入音韻歷程清單**的方言變異。所以這條附註**不可能**以歷程 id 當條件——它讀的是母語，加上治療師自己挑的那組構音錯誤。

### 決定七:內建母語清單 ＝ 法定國家語言 ＋ 新住民語文課綱七語 ＋ 粵語

開發者定案的組合，兩條官方界線加一個手動補上的缺口:

- **法定國家語言**（《國家語言發展法》§3）:華語、台灣台語、台灣客語、原住民族語、平埔族群語、馬祖語，以及**手語**。
- **教育部新住民語文課綱七語**（107 年發布）:越南、印尼、泰、緬甸、柬埔寨、菲律賓、馬來。
- **粵語**——不在上述任何一條界線上。開發者補上的理由是實務觀察:「港澳很多語言治療師來台灣留學。」移民署的來源地排序也支持這一點，港澳高於菲律賓。

這個組合有一個好處值得寫下來:它讓「為什麼沒有日語、韓語、英語」有一個可以說出口的答案——**它們不在任何一條官方界線上**，而不是誰主觀覺得用不到。如果改用人口排序當界線，東南亞語言反而會被強制納入（柬埔寨籍累計人數高於韓國籍），依據見 `references/copyright-and-sources.md` 第一節。

**手語分成兩項**:開發者定案「自然手語跟文法手語是台灣的兩種手語體系，分別勾選就可以」。所以清單上是兩個獨立項目，不是一項「台灣手語」。

原住民族語**列成一項**，不分族別——16 族 42 語別放進一個個案基本資料的多選清單並不實用;真的需要指名哪一族的治療師可以用「其他」自行輸入。這一項如果開發者要改成分族別，說一聲。

**華語那一項就叫「華語」。** 原本有一題在問要不要拆成「華語／台灣華語」，那一題是被聲調規則的措辭（「母語含台灣華語」）逼出來的;規則沒了，清單就依它自己的兩條界線走，用《國家語言發展法》的用詞。要拆的話說一聲，這是一句話就能改的事。

### 決定八:母語條件問的是「評估標的是不是他的語言背景」

這一條原本是為聲調規則寫的，**原則活下來了，寫法變了**，所以完整保留。

助理原本以為那條規則要問的是「母語是不是聲調語言」。開發者否定了這個方向:判準不是母語有沒有聲調，而是評估標的（台灣華語）是不是他的語言。如果不是，錯誤照樣觸發但要附註它可能不算真的異常;或者乾脆不要觸發。

也就是說:**這張表評的是台灣華語。** 錯誤是「相對於台灣華語」的錯誤。如果個案的語言背景不是（或不只是）台灣華語，那個錯誤可能是語言差異而不是異常——判準不是母語有沒有聲調，而是**評估標的跟他的語言背景對不對得上**。

決定六是同一個原則的另一種寫法，而且是實務上更常見的那一種:孩子的華語就是他的母語，只是**同時**有台語，於是台語的特徵帶進華語裡。前者要問「不含台灣華語」（全稱否定），後者只要問「含台語」（存在型包含）。**這個轉向就是這次不需要第三種 mode 的原因。**

這個道理不限於任何一種錯誤:任何拿台灣華語常模去評一個語言背景不同的人的項目，都適用同一條保留。這次做的是讓它寫得出來，`design.md` 會把這個推廣寫在型別註解裡。

### 決定九:聽力欄位不加「由誰判定」的說明文字

問的是「這兩個欄位是治療師憑自己的觀察就能填，還是要有聽力師或耳鼻喉科的報告」，原本預期答案會變成 label 旁邊的一句話與《使用說明》裡的一句話。

開發者裁定**畫面上什麼都不加**。理由是這類資訊病歷上本來就有，治療師是照著病歷填，不是在這裡自己做聽力判斷——那句說明對他而言不提供任何他不知道的事。

所以原本規劃的那一句話**取消**，不是改寫成別的句子。這一條要記下來，因為下一個讀 `docs/screen-text-policy.md` 三問的人很可能會重新推導出「應該要講」——這裡的判定不是那三問的結果，是開發者對他的使用者實際工作方式的認定，優先於推導。

### 決定十:母語多選不設上限

開發者裁定不設上限。填幾個就是幾個，畫面上不擋、不提示、也不需要為「填太多」設計任何行為。

### 決定十一:出貨一條示範的附註規則，代價是儲存整組升版

提案原本建議**不**出貨，開發者**推翻**了這個建議:決定六那條「照樣觸發 ＋ 一條提示」的兩規則寫法，光靠文件說得出來、光靠編輯器寫得出來，但沒有人會在第一次開 app 的時候自己想到——出貨一條看得到、改得動的示範，價值大於代價。

**代價開發者已經被明確告知並接受。** 完整寫在這裡，因為它不是一句「順便升個版」:

`starter-rules.ts` 的種子只在集合為空時才跑，所以新增的示範規則對已經開過這個 app 的人完全不會出現，除非升版。而升版必須**所有 key 一起升**——各集合分開存，只升規則那一個會留下一堆指著不存在個案的孤兒資料。而且**升版是作廢不是遷移**。所以出貨這條示範規則的實際效果是:每一個已經用過這個 app 的人，個案、課節紀錄、每一張表填過的值、構音音對、音韻歷程覆寫、吞嚥嘗試、報告草稿，以及**他自己新增的評估項目、自己新增的音韻歷程、自己寫的規則**，全部歸零。規則可以先匯出成檔案再匯回來，其他的不行。

這個取捨本身不是本案發明的，`docs/ARCHITECTURE.md` 第五節早就寫著「升版是作廢，不是遷移」，本案只是又一次付這個代價。程式碼核對過:十個 key 目前一致停在 `:v7`，這次一起升到 `:v8`。

**示範規則的內容**，開發者以台灣國語為例指定，本案不擴充也不改寫:

- 條件一——母語包含台灣台語。
- 條件二——構音錯誤的目標音包含 ㄕ、ㄈ、ㄩ。
- 等級——提示（`info`），因為它的角色是附註，原本那條警示照樣跳。
- 訊息——把開發者給的三組替代講出來:石頭說成俗頭（ㄕ 替代成 ㄙ）、飛機說成灰機（ㄈ 替代成 ㄏ）、萵苣說成萵記（ㄩ 替代成 ㄧ）。

**這裡有一個表達力的缺口必須寫明。** 條件列問得出「目標音是哪幾個」，問不出「替代成哪個音」——事實上每一筆錯誤都帶著錯音，但沒有任何條件對象指得到它。所以這條示範規則的條件只認得三個目標音，**比開發者描述的三組替代寬**:一個把 ㄕ 說成 ㄉ 的孩子也會讓它成立，而那不是台灣國語的特徵。

處理方式是把替代的方向放進規則的**訊息文字**，讓治療師打開規則就讀得到它實際在講什麼。不採用的做法有兩個，理由各自寫清楚:

- **手寫一段編輯器反解不出來的 JsonLogic**（同時比對目標音與錯音）。條件是準了，但那條規則在編輯器裡會顯示成原始 JSON——一條打不開、改不動的示範規則，等於沒有示範。
- **這次順便加一個「錯成哪個音」的條件對象**。那是新的條件詞彙，要動 `condition-mapper.ts` 的來回轉換、編輯器的選項、以及匯出格式，屬於它自己的 change。範圍紀律在這裡的意思是:為了讓一條示範規則更準而擴充規則語言，是把 change 撐開，不是收尾。

**示範個案要跟著補，否則規則出貨了也看不到。** 示範個案身上沒有母語（守門會擋住這條規則），也沒有 ㄕ、ㄈ、ㄩ 的音對。所以連帶要做兩件事:示範個案的母語補上台灣台語，以及依開發者給的那三組詞加三筆音對。示範個案的**聽力刻意留空**——留空正好示範「沒填就不判斷」，而替一個虛構個案填一個聽力狀態沒有任何依據。
