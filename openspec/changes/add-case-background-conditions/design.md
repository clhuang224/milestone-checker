# 設計:add-case-background-conditions

## 一、那條聲調規則走了，誰跟著走、誰留下來

原本的 change 有一半的內容是為了寫出「母語含台灣華語 AND 聽力正常 AND 有聲調錯誤 → 警示」。開發者定案聲調只記錄不判斷（proposal 決定一），那條規則整條出局。

**但「因為聲調規則才做」不等於「只有聲調規則需要它」。** 逐項判過，不照關鍵字刪:

| 原本的東西                             | 判定       | 理由                                                                                                |
| -------------------------------------- | ---------- | --------------------------------------------------------------------------------------------------- |
| 那條規則本身                           | **刪**     | 決定一                                                                                              |
| 出貨 starter rule ＋ 升版到 `:v8`      | **刪**     | 沒有規則要出貨。附註規則要不要出貨是 Q5，建議也不出                                                 |
| 「完全不含某語言」第三種 mode          | **刪**     | 只有那條規則需要全稱否定;決定六的附註是存在型的「包含」，見第三節                                   |
| Q「華語還是台灣華語」                  | **刪**     | 是被規則措辭逼出來的。清單依決定七自己的兩條界線走                                                  |
| Q「一聲怎麼寫」「輕聲算不算聲調錯誤」  | **刪**     | 兩題都在問「規則要怎麼算」。沒有規則要算了                                                          |
| Q「兩耳不一致算不算聽力正常」          | **刪**     | 曾經是那條規則的參數，現在由決定五獨立回答（看優耳）                                                |
| 聲調不推導音韻歷程                     | **已完成** | commit `94665c6`。留規格記載，不留任務                                                              |
| 聲調列的錯音解析取錯符號               | **留**     | 理由整個換掉了，見第二節。簡短版:沒有機器在判斷之後，記錯了不會有任何東西發現                       |
| 條件編輯器的聲調選項是五個沒名字的符號 | **留**     | `docs/screen-text-policy.md` 例四已經判過「一個裸的聲調符號沒有名字讀不出來，旁邊那個中文名是資料」 |
| `'articulationCategory'` 條件對象      | **留**     | 見下                                                                                                |
| 個案母語欄位                           | **留**     | 用途換成決定六的附註                                                                                |
| 母語列參與未填欄位守門                 | **留**     | 只要母語條件存在就需要                                                                              |
| 個案聽力欄位（分左右耳）               | **留**     | 決定四、決定五本身就是要求，不是那條規則的配件                                                      |

### `'articulationCategory'` 為什麼留下來

它是這次最容易誤刪的一項:proposal 原本明寫它是「為了表達『有聲調錯誤』」而加的。但它有兩個跟聲調規則無關的理由，而且兩個都比原本的理由硬。

**一、它是 `add-articulation-rule-conditions` 欠的帳。** 那份 proposal 寫著「不做『只算聲母錯誤』的判定:構音事實裡會帶著目標音的類別欄位，之後要收斂成只看聲母不用改資料結構」，而它的 2.2 已經做完並打勾——`targetCategory` 已經在每一筆 `ArticulationErrorFact` 上，就是為了這一天預留的。欄位存在但沒有任何東西指得到它，是一個半成品，不是一個功能。

**二、決定三需要一個出口。** 決定三保留了「純聲調錯誤照樣觸發轉介規則」。決定一說系統不判斷聲調。兩者要並存，治療師就必須有辦法在**自己**那條規則上說「我這條不算聲調」——而集合列的「排除」是存在型，「構音錯誤類別，排除 聲調」剛好讀作**扣掉聲調之後仍然有其他類別的錯誤**，正是「有聲調以外的構音錯誤」。這個出口不存在的話，決定一與決定三之間就只剩一句口頭上的並存。

**這不算「為聲調做條件對象」。** 決定一禁的是系統替聲調做判斷機器:推導、規則、專屬事實。「構音錯誤類別」是一個涵蓋 `ZhuyinCategory` 全部四個成員的通用對象，成員清單直接取自既有型別，沒有任何一行程式碼是為了聲調而寫的。治療師拿它寫得出「包含 聲調」——那是他的判斷，跟系統自動判斷是兩件事。規格裡的例子刻意用聲母與「排除 聲調」，不用「包含 聲調」，免得被讀成系統在鼓勵這種規則。

## 二、聲調:不判斷的話，記下來的東西更要是對的

`parseHeard()` 取的是文字裡**第一個**注音符號。這在聲母／韻母列是對的（一列比一個目標音）。在聲調列不對:治療師在聲調列寫「ㄆㄠˊ」——一個很自然的寫法，因為聲調不能單獨念——解析出來的 `symbolId` 是 `p`（ㄆ），這筆錯誤變成 `tone3 → ㄆ`，`errorLabel()` 顯示「ˇ→ㄆ」。

**原本修它的理由是「規則要讀得準」。那個理由沒了，換上一個更強的:**

`parse-heard.ts` 自己的註解寫著「解析不出注音符號不是錯誤:治療師寫的東西原樣留著，只是沒東西可推導」——**不無中生有**是這個模組的原則。在聲調列挑出 ㄆ 正好違反它:治療師寫的是一個聲調錯誤，系統記下來的是一個聲母錯誤，而且會把這個沒人寫過的東西顯示回去給他看。

而決定一讓這件事變得更嚴重，不是更輕:

- 系統不判斷聲調 → 聲調那一區記下來的東西**唯一的讀者是人**。
- 沒有任何規則會踩到這筆假的 `ㄆ`，所以**沒有任何機制會讓它現形**。
- 反而是解析失敗的情況比較安全:`errorLabel()` 找不到符號時會退回顯示原文（「ˇ→ㄆㄠˊ」），那是誠實的。**現況比不解析還糟。**

**做法**:`parseHeard()` 多收一個「要哪一類」的參數，`probeErrors()` 依 `targetPhonemeId` 的類別傳進去，聲調列就只認聲調符號。自由文字照樣能寫。

否決掉的做法:把聲調區的錯音格換成五選一的選單。輸入是變得沒有歧義，但跟其他區不一致，而且治療師沒辦法寫下他實際聽到的東西——自由文字這個決定在 `ProbeItem` 上有註解，是刻意的。

**一聲沒有標記符號這件事不再需要問。** 「該念二聲、念成一聲」寫「ㄆㄠ」的話一個聲調符號都找不到，這筆會是「有錯誤但解析不出錯音」:`isErrorItem()` 只看錯音格空不空，所以它仍然是一筆錯誤，`targetCategory` 仍然是 `tone`，`errorLabel()` 退回顯示原文。**這是一個完整、誠實、不需要任何臨床輸入就決定得了的行為**——原本它要問，是因為有規則要靠它算數;現在沒有。也因此不做插入 `ˉ` 的按鈕，那是替一個沒人要的精確度加介面。

## 三、母語

### 附註怎麼表達:兩條規則，靠嚴重度分開

決定六要的是「照樣觸發，外加一條附註」。模型裡**不需要**新增「附註」這個概念:

| 規則             | 條件                                  | 等級              |
| ---------------- | ------------------------------------- | ----------------- |
| 一（既有，不動） | 四歲以上 AND 構音錯誤排除 ㄓㄔㄕㄖ ⋯⋯ | 警示（`warning`） |
| 二（附註）       | 母語包含台語 AND（同一組構音錯誤）    | 提示（`info`）    |

`RuleSeverity` 已經是 `'info' | 'warning' | 'critical'`，`warnings-list.ts` 已經把 `info` 顯示成「提示」。**一個新概念、一行新程式碼都不用加**，本案只要讓規則二的第一列寫得出來。

規則二實際涵蓋哪些錯誤、哪些語言算數，是治療師自己的臨床判斷，本案不代填。

### 附註不能以歷程 id 當條件

`references/open-questions.md` 已經定案:**不捲舌**與**空韻圓唇化**（石頭→俗頭）是台灣國語的方言變異，**刻意不列入音韻歷程清單**。所以規則二不可能寫成「音韻歷程 包含 不捲舌化」——那條歷程按設計就不存在，將來也不會存在。

它讀的是兩件現成的東西:

- **`case.nativeLanguages`**——本案要做的部分。
- **`articulation.errors` 上的目標音或類別**——已經有了。不捲舌是「構音錯誤目標音，包含 ㄓㄔㄕㄖ」;空韻圓唇化的 ʅ→ㄨ 本身就是一筆韻母錯誤，目標音 `ihBack` 也在清單上。

### 「包含」夠用，「完全不含」不做

集合列的 `mode: 'excludes'` 是**存在型**。「排除台灣華語」編出來的是:

```json
{ "some": [{ "var": "case.nativeLanguages" }, { "!": { "in": [{ "var": "" }, ["mandarin"]] } }] }
```

讀作「母語裡**有某一個**不是華語」。跟「母語不含華語」在雙語個案身上給出相反的答案，而那正是台灣最常見的情況:

| 母語             | 存在型「排除華語」 | 全稱型「完全不含華語」 |
| ---------------- | ------------------ | ---------------------- |
| 台語 ＋ 越南語   | 成立               | 成立                   |
| **華語 ＋ 台語** | **成立**           | **不成立**             |
| 只有華語         | 不成立             | 不成立                 |

用存在型寫「母語不是華語」，一個華語台語雙語的孩子會被貼上「母語不是華語」，結論是錯的。要正確表達得用全稱否定 `{"!": {"some": [langs, {"in": [item, [...]]}]}}`，也就是母語列要有第三種 mode（包含／排除／完全不含），而且畫面上必須把三者的差別講清楚——「排除」已經是這個編輯器最容易被誤解的控制項。

**這次不需要。** 決定六要的附註是「母語**有**台語」，這是存在型的**包含**:

```json
{ "some": [{ "var": "case.nativeLanguages" }, { "in": [{ "var": "" }, ["taiwanese"]] }] }
```

一列寫完，語意跟直覺一致，沒有雙語陷阱。所以母語列**只提供「包含」**;`mode` 這個欄位型別上留著，UI 上不給另外兩個選項，之後真的有規則需要全稱否定時再開。

順帶一提，`MODE_HINTS` 的「排除」那句白話重述現在寫的是「⋯⋯個案身上仍然有其他**構音錯誤**時成立」。母語列不給「排除」，所以這句不必為它改寫;新增的「構音錯誤類別」對象給「排除」，而那句話對它照樣正確。

### 型別怎麼切

`CLAUDE.md` 要求聯集成員與識別字是英文、中文只在顯示層。而「其他，讓治療師自己輸入」的那一項**本質上不可能是聯集成員**——它沒有 id，內容是治療師當場打的字。

**結論:兩個欄位，不是一個。**

```ts
/**
 * 內建清單上的語言。自行輸入的語言在 `otherNativeLanguages`，不在這個聯集裡。
 *
 * A rule reading this asks whether the norms being applied match the case's language
 * background — 「母語包含台語」 flags a Mandarin error that may be a dialectal feature rather
 * than a disorder. That reservation is not specific to any one error type.
 */
export type NativeLanguageId = 'mandarin' | 'taiwanese' | 'hakka'; /* ⋯ 見決定七的完整清單 */

export const NATIVE_LANGUAGE_LABELS: Record<NativeLanguageId, string> = {
  mandarin: '華語',
  taiwanese: '台灣台語',
  hakka: '台灣客語',
  // 其餘依決定七補齊
};

export interface Case {
  // ⋯既有欄位⋯
  /** 內建清單裡被勾選的。未填時 undefined，不是 []——差別見第六節。 */
  nativeLanguages?: NativeLanguageId[];
  /** 治療師自行輸入的語言，原樣保存。規則讀不到這裡。 */
  otherNativeLanguages?: string[];
}
```

**為什麼不是一個陣列。** 最直接的理由是型別會失效:`(NativeLanguageId | string)[]` 在 TypeScript 裡就是 `string[]`——聯集被 `string` 吸收，編譯器從此不再檢查任何東西，`'taiwanse'` 這種打錯的字也照樣過。這不是風格問題，是那個聯集寫了等於沒寫。

第二個理由是**規則只讀得到有 id 的那一半**。分成兩個欄位，「規則能拿什麼寫條件」就是一個型別層次的事實，不是一段要記得遵守的約定。

### 否決掉的做法

| 做法                                                             | 為什麼不                                                                                                                                                                                                                   |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 單一陣列 `({kind:'listed', id} \| {kind:'other', text})[]`       | 型別是誠實的，也保住了「治療師勾選與輸入的先後順序」——但沒有任何畫面需要那個順序，代價是每一個讀它的地方都要先分辨 kind                                                                                                    |
| 每個語言一個布林型評估項目（`FindingDefinition`）                | 評估項目掛在**課節紀錄**上，一次回診一組值;母語不隨回診改變，掛在那裡等於每次評估都要重填。而且項目 id 是在事實物件**最上層平鋪**的，語言 id 會跟治療師自訂的項目 id 撞名，而沒有程式在擋（`docs/ARCHITECTURE.md` 第三節） |
| 每個語言一個布林事實（`case.nativeLanguage.taiwanese: boolean`） | 條件列不用改就寫得出來，很誘人——但「沒填過母語」會被組成 `taiwanese: false`，等於替一個什麼都沒填的個案主張「他不說台語」。要避開就得「至少填過一個才組這個物件」，那個細節很容易在下一次改動時掉，而掉了不會有人看見      |
| 直接存中文字串（`['華語','台語']`）                              | 違反 `CLAUDE.md`;而且規則檔匯出去之後，條件裡會出現中文字面值，換一個語言的介面就沒救了                                                                                                                                    |

### 自行輸入的語言進不進事實

**不進。** `case.nativeLanguages` 只裝有 id 的那些。

依 `docs/screen-text-policy.md` 的三問，這件事**不上畫面**:治療師在規則編輯器的母語選單裡本來就只看得到內建清單，自己打的字不在那裡——這是「做了就看得到」的自證級，不是無聲級。

但有一個真的會出事的角落:**如果治療師把一個清單上已經有的語言打進「其他」**，那條語言就悄悄變成規則讀不到的。這不該用一句說明文字解決，該用輸入方式解決——「其他」是清單的**補充**而不是替代（例如打字時就過濾掉清單上已有的項目）。形式是 UX 的事，這裡只定「不能有兩種說同一個語言的方法」。

### 內建清單不放進 `references/`

`references/` 裝的是臨床知識（辨異徵性、音韻歷程、吞嚥質地），而且每一份都有 `scripts/check-references.mjs` 在比對;母語清單是人口學欄位不是臨床判準，塞進去會讓那個資料夾的定位變模糊。開發者如果認為這份清單需要被別的治療師檢查，那就是另一回事，再說。

## 四、聽力:分左右耳記錄，整體看優耳

### 這次做:個案上的兩個欄位

```ts
/** 一耳的聽力狀態。沒有 'unknown' 這個成員——未評估就是那一耳的欄位不存在。 */
export type HearingStatus = 'normal' | 'abnormal';

export const HEARING_STATUS_LABELS: Record<HearingStatus, string> = {
  normal: '正常',
  abnormal: '異常',
};

/** 左右耳分開記。任一耳未填時該欄位 undefined，用到那一耳的規則就不會判斷。 */
export interface CaseHearing {
  left?: HearingStatus;
  right?: HearingStatus;
}

export interface Case {
  /** 兩耳都沒填時整個欄位不存在;只填一耳是合法狀態，不要補另一耳的預設值。 */
  hearing?: CaseHearing;
}
```

### 事實層:三個布林，其中一個是合成的

```
case: { ageInMonths, correctedAgeInMonths, nativeLanguages,
        hearing: { leftNormal, rightNormal, betterEarNormal } }
```

`leftNormal = hearing?.left === undefined ? undefined : hearing.left === 'normal'`，右耳同理。

### 這一節推翻了本案原本的決定

本案原本明寫「**不做**把兩耳合起來的聽力正常事實」，理由是:合起來就得決定單側異常算不算正常，那是臨床判斷，而合成之後那個決定會藏在 `buildFacts()` 的一行程式碼裡，規則在編輯器裡與匯出的檔案裡都長得一模一樣、看不出指的是哪一種。並且類比了「實齡與矯正齡兩個都給、不自動挑一個」。

開發者定了案:

整體狀態看優耳，依據是身心障礙鑑定採優耳認定。

**原本的理由不再成立，逐條說明為什麼:**

1. **「那是臨床判斷，不是我能替開發者決定的」**——對，所以當初不決定;現在開發者決定了，而且說了依據是身障判定的慣例。合成的那一行不再是一個被藏起來的猜測。這一條原本反對的是**我們自己偷偷選一種**，不是反對合成存在。
2. **「規則看不出指的是哪一種」**——這是可以修的，而且要修在名字上，不是靠拿掉功能:欄位名是「整體聽力正常（優耳）」，事實路徑是 `case.hearing.betterEarNormal`。匯出的 JSON 裡讀到的字就是 `betterEarNormal`，收到檔案的治療師手上沒有這個 app 也讀得懂。**原本的反對其實是在反對一個沒有名字的合成。**
3. **實齡／矯正齡的類比在這裡斷掉。** 那兩個年齡沒有任何外部慣例指定該用哪一個，所以「不自動挑」是唯一誠實的做法。優耳有一個可以指名、可以查證的外部慣例，情況不同。

**左右耳兩個事實照樣保留。** 合成是**加上去的**，不是取代:要寫「兩耳都正常」的人照樣兩列 AND，要寫「左耳異常」的人照樣寫得出來。原本那個決定唯一真正保住的東西（不失去表達力）一點都沒有損失。

### 優耳在資料不全時是什麼

這是這一節最容易做錯的地方，所以把真值表寫死:

| 左耳           | 右耳           | `betterEarNormal` | 理由                                             |
| -------------- | -------------- | ----------------- | ------------------------------------------------ |
| 正常           | 任何（含未填） | `true`            | 優耳至少跟這一耳一樣好，另一耳是什麼都不影響結論 |
| 任何（含未填） | 正常           | `true`            | 同上                                             |
| 異常           | 異常           | `false`           | 兩耳都異常，優耳只能是異常                       |
| 異常           | 未填           | `undefined`       | **沒填的那一耳可能才是優耳**，結論還沒定         |
| 未填           | 異常           | `undefined`       | 同上                                             |
| 未填           | 未填           | `undefined`       | 什麼都不知道                                     |

```ts
/**
 * 整體聽力狀態看優耳 —— the convention Taiwan's disability determination uses, the therapist's
 * ruling. Deliberately named after that basis: an exported rule carries `betterEarNormal` in its
 * JSON, so a therapist reading the file elsewhere can tell which reading it means.
 *
 * Order matters. One normal ear settles it whatever the other ear is (the better ear is at least
 * that good), but one abnormal ear settles nothing — an unrecorded ear could be the better one,
 * so the answer stays undefined and the unrecorded-field gate keeps the rule from firing.
 *
 * Lossy projection: adding a member to HearingStatus (Q2's 「配戴助聽器」) means deciding what it
 * counts as here, not just in leftNormal/rightNormal.
 */
function betterEarNormal(hearing?: CaseHearing): boolean | undefined {
  if (hearing?.left === 'normal' || hearing?.right === 'normal') {
    return true;
  }
  if (hearing?.left === 'abnormal' && hearing?.right === 'abnormal') {
    return false;
  }
  return undefined;
}
```

**「異常 ＋ 未填」是 `undefined` 而不是 `false`，這一格是整張表的重點。** 直覺會想「已經有一耳異常了，整體當然算異常」——那是把「優耳」讀成了「任一耳」。優耳是兩耳裡**比較好**的那一隻，沒填的那一隻完全可能是正常的，那樣整體就是正常。填一半就下結論，等於替沒填的那一耳假設它也是異常。

### 守門在這一格上的行為是對的

`hasFact()` 逐段走點路徑，最後一段要 `!== undefined && !== null` 才算有值，所以 `betterEarNormal` 是 `undefined` 時，**任何**用到它的比較列都會讓整條規則不成立——不管那條規則寫的是 `== true` 還是 `== false`。這正是要的:不知道就不判斷，跟沒填生日一樣。

兩種寫法都會被守門擋住，這一點要在測試裡釘住:一個「異常 ＋ 未填」的個案，對「整體聽力正常 == true」與「整體聽力正常 == false」**兩條規則都不觸發**。少了後者那一則測試，把 `undefined` 悄悄改成 `false` 的改動不會有任何東西抗議。

實作上這個事實可以是「這個 key 不存在」或「這個 key 的值是 `undefined`」，`hasFact()` 兩種都判成沒有值（先 `hasOwnProperty` 再看值）。

### 「看優耳」一定要在畫面上，而 tooltip 不能是唯一的載體

過 `docs/screen-text-policy.md` 的三問:

- **問一:工具行為。** 「身障判定看優耳」本身是外部慣例（換一張紙本表照樣成立，是領域知識）;但**這個 app 的「整體聽力正常」是用優耳算出來的**，是我們的實作決定，換一個工具不成立。要講的是後者。
- **問二:無聲級。** 一個以為它是「兩耳都正常」的人，會寫出一條在單側聽損個案身上照樣觸發的規則，而畫面上看不出任何異狀。
- **問三:無聲地產生錯判斷。**

**判定:一定要講。** 依準則的分工，PM 定「要不要講」與份量上限（一句話，說工具會做什麼），UX 定形式與位置。但這裡 PM 多壓一個下限，理由寫清楚:

**開發者要求的 tooltip 照留，但它不能是唯一的載體。** hover 才看得到的字，掃視選單時不存在、觸控裝置上不存在;更要緊的是**規則匯出成檔案之後 tooltip 完全不存在**，而「別的治療師讀得懂這條規則嗎」正是當初反對合成事實的核心。所以最低要求是兩個常駐的載體:

1. **欄位名本身**——「整體聽力正常（優耳）」。介面標籤不受份量準則管，成本是零。這跟例四判過的「一個裸的聲調符號沒有名字讀不出來，旁邊那個中文名是資料」是同一個做法。
2. **事實的路徑**——`case.hearing.betterEarNormal`。這是唯一跟著匯出檔案走的載體。

tooltip 承接完整那一句（「整體狀態看兩耳中較好的那一耳」），是加分，不是替代。UX 可以判斷要不要比照 `MODE_HINTS` 做成選到該欄位時出現的一行白話重述。

左右耳那兩個欄位**不需要**這個揭露:它們是原始記錄，沒有任何合成，填什麼就是什麼。

### 三態不能用兩態的控制項——現在有兩組

「未填／正常／異常」是三個狀態，而一個 switch 只有兩個位置。一個預設在「正常」的開關，會讓**每一個現有個案**都靜靜地主張自己聽力正常——這正是準則第三問裡「無聲地產生錯判斷」那一級。所以 PM 這邊的要求是**兩耳都不准有預設值**，具體用什麼控制項（三段式、`select` 第一項留白、比照〈出生週數〉的 placeholder）是 UX 的事。

多出來的一項要求:**兩耳要看得出是同一件事的兩半**，而且**只填一耳是合法狀態**，畫面不能逼使用者兩耳都填才存得起來——治療師手上可能真的只有一耳的資訊，而優耳那個事實在「有一耳正常」時本來就結論已定，不需要另一耳。

### 為什麼領域型別是聯集，事實是布林

因為 `ConditionRow.value` 的型別是 `boolean | number`——**條件列根本比不了字串**。要讓 `case.hearing.left == 'normal'` 寫得出來，得動 `ConditionOperator`、動 `value` 的型別、動編輯器的值輸入框、動已經匯出的規則檔會長什麼樣。為了這幾個欄位做這些不值得。

反過來把領域型別也做成布林（`left?: boolean`）則會在第一次要加第三個值的時候卡住——Q2 問的「配戴助聽器」如果是一個獨立狀態，聯集加一個成員就好，布林要改資料形狀。

代價寫清楚:**投影是有損的。** 聯集之後多出來的成員不會自動有正確的布林值，加成員的人必須同時決定它在 `leftNormal`／`rightNormal` **以及 `betterEarNormal`** 這三處各算什麼。型別註解要寫這句話。

### 這次不做:純音聽力檢查評估表

那張表要記左右耳 × 氣導骨導 × 各個頻率的閾值，是一張有自己輸入方式的儀器表，也就是 `FormBody` 要多一個 `kind`。**分左右耳只解決了「哪一耳」這一個維度，其餘維度一個都沒解決。** 依 `docs/ARCHITECTURE.md` 第二節，**這是程式碼不是資料**——治療師沒辦法自己加，每一次都得寫程式，而且照 `CLAUDE.md` 的範圍紀律，「加一張目前沒有的表」本來就是它自己的 change。

延後的理由不只是工程量，主要是**這張表上幾乎每一格都是這裡沒有的臨床內容**:測哪些頻率、dB 的範圍與級距、要不要記遮蔽、氣導骨導差多少才算傳導性、哪一組門檻算「正常」（要不要用平均？平均哪幾個頻率？切在幾 dB？）、要不要分程度。這些一個都不能猜。

還有一個更難反悔的問題必須先問清楚，**這才是延後真正的理由**:那張表跟這兩個欄位是什麼關係？

- 表**推導**欄位 → 欄位變成推導值，不能手填（比照生日推月齡的做法:推導結果不存）。
- 兩者**並存** → 就會有一個個案的左耳欄位寫「正常」而聽檢資料寫「異常」的情況，那時要聽誰的。

現在先做欄位不會擋住任何一種;現在先猜一種關係才會。所以這次明寫:**三個聽力事實的唯一來源是這兩個欄位**，將來那張表要覆寫它們、還是要換掉它們，由那個 change 決定。

## 五、條件列:兩種新對象

把要寫的東西拆開，逐支對現有的條件列詞彙:

| 支                       | 現在寫得出來嗎               | 要動什麼                        |
| ------------------------ | ---------------------------- | ------------------------------- |
| 整體聽力正常／左耳／右耳 | **可以**（新增事實與欄位後） | 加三個 `RuleField`，mapper 不動 |
| 有某一類構音錯誤         | 勉強，而且很脆               | 新增一種 `subject`              |
| 母語包含某個語言         | **不行**                     | 新增一種 `subject` ＋ 集合對照  |

### 聽力

`{"==": [{"var": "case.hearing.betterEarNormal"}, true]}` 就是一個普通的比較列。`CASE_FIELDS` 加三筆:

```ts
{ id: 'case.hearing.betterEarNormal', label: '整體聽力正常（優耳）', kind: 'boolean' },
{ id: 'case.hearing.leftNormal', label: '左耳聽力正常', kind: 'boolean' },
{ id: 'case.hearing.rightNormal', label: '右耳聽力正常', kind: 'boolean' },
```

`hasFact()` 已經會走點路徑（深度不限），所以未填的個案自動不觸發，跟沒填生日一樣。`condition-mapper.ts` 一行都不用改。

### 有某一類構音錯誤

**今天的寫法**:一列 `set` 條件，對象「構音錯誤目標音」、模式「包含」，把那一類的 id 全部勾起來。它會動，但有兩個毛病:

1. 條件編輯器的選項標籤用的是 `s.symbol`，聲調那一組就是五個沒有名字的 `ˉ ˊ ˇ ˋ ˙`（格子表那邊是特地用 `label` 才讀得出來的）。
2. 它把「這一類」表達成「這幾個 id」。之後只要清單有任何變動，這條規則就靜靜地少涵蓋一個，而規則長得跟原來一模一樣。

**要做的**:`ConditionSubject` 加一個 `'articulationCategory'`，比對每一筆錯誤的 `targetCategory`:

```json
{ "some": [{ "var": "articulation.errors" }, { "in": [{ "var": "targetCategory" }, ["initial"]] }] }
```

`ArticulationErrorFact.targetCategory` 已經存在，**不用改資料結構**——這正是 `add-articulation-rule-conditions` 當初預留的那一格。選項的四個名字直接取 `ZHUYIN_CATEGORY_LABELS`，不另外造字。

「排除」對這個對象照樣有意義而且好用:存在型的「排除 聲調」讀作**扣掉聲調之後仍然有其他類別的錯誤**，就是決定三需要的那個出口。

### 母語包含某個語言

寫不出來，兩條路都不通:比較列只比純量、而且只吃 `boolean | number`;`set` 列的集合是寫死的 `articulation.errors`。

**要做的**:讓 `set` 列的集合**由 subject 決定**，並加一個 `'nativeLanguage'`:

```ts
const SUBJECT_COLLECTION: Record<ConditionSubject, string> = {
  articulationTarget: 'articulation.errors',
  articulationProcess: 'articulation.errors',
  articulationCategory: 'articulation.errors',
  nativeLanguage: 'case.nativeLanguages',
};
```

編出來的形狀沿用 `processIds` 已經在用的「純量陣列」寫法（`{"var": ""}` 是 json-logic-js 對當前元素的稱呼）:

```json
{ "some": [{ "var": "case.nativeLanguages" }, { "in": [{ "var": "" }, ["taiwanese"]] }] }
```

**為什麼是加 subject 而不是新開一個列型別。** `ConditionTrialRow` 之所以自成一型，理由寫在型別註解裡:trial 的每個子句都在**收窄同一筆嘗試**，是單一項目上的合取，跟 set 列的成員判定不是同一種東西，而且共用型別會硬拖進 `mode: 'excludes'` 那個在吞嚥情境沒有意義的存在型語意。母語列**不是**這種情況——它就是一個集合上的成員判定，跟 set 列一模一樣。既然語意相同，多一個型別只會多一份要維護的來回轉換。

### 來回轉換的一個約束

`fromJsonLogic()` 目前靠 `some` 的**集合**分辨 trial 與 set，再靠**內層述詞的欄位名**分辨 target 與 process。母語列的內層述詞是 `{"in": [{"var": ""}, [...]]}`，沒有欄位名可看，跟 process 列的內層長得一模一樣。所以反解時**必須先看集合再看述詞**:集合是 `case.nativeLanguages` 就是母語列，不必看述詞。實作時這是 `setRowFrom()` 的第一件事，不是最後的 fallback。

（`add-score-band-conditions` 也會動 `fromJsonLogic()`，但動的是 `and` 與二元比較那兩條路徑，跟這裡不衝突;先後都可以，後做的那份 rebase 一次測試檔即可。）

### 決定六那條附註規則長這樣

```json
{
  "and": [
    { "some": [{ "var": "case.nativeLanguages" }, { "in": [{ "var": "" }, ["taiwanese"]] }] },
    {
      "some": [
        { "var": "articulation.errors" },
        { "in": [{ "var": "targetPhonemeId" }, ["zh", "ch", "sh", "r"]] }
      ]
    }
  ]
}
```

（第二列的內容是治療師自己挑的，這裡只是示意。）全部是 JsonLogic 原生運算子，沒有自訂的東西，匯出去對別的實作照樣成立。

## 六、未填欄位的守門要延伸到母語列

`evaluateCondition()` 的守門**只走比較列**，`set` 與 `trial` 刻意跳過，理由在 `docs/ARCHITECTURE.md` 第三節寫得很清楚:它們跑在一個清單上，而**空清單是「沒有記錄到」這個合法答案**。

母語不是這種東西。「這個孩子沒有母語」不是一個臨床答案，那只是欄位還沒填。而 `some` 對空陣列回 `false`，於是:

- 沒填母語 → 規則不觸發
- 填了母語、但不含指定的語言 → 規則不觸發

兩者長得一模一樣，而它們的意思差很多。所以:

1. **`case.nativeLanguages` 未填時是 `undefined`，不是 `[]`。** 這樣兩種狀態在事實層是分得開的。
2. **母語列要參與守門**:`comparisonFieldIdsIn()`（名字屆時要改，它不再只收比較列）對 `subject === 'nativeLanguage'` 的 set 列回 `['case.nativeLanguages']`。構音那三種 subject 維持跳過，理由不變。

這是本案唯一一處推翻既有註解裡的通則的地方，所以理由要寫進程式碼的註解:**跳過守門的理由是「空清單是合法答案」，不是「set 列一律跳過」。** 母語不滿足那個前提。

決定六那條附註規則因此有一個值得講明的非對稱行為:**警示照樣跳，附註只在母語填過的時候才跳。** 這是對的——不知道個案的語言背景時，系統沒有立場說那個錯誤可能是方言變異。

### 這會讓 6.4 那個缺口多幾個入口

`docs/screen-text-policy.md` 6.4 記著:警示頁的「目前沒有規則被觸發」同時代表「都判斷過而沒對上」與「有規則因為缺資料而根本沒判斷」，而畫面上分不出來。本案新增的欄位（母語、左耳、右耳）都會落進後者，而且「只填了一耳」是一個新的、很容易發生的落點。

補那個機制是它自己的 change（見 proposal 的範圍外）。這次做一件小的:個案頁那一行「沒填生日的話，用到年齡的規則不會判斷」改成講**機制**而不是講**生日**——`docs/screen-text-policy.md` 例二已經判定過「要講的是那個機制不是那個欄位」，本案正好是那句話預言的第二、第三、第四個欄位。

### 三問覆核

本案要放上畫面的東西，逐項過一次準則第五節的檢查表:

| 要放的東西                           | 判定                                                                                                                   |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 母語欄位的 label、選項名、其他輸入框 | **介面標籤**，不受份量準則管                                                                                           |

## 七、儲存升版:會毀掉什麼

`Case` 新增的欄位（母語兩個、聽力一個巢狀物件）都是選填的，舊資料讀出來就是 `undefined`——而 `undefined` 的意思正好就是「未填」，包含「只填一耳、另一耳缺席」這種情況，這都是正確的意思。**所以只為了這些欄位不需要升版。**

會逼出升版的只有一件事:**種子只在集合是空的時候才跑。** 所以

- 要讓示範個案帶上母語／聽力 → 得升 `CASES_KEY`。
- 要出貨決定六那條附註規則 → 得升 `RULES_KEY`。

而**升版是作廢不是遷移**，這是 `storage.ts` 最上面寫明的 PoC 取捨。還有一個沒寫在那裡但這次必須講的:**升版必須所有 key 一起升。** 各集合分開存，只升 `CASES_KEY` 的話個案沒了，但課節紀錄、填答值、構音音對、音韻歷程覆寫、吞嚥嘗試、報告草稿全部留著，指著一堆不存在的個案 id——`removeCase()` 的連動刪除不會被升版觸發。所以既有的 key 才會全部一致停在 `:v7`。

一起升到 `:v8` 會歸零的東西，講白話:

- 所有個案，以及他們的所有課節紀錄
- 每一張表填過的值、每一格構音音對、每一筆音韻歷程覆寫、每一筆吞嚥嘗試
- 每一份報告草稿
- **治療師自己新增的評估項目、自己新增的音韻歷程、自己寫的規則**（這一項最貴，因為那是使用者自己產出的內容，不是示範資料）

規則可以匯出成檔案再匯回來，其他的不行。

**建議:不升版**（Q5）。附註規則的價值在於「寫得出來」，而不在於「內建好了」;治療師在編輯器裡建一次的成本，遠低於所有人資料歸零，而且那條規則的內容本來就該由他自己定。

## 八、事實物件不變量

新增的事實都在 `case.` 底下:

```
{
  ...profile.values,          // 項目值仍然平鋪在最上層，一個字沒動
  case: {
    ageInMonths,
    correctedAgeInMonths,
    nativeLanguages,
    hearing: { leftNormal, rightNormal, betterEarNormal }
  },
  articulation: { errors: [ { targetPhonemeId, targetCategory, errorPhonemeId, diacritic, processIds } ] },
  swallowing: { trials: [ ⋯ ] }
}
```

沒有新增任何最上層的 key，所以項目 id 全域唯一且平鋪的那個不變量不受影響，已經匯出的規則檔（`{"var": "drooling"}` 那種）一條都不會壞。`case.hearing.` 多了一層巢狀，這不影響 `hasFact()`（它逐段走點路徑，深度不限），也不影響 `{"var": "case.hearing.betterEarNormal"}` 在 json-logic-js 裡的解析。

`articulation.errors` 裡每一筆的形狀也沒有改——`targetCategory` 本來就在。這次是讓條件列指得到它，不是加東西進去。
