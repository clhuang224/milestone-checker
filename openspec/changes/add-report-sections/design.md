# 設計:add-report-sections

## 一、現在的形狀，以及它答不出來的那一句

```ts
export function buildReportDraft(triggeredRules, caseRecord, assessment, values): string {
  return triggeredRules
    .map((rule) => rule.action.reportTemplate)
    .filter((template): template is string => !!template)
    .map((template) => /* 三個代入值 */)
    .join('\n\n');
}
```

```ts
export interface ReportDraftRecord {
  recordId: string;
  text: string;
}
```

一個字串進、一個字串出。畫面上是一個 `<textarea>`、一顆〈重新產生〉、一顆〈複製〉，`draftText = saved?.text ?? generatedText`。

**這個形狀有一個隱含的主張:報告的每一句話都是某一條規則說的。**而規則是門檻被跨過才觸發的東西，所以等價的主張是「報告的每一句話都在講哪裡不對」。開發者要的那一句——「個案能在無提示的情況下說出 SVO 結構的簡單句型」——在這個主張底下沒有位置。

## 二、「現況」從哪裡來:三條路

### 路一:治療師自己打字

**代價**:每次回診都要打。而且它擺明不是自動化，工具在這一段沒有幫上忙。

**但它是唯一今天就對的答案**，理由在下面兩條路的失敗方式裡。

### 路二:從記錄的資料推導

要推導「能做到什麼」，得先有東西代表「做到了」。目前:

- `articulation.errors` 只裝錯誤。`docs/todo.md` 已經記著:「事實模型分不出『測過而且正確』與『沒測』」——格子表本身分得出來（目標詞有填就留著記錄），但事實層沒有把這件事送出去。
- `RecordProfile.values` 是有值的，但 `itemList` 表還沒有畫面，所以實際上一格都填不了。
- 開發者例句裡的**「無提示」是提示層級**。資料模型裡沒有這個維度，連一個欄位都沒有。

就算把上面兩個洞都補起來，第三個洞還在:那句話講的是**能力的上限**（「目前能做到最好的程度」），而資料是一格一格的對錯。從「這幾格對了」跳到「他最好能做到 SVO 結構的簡單句型」，中間那一步是臨床判斷，不是彙總。

### 路三:一條在「成功」時觸發的規則

技術上沒有障礙:規則的條件只是一個述詞，`{"==": [{"var": "canProduceSVO"}, true]}` 跟任何門檻規則一樣跑得動。真正卡住的是兩件別的事。

**卡點一:它踩不到東西。**跟路二同一個洞——沒有代表能力的事實，這條規則沒有 `var` 可以指。

**卡點二:觸發的規則一律是警示。**`evaluateRules()` 回傳的清單同時餵給〈警示〉頁與報告草稿，`RuleAction` 上唯一的分流是 `severity`（重要／警示／提示），三個值都會出現在警示清單裡。一條「能力達標」的規則會在〈警示〉頁上冒出來，而那一頁的標題是「觸發的警示/歸納」。要分流就得讓 `RuleAction` 多一個維度:這條規則的文字進報告的哪一段、算不算警示。**那個欄位會出現在每一份匯出的規則檔裡**，是一個不容易反悔的形狀改動，不該順手做。

### 結論

**這次選路一，而且不把它當成暫時的權宜。**理由不是「路三太難」，是**路三成立的時候，路一還是得在**:提示層級、家庭作息、這次會談裡治療師觀察到但沒有一格可以填的東西——這些永遠會有一部分落在規則以外。報告草稿需要一個「人寫的東西住這裡」的地方，這件事跟事實層以後補得多完整無關。

所以本案要做的不是「加一個備註欄」，是**讓「人寫的」跟「算出來的」在報告草稿裡是兩個平等的層**。

## 三、「反正草稿本來就能編輯」為什麼不是答案

`report-draft.ts` 現在的行為:

```ts
readonly draftText = computed(() => this.saved()?.text ?? this.generatedText());
readonly hasEdits = computed(() => { /* saved.text !== generatedText */ });
regenerate(): void { /* confirm 之後，用 generatedText 蓋掉 saved.text */ }
```

治療師在文字框裡打的字，跟規則產生的文字住在同一個字串裡。於是:

> 資料一改（多記了一筆錯誤音、改了生日、開了一條規則），你就得在「更新規則產生的部分」跟「保住自己寫的字」之間二選一。

`report-draft.html` 那行橘字「這份草稿已經手動改過，重新產生會蓋掉」是誠實的，它揭露了一個真的會發生的破壞——但**它揭露的是這個形狀的症狀，不是一個需要更好文案的地方**。分層之後，〈重新產生〉不再碰手寫的那一層，那句話的涵蓋範圍自然縮小到規則那一層，也才是它本來該有的大小。

### 反過來:規則那一層要不要乾脆改成唯讀？

分層之後有一個很誘人的簡化:規則那一層完全不存、每次現算、唯讀，治療師只在手寫那一層寫字。〈重新產生〉這顆按鈕連同它的 `confirm` 一起消失，`hasEdits` 也不用了。

**否決。**理由就在開發者給的那則警示例句裡:

「個案在某某測驗某某項目為 \_ 分，未達發展里程碑標準，**且家長平日上班，日常語言刺激較不足**，建議提早進入幼兒園，並安排每個月一次語言諮詢。」

「家長平日上班，日常語言刺激較不足」是**這一戶人家的事**。一條要匯出、要分享給別的治療師用的規則，其 `reportTemplate` 不可能知道它。這句話只可能是治療師在規則產生的句子上**逐案插進去的**——也就是說，逐案修改規則產生的文字是那則例句成立的前提。唯讀會把它拿掉。

所以兩層都要能編輯，差別在**誰會被〈重新產生〉蓋掉**。

## 四、要不要具名段落，要幾段

### 兩個候選

| 做法                                             | 形狀                                                                     | 代價                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| **A. 兩層**（建議）:手寫的一層 ＋ 規則產生的一層 | `ReportDraftRecord` 加一個欄位;`Rule.action` 不動                        | 「發現」與「建議」不分家，報告上沒有這兩個小標                            |
| B. 三段:現況／發現／建議                         | `Rule.action` 要多一個「這段文字屬於哪一段」的欄位，並在畫面上分成三個框 | 已匯出的規則檔沒有這個欄位，全部落進預設段;而且治療師寫範本時得先決定切點 |

**選 A，理由來自開發者自己的句子。**那則例句是一整句話流過去的:「⋯⋯未達發展里程碑標準，且⋯⋯較不足，**建議**提早進入幼兒園，並安排每個月一次語言諮詢。」發現與建議在同一個句子裡，中間靠「且」跟「建議」接。要把它塞進 B，治療師得把這句話剪成兩半，然後兩半在報告上會被兩個小標隔開，接不回原來那一句。

**分層的軸線是「這段字是誰寫的」，不是「這段字在講什麼」。**前者是工具知道的事（它知道哪段是自己產的），後者只有寫的人知道。用工具知道的那條軸線切，切出來的界線不會歪。

這一題是 Q1。答 B 的話 1.1 與 2.1 要重做，而且要一併決定舊規則落在哪一段。

### 順序

複製出去的時候兩層要接成一份，順序固定。**預設手寫在前**——開發者把「個案的評估狀況」列為報告該有的內容，聽起來是報告的前段——但這是報告寫作慣例，屬於臨床，不由助理決定，所以是 Q3。畫面上兩個框的上下順序跟複製的順序一致，不能一個順一個逆。

## 五、`ReportDraftRecord`:加欄位，不改欄位

```ts
export interface ReportDraftRecord {
  recordId: string;
  /**
   * 治療師改過的「規則產生的那一層」。undefined 代表沒改過，顯示現算的結果。
   * 本案之前存下來的草稿只有這個欄位，而它裝的內容本來就全部來自規則範本，
   * 所以舊資料讀出來的意思是對的——不必升儲存版號。
   */
  text?: string;
  /** 治療師自己寫的那一層。永遠不由工具產生，〈重新產生〉不碰它。 */
  authoredText?: string;
}
```

### 為什麼這樣不必升版

`storage.ts` 最上面寫著**升版是作廢不是遷移**，而且（`add-case-background-conditions` 的 `design.md` 第七節）**升版必須所有 key 一起升**——只升 `REPORTS_KEY` 會留下一堆指著不存在的紀錄的孤兒。所以升一次版的代價是:所有個案、所有課節紀錄、所有填答值、所有構音音對、所有音韻歷程覆寫、所有吞嚥嘗試、以及**治療師自己新增的評估項目、自己新增的音韻歷程、自己寫的規則**全部歸零。

為了一個報告草稿的形狀付這個代價是不划算的，而且**不必付**:

- 舊記錄 `{ recordId, text }` 讀成「規則那一層被改過、手寫那一層是空的」。這正是它的真實情況——本案之前，那個字串裡的每一個字都來自規則範本或治療師對規則範本的修改。
- 新記錄可能只有 `authoredText`，`text` 缺席，代表「規則那一層沒改過」。

`text` 從必填變成選填是這裡唯一要注意的地方:讀的地方要 `?? ''`，而且**不能**改用空字串代表「沒改過」——治療師可能真的想把規則產生的那一段整段刪掉，空字串是一個合法的覆寫值。

### 否決掉的做法

| 做法                                           | 為什麼不                                                                                                                                              |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `text` 改成 `sections: Record<string, string>` | 段落名還沒定案（Q1／Q2），現在就把段落 id 寫進儲存格式，等於先猜一個答案;而且舊記錄的 `text` 沒有段落 id 可以落腳，要嘛升版要嘛在讀取端硬塞一個預設值 |
| 手寫段落存到 `SessionRecord.note`              | `note` 是通用備註（而且今天連畫面都沒有，見 `docs/todo.md`）。把報告散文塞進去，`note` 就靜靜變成報告內容，而且刪報告草稿不會刪掉它                   |
| 手寫段落存到 `Case` 上                         | 它是**這一次課節**的觀察。掛在個案上等於主張這句話跨課節成立——那正是 Q4 在問、而且有安靜出錯方式的東西                                                |
| 不存，只放在元件的 signal 裡                   | 這正是 `report-draft.ts` 註解裡記著的那個舊 bug:換一筆紀錄，上一次的散文留在畫面上，旁邊沒有任何東西顯示它已經過期                                    |

## 六、`Rule.action.reportTemplate`:一個字不動

```ts
export interface RuleAction {
  message: string;
  severity: RuleSeverity;
  reportTemplate?: string; // 不動
}
```

規則檔是**會被匯出成檔案、在治療師之間傳**的東西（`docs/ARCHITECTURE.md` 第三節，這是整個規則引擎選 JsonLogic 的理由）。而**匯入沒有版本、沒有遷移**:`rule-list` 讀進來的就是檔案裡的形狀。所以任何對 `RuleAction` 的形狀改動，都是對別人硬碟上那些檔案的改動。

因此本案的界線是:

- **可以加選填欄位**（舊檔缺席就是預設值，讀得進來）。
- **不可以改既有欄位的型別或意思**。`reportTemplate?: string` 變成 `{ section, text }` 這種形狀，會讓每一份既有的規則檔在讀進來時 `reportTemplate` 變成一個字串而不是物件，而 `buildReportDraft()` 沒有地方分辨——它會安靜地把物件字串化或整段跳過。**沒有遷移路徑**，因為工具看不到那些檔案。

本案落在第一種以外:它**一個欄位都不加**。Q1 答 B（三段）、或 Q5 答「要成功規則」，才會需要加欄位——那時加的是選填欄位，舊檔落進預設值，而「預設值是哪一段」本身就要當成一個決定寫下來。

## 七、代入值只跑在規則範本上

`{{case.label}}`／`{{assessment.date}}`／`{{value:欄位ID}}` 三個替換維持只在 `buildReportDraft()` 裡跑，**不套用到手寫那一層**（Q8，建議如此）。

理由:代入值存在的目的是讓一條**要分享出去**的規則範本不綁死在某個個案身上。手寫那一層本來就是為這個個案這一次寫的，直接打字就好。而一旦在手寫層生效，治療師哪天真的要在報告裡寫一對大括號，就會被安靜地吃掉——`{{value:xxx}}` 找不到欄位時替換成空字串，畫面上不會有任何抗議。

`rule-editor.html` 那段「可代入（大括號要寫兩層）」的說明因此留在規則編輯器裡不動，**報告畫面的手寫框不重複列出這些 token**——列了就是在說它們在這裡有效。

## 八、畫面

形式與位置是 UX 的，這裡只定「要不要講」。逐項過 `docs/畫面說明文字準則.md` 第五節的檢查表:

| 要放的東西                 | 判定                                                                                                                                                                                         |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 兩層各自的標題（Q2）       | **介面標籤**，不受份量準則管                                                                                                                                                                 |
| 手寫層是空的時候的空狀態   | 狀態陳述。而且「這個框是空的、該由你填」是**自證的**（框就在那裡、有標題）→ 不需要額外解釋為什麼工具不幫他寫                                                                                 |
| 「重新產生會蓋掉」那行橘字 | 不可逆預告，`docs/畫面說明文字準則.md` 6.1 判定保留。本案**不刪它，是縮小它**——文字要講明只蓋掉規則產生的那一層                                                                              |
| 〈重新產生〉的 `confirm`   | 同上，保留，文字同樣縮小                                                                                                                                                                     |
| 〈複製〉複製的是哪些內容   | **無聲級，一定要講。**複製出去的東西跟畫面上看到的不一致（少了一半）是看不出來的——治療師會貼進真正的報告系統才發現。所以複製的範圍必須是**完整的一份**，行為本身就答完這件事，不必額外一行字 |
| 手寫層不支援代入值         | 問二**自證的**? 不是——打了 `{{case.label}}` 不會被替換，看起來就像沒生效，屬於**可疑級**。但本案的作法讓它連可疑都不會發生:報告畫面不提代入值，token 清單只出現在規則編輯器裡                |

**這一項是本案範圍的一部分，不是後續的文案工作**（`docs/畫面說明文字準則.md` 第二節:揭露是功能的一部分）:〈重新產生〉的破壞範圍縮小之後，那行橘字與 `confirm` 的文字必須跟著改。留著舊文字會變成**反向的錯誤揭露**——它會讓治療師以為自己寫的東西有危險，於是不敢按〈重新產生〉，等於分層白做。

## 九、連動刪除

`docs/ARCHITECTURE.md` 第五節記著:`ReportDraftRecord` 沒有被任何一條連動刪除清掉，刪個案或刪紀錄之後草稿會留在 `localStorage` 裡。

本案把它補上（`removeCase()` 與 `removeRecord()`），理由不只是「順手」:

- 本案之前，草稿裡的內容全部是**規則重算得出來的東西**，留著只是垃圾。
- 本案之後，草稿裡裝著**治療師自己寫的散文**。而 `docs/使用說明.md` 明寫「不要在報告草稿裡寫可以辨識出本人的細節」——那句話的前提是治療師刪掉個案時，草稿也會跟著走。今天不會。

這是本案唯一一項不在「報告分層」這條主線上的工作，寫在這裡是為了讓它不被當成夾帶。

## 十、事實物件與規則引擎:完全不動

`buildFacts()`、`evaluateCondition()`、`condition-mapper.ts` 一行都不改。項目 id 全域唯一且在事實物件最上層平鋪的不變量不受影響，已匯出的規則檔的條件與動作也都不受影響。

本案動的是**報告草稿怎麼組、怎麼存、怎麼顯示**，不是規則怎麼判斷。
