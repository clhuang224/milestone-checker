# 提案:add-score-band-conditions

## 為什麼要做

開發者拿標準化測驗的分數去試現有的條件列，發現只夠表達最單純的那一種:

> 除了切截分數 > >= = < <= 以外，另外還有分數區間的類型，例如某個失語症測驗在各種向度都有不同的分數判斷，也可能有加權跟加總。這種規則編輯器要涵蓋。

現在的比較列是「欄位 × 運算子 × 一個數值」，它答得出「達不達到某一條線」，答不出下面三件事:

1. **一個分數落在某一段裡代表某件事。** 不是高於或低於一條線，是「10 到 19 分之間」。目前只能寫成 AND 群組裡的兩列比較，而那兩列各自看起來都像一條獨立的門檻——讀規則的人看不出這兩列其實是同一個區間，改動時很容易只改一邊。

2. **同一份測驗的各向度各有各的判準。** 一份工具吐出好幾個分數，每個分數自己的線不一樣。這件事本身資料模型已經支援（各向度就是各自獨立的評估項目），但它會把「一份測驗」這個概念推到編輯器面前，需要先講清楚我們**不**為了它動事實物件的形狀。

3. **加權與加總。** 判斷的對象不是任何一個記下來的分數，而是幾個分數算出來的一個值。這裡有一個要當場定案的問題:那個算出來的值**存不存**。

第 3 點還牽著一個版權界線。`references/open-questions-research.md` 查證的結論是:常模表與切截分數落在受著作權保護那一側的機率高，而**風險發生在發布**——數字一旦寫進公開 repo 的原始碼就是散布;治療師在自己的瀏覽器裡打進去的同一個數字則是他自己的臨床紀錄。同一個功能，差別只在那個數字是誰放進去的。所以這次要做的是**機制**，而機制裡不能預先填好任何真實的門檻。

## 要做什麼

- **新增「分數區間」條件列**:一個數值欄位落在一個上下界之間，**上下界各自可以含或不含**，而且畫面上要把含不含用白話寫出來。邊界差一分是無聲的臨床錯誤，猜不得。
- **新增「加權總分」條件列**:幾個數值項目各乘一個權重相加，得到的值再拿去比較或落區間。**這個總分不儲存**，每次評估重算。
- **各向度維持各自是一個獨立項目**:一份測驗的各向度分數就是各自獨立的 `FindingDefinition`，id 全域唯一、在事實物件最上層平鋪，這次**不動**。要做的只是把這個結論寫成規格釘住，並說明代價。
- **兩種新列都只用 JsonLogic 原生運算子**:區間用 `and` ＋ `<`／`<=`，加權總分用 `+`／`*`。不自訂 operator。
- **反解不得把手寫的兩列比較誤認成區間**:`fromJsonLogic()` 要認得出自己寫出去的形狀，而且只認得出那一種。作法見 `design.md` 第三節。
- **未填欄位的守門延伸到兩種新列**:區間列看它那一個欄位，加權總分列看它**全部**的項目——只填了一半的總分不是總分。
- **佔位示範內容**:規則與文件裡出現的測驗一律用開發者給的佔位形狀「某某標準化測驗 聽理解分測驗 切截分數 達 10 分 → 建議安排語言治療」。

## 這次不做的事（範圍外）

- **不做「具名等第目錄」。** 也就是不把一組區間（重度／中度／輕度那種）存在項目定義上、規則只引用名稱。理由是它會讓一條規則離開它引用的那份目錄就沒有意義，而規則檔是要單獨匯出、單獨傳給另一位治療師的。完整的取捨與日後要做的話怎麼加，見 `design.md` 第二節。
- **不做常模表或原始分轉標準分的對照。** 這正是查證報告裡「不行」的那一格。治療師手上有測驗、也已經算好標準分，他要輸入的是那個算好的數字。
- **不做四捨五入、無條件進位、取整。** json-logic-js 沒有原生的 `round`／`floor`／`ceil`，用 `%` 湊得出來但那是一個沒有人看得懂的算式。要做的話得先問清楚在哪一步取整。
- **不做平均**（除以項數）。理由不是做不到（`/` 是原生的），是**不需要**:權重是常數，所以「加權平均 ≥ t」跟「加權總分 ≥ t × 權重和」是同一件事，門檻自己乘過去就好，表達力沒有損失。見 Q3。
- **不做「N 個向度低於切截就警示」的計數條件。** 這是一種不同的東西——它問的是有幾條線被跨過，不是一個值落在哪裡。用 `if` ＋ `+` 湊得出來，但它該有自己的一列與自己的畫面。見 Q5。
- **不做 `itemList` 表的編輯與填答畫面。** 這是已知的既有缺口（`docs/todo.md`），也是這次最大的一個現實:**分數項目今天在 app 裡填不進去**。這次做的是條件那一層，做完之後規則寫得出來、存得住、匯得出去、反解得回來，但要真的觸發，得等那張表的畫面。這一條的完整說明見下面〈這次做完之後還不能做什麼〉。
- **不做警示頁「有規則因為缺資料而根本沒判斷」的分辨。** 那是 `docs/畫面說明文字準則.md` 6.4 記的缺口。本案會讓它**多很多入口**——一條加權總分規則有幾個項目就有幾個入口——但補那個機制是它自己的 change。
- **不做評估項目 id 重複的檢查。** 一份測驗有十幾個向度時，id 撞名的機會比現在高得多，而目前沒有任何程式在擋（`docs/ARCHITECTURE.md` 第三節明寫這個代價）。它屬於項目編輯那一側，不屬於條件這一側。
- **不動既有的比較列。** `ConditionRow` 的型別、它寫出去的 JSON、它的反解路徑，一個字都不改。已經匯出、已經傳出去的規則檔行為完全相同。

## 這次做完之後還不能做什麼

寫下來免得被誤讀成做壞了。

`STARTER_FINDINGS` 是空的，`itemList` 表既沒有編輯項目的畫面、也沒有填答的畫面。所以今天規則編輯器的欄位下拉裡，數值欄位**只有月齡（實齡）與月齡（矯正齡）兩個**。本案做完之後:

- **分數區間列**可以完整驗證，因為月齡是數值欄位——「月齡 48 到 60 之間（兩端含）」是一條寫得出來、也真的會觸發的規則。
- **加權總分列**寫得出來、存得住、反解得回來，但**沒有一組有意義的資料可以餵它**（把兩個年齡加權相加沒有臨床意義）。它的驗證只到單元測試與元件測試，e2e 只驗到「建得出來、重開還原得回同一列」。

這不是本案的缺口，是 `itemList` 表那個 change 的範圍。先做機制不會擋住它;先猜一張表的欄位才會。

## 對既有規格的影響

- **`規則定義` 要 MODIFIED**:條件列從兩種（比較／適用條件）變成四種（比較／分數區間／加權總分／適用條件）。
- **與 `add-tone-and-case-background` 會撞到同兩個檔案。** 那份 change 目前一項都還沒做，它要改 `condition-mapper.ts` 的 `setRowFrom()`（改成先看集合再看述詞）與 `json-logic.ts` 的守門（延伸到母語列）。本案改的是**別的分支**:`fromJsonLogic()` 的 `and` 與二元比較兩條路徑，以及守門的欄位蒐集。兩份互相不依賴，先後都可以，後做的那份 rebase 一次測試檔即可。
- **儲存版號不用動**，除非 Q6 決定要出貨那條佔位規則——seed 只在集合為空時才跑，所以要出貨就得把 `storage.ts` **全部**的 key 一起升版，而**升版是作廢不是遷移**。

## 技術方向

不引入新套件。清點過 `json-logic-js` 原生有的東西之後確認:區間與加權總分**都能用原生運算子寫出來**，不需要自訂 operator，匯出的 JSON 對其他 JsonLogic 實作照樣有意義。取整與常模查表原生做不到，所以這次也不做——這是「做不到就說做不到」，不是「先自訂一個再說」。

原生運算子的清點、選定的 JSON 形狀、以及反解為什麼不會跟手寫的兩列比較混淆，全部在 `design.md`。

## 開始實作前要開發者回答的問題

依實作會撞到的順序排。**每一題都可以用一句話回答。**

### Q1. 區間的邊界要提供哪幾種「含／不含」，預設是哪一種？

目前規劃是四種組合都提供（`[10,19]`、`[10,19)`、`(10,19]`、`(10,19)`），預設**兩端都含**——整數分數的臨床講法「10 到 19 分」是兩端都含。如果實際上只會用到「兩端都含」，只做那一種可以讓 JSON 更小、編輯器少兩個下拉。

**擋住**:1.1、1.2（寫出去的 JSON 形狀與反解）、3.1（畫面上有幾個控制項）。

### Q2. 加權總分的權重可以是小數與負數嗎？

例如 0.5、或用 −1 表示某個向度要扣分。純粹是輸入驗證，不影響型別與 JSON 形狀。

**擋住**:3.3（權重輸入格的限制），不擋前面。

### Q3. 「加總之後除以項數」的平均要不要做？

規劃是**不做**:權重是常數，「加權平均 ≥ t」等價於「加權總分 ≥ t × 權重和」，門檻自己乘過去就好，所以不做並沒有少掉任何寫得出來的規則。除非你要的是畫面上看得到「平均」這兩個字。

**擋住**:1.4（`/` 要不要進 JSON 形狀）。答「不做」的話這一題就永久關掉。

### Q4. 加權總分只提供 `>` `>=` `<` `<=` 與區間，不提供 `==` 與 `!=`，可以嗎？

理由是權重一旦是小數，浮點數的相等比較會在看不出來的地方失準——一條寫著「總分等於 30」的規則可能永遠不觸發。

**擋住**:3.3（判定的下拉選項）。

### Q5. 「有 N 個向度低於各自的切截分數就警示」要不要在這次做？

這是一種跟區間、加權都不一樣的判定:它問的是**有幾條線被跨過**。原生 `if` ＋ `+` 湊得出來，但它要自己的一列與自己的畫面。

**擋住**:整份範圍。要的話 `tasks.md` 多一節，而且要先問清楚「低於切截」的每一條線是不是各自不同。

### Q6. 那條佔位規則（「某某標準化測驗 聽理解分測驗 切截分數 達 10 分 → 建議安排語言治療」）要不要現在就出貨成 starter 內容？

要的話有兩個連帶代價:(1) 它引用的分數項目今天**填不進去**（`itemList` 表沒有畫面），所以那條規則永遠不會觸發，還會在〈警示〉頁那個「沒判斷／判斷過了」分不出來的缺口上多佔一格;(2) seed 只在集合為空時才跑，所以要出貨就得把 `storage.ts` **全部**的 key 一起升版，而升版是作廢不是遷移——每一位已經開過這個 app 的人，個案、課節紀錄、構音音對、自己寫的規則，全部歸零。

不出貨的話，`design.md` 與《使用說明》裡照樣寫這個例子，只是不進 `starter-rules.ts`。

**擋住**:第 5 節（且只擋這一節）。

### Q7. 分數項目要不要記「這個分數是哪一份測驗的」？

查證報告把「測驗名稱」列在第 1 層（可以記錄，是事實陳述），而目前 `FindingDefinition` 沒有任何欄位表達它屬於哪一份工具——`sourceNote` 是自由文字。有這個欄位的話，條件列的欄位下拉就能依測驗分組，一份測驗有十幾個向度時差很多。

**擋住**:本案不擋任何一項——本案照現況做，下拉維持一份平的清單。這一題擋的是它自己的那個 change，現在問是因為它會決定那個 change 要不要開。
