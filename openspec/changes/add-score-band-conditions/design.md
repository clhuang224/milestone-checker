# 設計:add-score-band-conditions

## 〇、先把可用的原料清點完

整份設計受一條硬約束支配:`docs/ARCHITECTURE.md` 第三節寫的「只用原生運算子，不自訂 operator」。自訂了，匯出的 JSON 對別的 JsonLogic 實作就沒有意義，而規則檔要單獨傳給另一位治療師才是它存在的理由。所以先讀 `json-logic-js` 的原始碼，確認手上到底有什麼:

| 需要的能力       | 原生有沒有                   | 註                                                                                                   |
| ---------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| 上下界都比一次   | **有**，`and` ＋ `<`／`<=`   | 也有三參數寫法，見第三節為什麼不用                                                                   |
| 三參數的 between | **有**，`{"<": [lo, x, hi]}` | `logic.js` 的 `<` 與 `<=` 第三個參數在，`jsonlogic.com` 的規格也寫了。但**只有兩端同時含或同時不含** |
| 加               | **有**，`+`，可變參數        | `reduce` 起始值是 `0`，所以 `{"+": []}` 是 **0** 不是錯誤——第四節的一個地雷                          |
| 乘               | **有**，`*`，可變參數        | 沒有起始值，一個參數時回它自己                                                                       |
| 減、除           | **有**，`-`／`/`             | 這次用不到，見〈平均〉                                                                               |
| 取最大／最小     | **有**，`min`／`max`         | 「兩個向度取高的那個」寫得出來，這次不做成一列                                                       |
| 條件式           | **有**，`if`／`?:`，可變參數 | 查表與計數都湊得出來，這次不做，見 proposal 的 Q5                                                    |
| 四捨五入／取整   | **沒有**                     | `%` 湊得出正數的無條件捨去，但那是一個沒有人看得懂的算式。**做不到就說做不到**                       |
| 常模查表         | 技術上用 `if` 鏈湊得出來     | 但那正是查證報告裡「不行」的那一格，是**不做**而不是做不到                                           |

結論:這次要做的兩件事**都在原生範圍內**，一個自訂 operator 都不需要。做不到的那兩格（取整、查表）在 proposal 的〈這次不做的事〉裡明寫，不用替代方案硬湊。

另外一件在寫任何形狀之前就要知道的事:`+` 與 `*` 內部用 `parseFloat`，而 `{"var": ...}` 對缺少的鍵回 `null`。`parseFloat(null)` 是 `NaN`。這條性質決定了第五節整節。

## 一、三個要求各自變成什麼

開發者提的三件事，答案不一樣:

| 要求         | 這次的答案                                                       |
| ------------ | ---------------------------------------------------------------- |
| 分數區間     | **新增一種條件列**（`type: 'band'`）                             |
| 各向度各自判 | **什麼都不做**——資料模型已經支援，把它寫成規格釘住，並說明代價   |

中間那一列是刻意的。它看起來像一個要求，實際上是一個**不要動事實物件**的要求，第六節說明。

## 二、分數區間:一列一個區間，區間的數字長在規則上

### 考慮過的三種形狀

**（甲）一列一個區間，上下界寫在那一列上。**「這個欄位落在 10 到 19 之間」就是一列，兩個數字是這一列自己的東西。

**（乙）具名等第目錄。** 在項目定義上掛一組區間（`{ id: 'severe', label: '重度', min: 0, max: 9 }` 這種），條件列變成「這個項目的等第是『重度』」。

**（丙）由治療師逐項自訂等第。** 是（乙）的一種說法——目錄由治療師編，不是內建。

### 選（甲），理由是規則檔要能單獨活著

（乙）跟（丙）在編輯體驗上明顯比較好:等第只定義一次，之後每條規則都引用它，改一次全部改到，而且畫面上讀到的是「重度」不是「0 到 9」。這個好處是真的。

但它跟這個專案的一條硬約束正面相撞。規則存成 JsonLogic 的理由是**要匯出成檔案、在治療師之間傳**。一條「等第是重度」的規則，匯出之後有兩種可能:

- 匯出的 JSON 把等第**編譯成邊界數字**——那它就是（甲），只是編輯器上長得不一樣;而且反解回來時等第的名字已經掉了，`fromJsonLogic()` 認不回「重度」這兩個字，除非再引入一份對照。
- 匯出的 JSON **引用等第的 id**（`{"==": [{"var": "xxx.band"}, "severe"]}`）——那這條規則離開它引用的那份目錄就沒有意義。收到檔案的治療師手上沒有那份目錄，`severe` 是什麼、邊界在哪，檔案裡讀不出來。而且它還要求事實物件多出一個 `xxx.band` 的推導欄位，等於把「哪個分數算重度」這個臨床判斷藏進事實層。`add-case-background-conditions` 後來確實做了一個合成事實（整體聽力看優耳），但那是**反例而不是先例**:那個判斷由開發者定案、有一個可以指名的外部依據，而且**名字本身帶著判準**（事實路徑就叫 `betterEarNormal`），所以匯出的檔案自己讀得懂。等第這三樣一樣都沒有——邊界是每一份目錄自己的，離開那份目錄就讀不出來。

所以:**區間的數字長在規則上，跟門檻長在比較列上是同一件事。** 一條規則自己就說得完自己的意思。

日後真的要做（乙），它是一層**編輯器上的預設值**，不是一層儲存格式:治療師從目錄挑一個等第，編輯器把邊界**填進**這一列，存下去的還是（甲）的形狀。那樣就沒有上面兩個問題，而且不需要遷移任何既有規則。這條路留著，這次不走。

### 為什麼不是「用兩列比較就好」

因為那正是開發者說不夠的地方。技術上「兩列比較」跟「一個區間」求值結果一樣，差別在**讀規則的人**:兩列各自看起來都像一條獨立的門檻，看不出它們是同一段的兩端，改動時很容易只改一邊，而且改完照樣存得下去、照樣跑。這是一種無聲的錯。一列一個區間讓「這是一段」變成看得見的東西。

### 邊界含不含:四種都提供，預設兩端都含

一分之差在臨床上是真的差，而且錯了不會有任何徵兆——規則照樣觸發或不觸發，只是在不對的個案身上。所以:

- **兩端的含／不含各自獨立設定**，四種組合都寫得出來。
- **預設兩端都含**（`[min, max]`）。整數分數的臨床講法「10 到 19 分」就是兩端都含。
- 畫面上**永遠**顯示白話重述，例如「分數在 10 分（含）到 19 分（含）之間時成立」，而且跟著下拉即時變。理由與作法見第七節。

只提供「兩端都含」是一個合理的簡化選項（Q1），代價是連續分數的相鄰區間會蓋不住或重疊——`[0,10]` 跟 `[10,20]` 在 10 這一點同時成立。整數分數不會碰到，非整數分數會。

無效的區間要出聲:下界大於上界、或上下界相等但有一端寫成不含，這一列就永遠不成立。這跟「還沒選任何項目」的空適用條件列是同一種狀況，用同一種橘字處理。

## 三、JsonLogic 怎麼寫，以及反解怎麼不混淆

### 選定的形狀

一律寫成 `and` 底下兩個二元比較，**下界那一句把數字寫在左邊**:

```jsonc
// 「聽理解分測驗的分數在 10 到 19 之間（兩端含）」
{
  "and": [
    { "<=": [10, { "var": "placeholderComprehension" }] },
    { "<=": [{ "var": "placeholderComprehension" }, 19] },
  ],
}
```

四種含／不含就是兩個運算子各自在 `<` 與 `<=` 之間選:

| 區間        | 下界那一句 | 上界那一句 |
| ----------- | ---------- | ---------- |
| `[min,max]` | `<=`       | `<=`       |
| `[min,max)` | `<=`       | `<`        |
| `(min,max]` | `<`        | `<=`       |
| `(min,max)` | `<`        | `<`        |

### 為什麼不用原生的三參數 between

`json-logic-js` 的 `<` 與 `<=` 收第三個參數:`{"<=": [10, {"var":"x"}, 19]}` 就是 `10 <= x <= 19`，規格上也有，比上面短。不用它的理由是:

**它只表達得出兩端同時含或同時不含。** `[10,19)` 沒有三參數寫法。所以採用它的話，四種區間會分成兩種 JSON 形狀——兩種寫出去的路徑、兩條反解的路徑、兩組要維護一致的測試。一種形狀蓋住四種情況，比「兩種形狀、其中一種比較短」好。

如果 Q1 的答案是「只要兩端都含」，這個取捨要重看:那時只剩一種情況，三參數就是更好的選擇。

### 反解怎麼不會把手寫的兩列比較誤認成區間

這是整個形狀選擇的真正原因。

`fromJsonLogic()` 讀到一個 `and` 的時候，它可能是一個群組（治療師自己排了兩列比較），也可能是一個區間列。**如果區間寫成一般的「變數在左、數字在右」，兩者的 JSON 會長得一模一樣**:

```jsonc
// 治療師手寫的兩列比較，放在一個 AND 群組裡
{ "and": [{ ">=": [{ "var": "x" }, 10] }, { "<=": [{ "var": "x" }, 19] }] }
```

那樣的話，一個治療師刻意排出來的兩列群組，重新打開時會變成一列區間——求值結果沒變，但**畫面上的東西跟他寫的不一樣**，而且來回轉換的測試會抓到（群組 → JSON → 區間列 ≠ 群組）。

**下界那一句把數字寫在左邊，就是那個消歧的記號。** 現有的比較列**永遠**寫成 `{ op: [{var}, 數字] }`，變數一定在左邊——`toJsonLogic()` 只有這一條路。所以「數字在左、變數在右」這個形狀在整個檔案裡沒有被任何東西佔用;更精確地說，今天 `fromJsonLogic()` 碰到它會直接丟例外（「first argument must be a { var } reference」），也就是這個形狀現在是**空的**。

反解的判斷因此很短，而且不需要任何額外標記:

```
遇到 and:
  若剛好兩個子句
     且 子句[0] 是 { '<'|'<=': [數字, 目標] }        ← 數字在左
     且 子句[1] 是 { '<'|'<=': [目標, 數字] }        ← 目標在左，且與子句[0] 的目標相同
  → 區間列
  否則 → 群組（原本的行為）
```

「目標」是 `{"var": "欄位"}`（分數區間列）或一個加權總和運算式（加權總分列的區間判定）。兩者要**深層相等**，否則不是同一個區間。

三個要一起講清楚的後果:

1. **手寫的兩列比較照樣是兩列。** 上面那個 `{">=": [{"var":"x"}, 10]}` 開頭的 `and` 走「否則」那一支，還原成群組，跟改動前一模一樣。這要有一則測試釘住，因為它就是這整個形狀選擇要保護的東西。
2. **外面來的 JSON 若剛好寫成數字在左，會被讀成一個區間列。** 語意完全相同，只是畫面上顯示成一列而不是兩列。可以接受:那個形狀今天會丟例外，也就是今天那條規則根本不會被評估（`evaluateCondition()` 攔到例外就回 `false`），能讀成區間是變好不是變壞。
3. **這個約定是承重牆，不是排版偏好。** 有人「順手」把下界那一句改成變數在左，區間列就靜靜地變成群組，而且測試不一定抓得到（求值結果一樣）。程式碼註解要寫清楚，比照 `trialClauses()` 那個 `!= null` 守門的寫法。

### 條件模型的型別

既有的 `ConditionRow` 一個字都不改。新增:

```ts
/** 一段區間。兩端各自可以含或不含——差一分是無聲的臨床錯誤，所以不給共用的預設。 */
export interface ConditionBand {
  min: number;
  max: number;
  minInclusive: boolean;
  maxInclusive: boolean;
}

export interface ConditionBandRow {
  type: 'band';
  fieldId: string;
  band: ConditionBand;
}

export interface WeightedTerm {
  fieldId: string;
  weight: number;
}

/** 加權總分算出來之後怎麼判。 */
export type ConditionThreshold =
  | { kind: 'compare'; operator: ConditionOperator; value: number }
  | { kind: 'band'; band: ConditionBand };

export interface ConditionWeightedRow {
  type: 'weighted';
  /** 至少一項——空的 terms 會讓 `{"+": []}` 求值成 0，見 design 第四節。 */
  terms: WeightedTerm[];
  threshold: ConditionThreshold;
}

export type ConditionNode =
  | ConditionRow
  | ConditionBandRow
  | ConditionWeightedRow
  | ConditionSetRow
  | ConditionTrialRow
  | ConditionGroup;
```

`ConditionBand` 只定義一次、兩邊共用，因為「四個欄位的含意」只該有一份。

## 四、加權總分:算出來的不存

### 存起來還是每次算

`docs/ARCHITECTURE.md` 第一節的立場是明確的:**推導結果一律不存**，只存覆寫。理由是存下來只會讓兩邊有機會不一致。月齡不存（存了當天就開始過期），`derivedProcessGroups()` 不存（存了會跟音對漂掉）。

加權總分**完全落在這條線的同一側**，而且更糟:

| 把總分存成一個項目                                        | 每次評估重算                       |
| --------------------------------------------------------- | ---------------------------------- |
| 治療師改了某個分測驗分數，總分就是舊的，畫面不會抗議      | 永遠跟當下的分數一致               |
| 權重改了，所有已存的總分全部作廢，而且沒有東西知道要重算  | 權重長在規則上，改規則就改到了     |
| 「總分」變成一個 `FindingDefinition`，佔一個全域唯一的 id | 事實物件一個新鍵都不加             |
| 匯出的規則引用那個 id，收檔案的人手上沒有那個項目         | 算式整個長在規則裡，檔案自己說得完 |

最後一列是壓倒性的:**JsonLogic 原生就會算術**，所以那個算式可以整個住在規則的 condition 裡，匯出的檔案自己就完整。存成項目反而讓規則變得依賴外部的東西。

存起來唯一真的好處是「畫面上看得到那個總分」。那是報告與畫面那一層的需求，不是條件這一層的;真的要，是在該顯示它的地方**算一次顯示出來**，仍然不存。

### 寫出去的形狀

```jsonc
// 「A 分測驗 ×2 ＋ B 分測驗 ×1 的加權總分達 30 分」
{
  ">=": [
    {
      "+": [
        { "*": [{ "var": "placeholderSubtestA" }, 2] },
        { "*": [{ "var": "placeholderSubtestB" }, 1] },
      ],
    },
    30,
  ],
}
```

三個決定:

- **權重是 1 也照樣寫出 `{"*": [..., 1]}`。** 省掉的話 `+` 底下會有兩種形狀（裸的 `var` 與 `*` 對），反解要兩條路。JSON 冗一點換反解只有一條路，划算。
- **`+` 用可變參數一次收全部的項**，不做巢狀的兩兩相加。
- **落區間的判定沿用第三節的形狀**，把「目標」從 `{"var": f}` 換成整個 `+` 運算式:

```jsonc
{
  "and": [
    { "<=": [30, { "+": [ ... ] }] },
    { "<=": [{ "+": [ ... ] }, 49] },
  ],
}
```

那一整段 `+` 運算式會**出現兩次**。這是為了「一種形狀蓋住四種區間」付的代價（三參數的 `<=` 可以只寫一次，但只蓋得住兩種）。JSON 大一點，反解時對兩邊做深層相等比較即可。

### 反解

- 二元比較的左邊是 `{"var": ...}` → 既有的比較列，行為不變。
- 二元比較的左邊是 `{"+": [...]}`，而且每一項都是 `{"*": [{"var": f}, 數字]}` → 加權總分列（比較判定）。
- `and` 的兩個子句符合第三節的形狀，而且目標是那個 `+` 運算式 → 加權總分列（區間判定）。
- 其他 → 照舊丟例外。**不要為了寬容而放行沒把握的形狀**:`evaluateCondition()` 攔到例外會回 `false`，也就是放行一個看錯的形狀，等於安靜地把規則的意思改掉。

### 空的 terms 是一個地雷

`{"+": []}` 在 `json-logic-js` 裡求值是 **0**（`reduce` 的起始值是 0），不是錯誤。所以一列沒有任何項目的加權總分列會拿 `0` 去跟門檻比——「總分小於 30」會**成立**，在一條治療師還沒填完的列上。

處理方式跟空的適用條件列同一個立場（那一列刻意什麼都不匹配）:**這一列至少要有一項**，編輯器不讓移除最後一項，型別註解寫明理由。

### 為什麼不做平均

`/` 是原生的，做得到。不做的理由是**做了也沒有多出任何寫得出來的規則**:權重是常數，所以

```
(w₁x₁ + w₂x₂) / (w₁ + w₂) ≥ t   ⟺   w₁x₁ + w₂x₂ ≥ t × (w₁ + w₂)
```

門檻自己乘過去就好。多一個除法只是多一種要維護的形狀、多一條反解路徑、多一個除以零的邊界情況。這是 Q3。

### 為什麼不提供 `==` 與 `!=`

權重一旦是小數，`0.1 + 0.2` 這種浮點數誤差會讓「總分等於 30」在看不出來的地方永遠不成立。一條永遠不觸發的規則沒有任何徵兆。所以加權總分的比較只提供 `>` `>=` `<` `<=`（外加區間）。這是 Q4;既有的比較列不受影響，它比的是治療師直接輸入的一個數，不是算出來的。

## 五、未填欄位的守門:這一節是本案最容易出事的地方

`evaluateCondition()` 在丟給 `jsonLogic.apply()` 之前，先確認條件用到的每個欄位都有值。擋的是 `null < 40` 在 JS 裡是 `true` 這件事。兩種新列各自怎麼落進這道守門:

### 分數區間列

守門要收進**那一個 `fieldId`**。

不能省，理由要寫進註解:選定的形狀裡，下界那一句是 `{"<=": [min, {"var": f}]}`，欄位沒填時它是 `min <= null`。`min` 是正數時 `null` 會被當成 `0`，比較是 `false`，看起來好像自己擋掉了——**但下界是 0 或負數時就擋不掉**（`0 <= null` 是 `true`，`null <= 19` 也是 `true`），整段區間會在一個根本沒填過這個分數的個案身上成立。標準分數可以是 0 或負數。所以這是真的守門，不是防禦性的贅句。

### 加權總分列

守門要收進 **terms 裡全部的 `fieldId`，一個都不能少**。

`+` 與 `*` 內部用 `parseFloat`，`{"var": ...}` 對缺鍵回 `null`，`parseFloat(null)` 是 `NaN`。所以**只要有一項沒填，整個總分就是 `NaN`**，而 `NaN` 跟任何數比較都是 `false`。

這件事的形狀值得看清楚:它**不會**造成誤觸發，它造成的是**假陰性**——整條規則靜靜地不成立，而且畫面上跟「判斷過了，沒對上」長得完全一樣。這正是 `docs/畫面說明文字準則.md` 6.4 記的那個缺口，只是本案讓它從「一個欄位」變成「一條規則有幾個項目就有幾個入口」。

所以守門要**明確地**把全部欄位都要求到，而不是靠 `NaN` 的行為順便擋掉:

- 靠 `NaN` 的話，缺資料跟不成立在系統內部也分不出來，之後補 6.4 那個機制時沒有東西可以撈。
- `NaN` 的行為只在「比較」這個位置成立。放到 `!` 底下 `!NaN` 是 `true`——今天編輯器不會產生那個形狀，但「今天不會產生」不是一個能靠的前提。

### 實作上

`json-logic.ts` 的 `comparisonFieldIdsIn()` 現在只認 `type === 'row'`。它要多認兩種，名字也不再準確（它蒐集的是「要守門的欄位」，不只是比較列），改成 `guardedFieldIdsIn()`:

- `row` → `[fieldId]`
- `band` → `[fieldId]`
- `weighted` → `terms.map(t => t.fieldId)`
- `set`／`trial` → `[]`（維持刻意跳過，理由不變:空清單是「沒有記錄到」這個合法答案）
- `group` → 遞迴

### 順帶一個型別限制

`parseFloat(true)` 是 `NaN`。所以布林項目一旦進了加權總分，整個總分就毀了，而且是安靜地毀。同理，布林值落區間沒有意義。

**分數區間列與加權總分列的欄位下拉一律只列 `kind === 'number'` 的欄位。** 這是型別層的事，不是畫面文字能補的。

## 六、各向度各自判斷:什麼都不做，以及為什麼

開發者提到的情況是一份測驗在各個向度上有各自的分數判準。這有兩種讀法:

**（甲）各向度就是各自獨立的評估項目**，各自一個 id、各自一個值，規則各自寫各自的線。事實物件維持平鋪，什麼都不用改。

**（乙）真的要一個群組結構**，事實物件裡有一層「這份測驗」，底下掛各向度。

選（甲），而且這一次要把它寫成規格釘住，因為（乙）的代價大到不能靠讀 code 才發現。

### （乙）的代價

`docs/ARCHITECTURE.md` 第三節把話講死了:

> **項目 id 維持全域唯一、且在事實物件最上層平鋪，是這個專案最該保護的不變量。**

已儲存與已匯出的規則檔寫的是 `{"var": "drooling"}`。項目一旦改成表限定的路徑（`forms.xxx.yyy`），**所有既有規則、以及治療師之間分享出去的規則檔全部失效，而 `condition-mapper` 沒有遷移路徑**。而本案要加的兩種列會讓這件事更嚴重:一條加權總分規則同時引用好幾個項目 id，遷移的話一條規則要對好幾個路徑，錯一個就是安靜的錯。

而且（乙）換來的東西其實不在事實層:想要的是**編輯器的欄位下拉能依測驗分組**，那是顯示層的事。今天做不到不是因為事實平鋪，是因為 `FindingDefinition` 上沒有任何欄位說它屬於哪一份工具（`itemList` 的 `FormBody` 也不帶項目清單）。那是 Q7，跟事實物件的形狀無關。

### （甲）的代價，照樣要寫出來

`docs/ARCHITECTURE.md` 第三節同一段也寫了:**兩張不同的表不能有同名的項目 id，這個約束沒有程式在擋。** 一份測驗有十幾個向度時，這件事從「理論上會發生」變成「大概會發生」——例如兩份工具都有一個叫「理解」的向度。

本案不修這個（它在項目編輯那一側），但要在規格裡寫明這個代價存在，免得下一個人以為平鋪是沒有成本的。

## 七、畫面長什麼樣

兩種新列都是既有條件樹裡的一列，跟比較列、適用條件列並排，一樣可以塞進 AND／OR 群組。

### 分數區間列

```
[ 聽理解分測驗 ▾ ]  介於  [ 10 ]  [ 含 ▾ ]   ～   [ 19 ]  [ 含 ▾ ]
分數在 10 分（含）到 19 分（含）之間時成立。
```

那一行白話重述是**必要的，不是裝飾**，過一次 `docs/畫面說明文字準則.md` 的三問:

- **問一(補臨床知識還是工具行為)**:工具行為。「含／不含」是我們的 UI 詞彙，落在哪個數字上是我們的實作決定;換一張紙本評估表不成立。
- **問二(不講會不會自己發現)**:**無聲級**。邊界設錯照樣存得下去、照樣跑，只是在邊界上那一分的個案身上安靜地觸發或不觸發。
- **問三(猜錯的後果)**:產生錯的臨床判斷，而且看不出來。

判定與〈例一〉的「排除是存在型」完全同型:**保留，而且要跟著下拉即時變**——那正是「貼著後果現形的地方」。份量上限一句，不解釋為什麼要有這個功能。

無效的區間再加一行橘字，比照現有的「還沒選任何項目，這個條件不會成立。」:

```
下界大於上界，這個條件不會成立。
```

### 加權總分列

```
加權總分
  [ A 分測驗 ▾ ]  × [ 2 ]        [移除]
  [ B 分測驗 ▾ ]  × [ 1 ]        [移除]
  ＋ 加一項
判定  [ 比較 ▾ ]  [ >= ▾ ]  [ 30 ]
任一項分數沒填，整條規則就不會判斷。
```

那一行揭露同樣過三問:工具行為（第五節那個守門）、無聲級（假陰性，畫面上跟「判斷過了沒對上」一模一樣）、後果是治療師以為這個個案沒有跨過任何門檻。**一定要上畫面。**

位置上，準則說要「貼著後果現形的地方」，那個地方其實是〈警示〉頁——但那是 6.4 的缺口，不在本案範圍。所以這一行先貼在**寫規則的地方**，並且把「本案讓 6.4 多了很多入口」記進 `docs/todo.md`。這是刻意的次佳解，不是沒想到。

「判定」切到「區間」時，右邊換成跟分數區間列一樣的四個控制項與同一行白話重述。

**不上畫面的**（照準則砍掉）:

- 「加權總分不會存起來，每次評估都重算」——猜錯沒有後果，屬於《使用說明》。
- 「權重乘完之後相加」——問一就出局，那是算術不是工具行為。

### 新增列的按鈕

群組底下現在有三顆（＋ 條件／＋ 適用條件／＋ 群組），本案要變五顆，而 `add-case-background-conditions` 還會再往「適用條件」裡塞對象。**怎麼排是 UX 的事**（一顆 ＋ 帶選單、或分兩排），PM 這裡只定名字:「＋ 分數區間」與「＋ 加權總分」。

## 八、否決掉的做法一覽

| 做法                                          | 為什麼否決                                                                                     |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 自訂一個 `between` operator                   | 匯出的 JSON 對別的 JsonLogic 實作沒有意義。`ARCHITECTURE.md` 第三節明文禁止                    |
| 用原生的三參數 `<`／`<=` 寫區間               | 只表達得出兩端同時含或同時不含，四種區間會變成兩種 JSON 形狀、兩條反解路徑。除非 Q1 收斂成一種 |
| 區間寫成「變數在左」的兩句 `and`              | 跟治療師手寫的兩列比較群組長得一模一樣，反解不可能分辨，來回轉換測試會壞                       |
| 在 JSON 裡加一個標記欄位標示「這是區間」      | 那是自訂 operator 的變形，別的實作讀不懂                                                       |
| 混合含不含時把數字改掉（`< 20` 寫成 `<= 19`） | 只有整數分數成立，而我們不知道這個分數的刻度。小數分數上這是安靜地改掉臨床意思                 |
| 具名等第目錄，規則引用等第 id                 | 規則檔離開目錄就沒有意義，而規則檔要能單獨傳。日後可作為編輯器的預設值層，不作為儲存格式       |
| 把加權總分存成一個評估項目                    | 推導結果一律不存（`ARCHITECTURE.md` 第一節）;而且會讓匯出的規則依賴一個外部項目 id             |
| 加權總分支援平均（除以項數）                  | 權重是常數，門檻乘過去等價，不多任何表達力                                                     |
| 加權總分支援 `==`／`!=`                       | 小數權重下浮點誤差會讓規則永遠不觸發，而且沒有任何徵兆                                         |
| 各向度做成事實物件裡的巢狀群組                | 打破「項目 id 全域唯一且平鋪」的不變量，既有與已匯出的規則全毀，沒有遷移路徑                   |
| 靠 `NaN` 的比較行為順便擋掉缺資料的總分       | 缺資料與不成立在系統內部分不出來，6.4 那個機制之後撈不到;而且 `!NaN` 是 `true`                 |
| 內建任何真實測驗的名稱、切截值或常模          | `references/open-questions-research.md` 第二節:風險發生在發布。門檻由治療師自己輸入            |
