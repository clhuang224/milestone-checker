# 任務:add-score-band-conditions

順序就是執行順序。**先做條件模型與反解，再做畫面**——寫出去的形狀一旦反解不回來，`evaluateCondition()` 會攔到例外並靜靜地回 `false`，那條規則就永遠不觸發而且沒有任何徵兆。

## 1. 分數區間:條件模型與 JsonLogic 對應

- [ ] 1.1 （需 Q1）`core/rule-engine/condition-mapper.ts`:新增 `ConditionBand` 與 `ConditionBandRow` 型別，加進 `ConditionNode` 聯集;型別註解寫明「兩端各自可以含或不含，因為差一分是無聲的臨床錯誤」
- [ ] 1.2 （需 Q1）`toJsonLogic()` 寫出區間:`and` ＋ 兩句二元比較，**下界那一句把數字寫在左邊**;程式碼註解寫明這個順序是反解的消歧記號、不是排版偏好，比照 `trialClauses()` 那個 `!= null` 守門的註解寫法
- [ ] 1.3 `fromJsonLogic()` 的 `and` 分支:先試區間的形狀（兩個子句、下界數字在左、上下界的目標深層相等），不符合才退回群組;來回轉換測試涵蓋四種含／不含組合
- [ ] 1.4 **消歧的回歸測試**:一個由兩列手寫比較組成的 AND 群組（兩句都是變數在左）反解回來**仍然是群組**，不會變成區間列;測試名稱與註解要寫明它釘住的是什麼，否則下一個人會覺得這則測試在測廢話
- [ ] 1.5 `defaultBandRow(fields)`:挑第一個 `kind === 'number'` 的欄位，預設兩端都含;沒有數值欄位時的行為比照 `defaultRow()`

## 2. 加權總分:條件模型與 JsonLogic 對應

- [ ] 2.1 （需 Q3／Q4）`condition-mapper.ts`:新增 `WeightedTerm`、`ConditionThreshold`、`ConditionWeightedRow` 型別;`terms` 的註解寫明「至少一項，因為 `{"+": []}` 求值是 0 不是錯誤」
- [ ] 2.2 `toJsonLogic()` 寫出加權總分:`{"+": [{"*": [{var}, 權重]}, ...]}`，**權重是 1 也照樣寫出 `*`**（註解寫明理由是讓反解只有一條路）;比較判定與區間判定兩種都寫得出來
- [ ] 2.3 `fromJsonLogic()`:二元比較的左邊是 `+` 運算式時反解成加權總分列;`and` 的區間目標是 `+` 運算式時也反解成加權總分列;認不出來的形狀**維持丟例外**，不放行
- [ ] 2.4 來回轉換測試:比較判定、區間判定、單一項目、權重為 1、以及既有的比較列與適用條件列完全不受影響的回歸測試
- [ ] 2.5 `defaultWeightedRow(fields)`:一項、權重 1、`>=` 判定——不能是一列什麼都不匹配（或什麼都匹配）的空列

## 3. 未填欄位的守門

- [ ] 3.1 `core/rule-engine/json-logic.ts`:`comparisonFieldIdsIn()` 改名成 `guardedFieldIdsIn()` 並涵蓋 `band`（一個 id）與 `weighted`（**全部** term 的 id）;`set`／`trial` 維持跳過，原註解保留
- [ ] 3.2 單元測試:下界是 0 或負數的區間，在欄位未填時**不**觸發;測試註解寫明它擋的是 `0 <= null` 在 JS 裡是 `true`
- [ ] 3.3 單元測試:加權總分列只要有**任何一項**沒填就整條規則不判斷;測試註解寫明 `parseFloat(null)` 是 `NaN`、`NaN` 跟任何數比較都是 `false`，所以這是假陰性而不是誤觸發，守門必須明確要求全部欄位而不是靠 `NaN` 順便擋掉
- [ ] 3.4 `core/rule-engine/facts.ts`:加一個只回傳 `kind === 'number'` 欄位的輔助函式，供兩種新列的欄位下拉使用;註解寫明布林欄位進了加權總分會讓總分變 `NaN`（`parseFloat(true)` 是 `NaN`）
