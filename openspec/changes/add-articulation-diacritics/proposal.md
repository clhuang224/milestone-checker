# 提案:add-articulation-diacritics

## 為什麼要做

拿一組實際的構音記錄（改寫、簡化過的示意內容）去試現有的構音表格，發現有一整類錯誤**根本存不進去**:

> 蜘蛛 → ㄉㄭⁿ ㄉㄨⁿ、吃飯 → ㄎㄭⁿ 飯、ㄧ → ㄧⁿ、ㄨ → ㄨⁿ

這些是**母音鼻音化**——目標音沒有被換成另一個注音符號，而是在原本的音上面多了一個鼻音成分，書面上習慣寫成右上角的小 `ⁿ`。

現有的 `ArticulationSubstitution.errorPhonemeId` 只能指向注音參考表裡的某一個 `ZhuyinSymbol`，而參考表裡沒有、也不應該有「ㄧⁿ」這種帶附加符號的變體，所以治療師只能把它寫進範例字詞的自由文字備註裡，音韻歷程總覽也就分不到組。

順帶補齊兩個同一批資料暴露出來的缺口:注音參考表沒有**空韻 ㄭ**（ㄓㄔㄕㄖㄗㄘㄙ 單獨成音節時的韻），預設音韻歷程清單也沒有**母音鼻音化**跟**複韻母簡化**。

## 要做什麼

- **音對加附加符號欄位**:`ArticulationSubstitution` 新增一個選填的附加符號欄位，第一版只做「鼻音化」一種。錯誤音跟附加符號互相獨立——可以只有錯誤音（ㄓ→ㄉ）、只有附加符號（ㄧ→ㄧⁿ）、或兩者都有（ㄓ→ㄉⁿ）。
- **上標顯示**:音對標籤用 U+207F `ⁿ` 這個真字元組出 `ㄧⁿ`，構音表、音韻歷程總覽、報告草稿三處都吃得到，不用另外做 HTML 標記。
- **注音參考表補 ㄭ**:加入空韻，跟其他韻母一樣不附辨異徵性。
- **預設音韻歷程補兩筆**:「母音鼻音化」與「複韻母簡化」，一樣標為佔位待審核。

## 這次不做的事（範圍外）

- **不做鼻音化以外的附加符號**:欄位設計成可擴充（之後要加喉塞化、去鼻音化等等走同一個欄位），但這次只實作鼻音化一種，不預先塞入用不到的選項。
- **不接進規則引擎**:附加符號這次不會變成 JsonLogic 的 fact——那是後續 `add-articulation-rule-conditions` 的範圍。
- **不做系統自動判斷音韻歷程**:沿用既有設計，鼻音化的音對要不要貼「母音鼻音化」標籤，仍然由治療師手動決定。
- **不改既有音對資料**:新欄位是選填的，舊資料不需要遷移。

## 技術方向

沿用既有路線，不引入新套件。附加符號是 `ArticulationSubstitution` 上的一個選填字串聯集型別，跟 `errorPhonemeId` 平行;判定「這筆是不是錯誤」的邏輯從「`errorPhonemeId` 有沒有值」改成「兩個欄位至少一個有值」，集中在既有的 `substitution-label.ts` 一處，避免散落在各元件。
