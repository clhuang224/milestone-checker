# 提案:add-articulation-process-tracker

## 為什麼要做

`add-therapist-rule-engine` 做出了「觀察項目勾選/填分數 → 規則觸發警示 → 報告草稿」這條主線，但構音(articulation)評估在實務上不是單純的布林/數值勾選——治療師測完一輪之後，腦中真正在做的事情是:

> 這個孩子把「拼」念成「兵」(ㄆ→ㄅ)、「兔」念成「肚」(ㄊ→ㄉ)……這些音對放在一起看，是同一種**音韻歷程(phonological process)**——不送氣化。

現有的 `FindingDefinition`（`boolean`/`number` 兩種 `kind`）裝不下「正確音→錯誤音」這種配對資料，也裝不下「多筆音對可以歸納成同一個音韻歷程」這種多對多關係。這次 change 就是把構音音對記錄跟音韻歷程歸類獨立做成一塊，補上這個資料模型。

跟治療師確認過幾個關鍵範圍問題後定案:

- 注音範圍涵蓋**聲母 + 韻母/介音 + 聲調**（共 37 個符號 + 5 個聲調），不只聲母。
- 記錄單位是**抽象音對**（正確音→錯誤音），不是逐字詞的正式測驗題本，但每筆音對可以掛**範例字詞**（例如「包→ㄆㄠ」）方便之後寫報告時舉例。
- 音韻歷程分類是**治療師手動貼標籤**，清單有預設項目、可自建——這次不做「系統依構音特徵自動判斷屬於哪個歷程」。
- 構音特徵（部位/方式/送氣）這次先只做**聲母**的參考資料，附掛在注音參考表上當顯示/輔助判斷用，不參與任何自動運算。

## 要做什麼

- **注音符號參考表**:一份依教育部標準順序排列的靜態資料（聲母 21 個、韻母/介音 16 個、聲調 5 個），聲母另外附掛部位/方式/送氣三個構音特徵欄位。
- **構音記錄表格**（單一個案）:依注音參考表順序列出所有列，每一列可以新增多筆「音對」——正確音固定是該列注音，錯誤音可留空（代表這個音正確/✓）或填一個錯誤音;每筆音對可以再掛 0~~多個音韻歷程標籤、0~~多個範例字詞。
- **音韻歷程目錄**:可擴充的分類清單（id、名稱、說明、`sourceNote`），預設一批常見項目（不送氣化、前置化、後置化……），治療師可以新增/編輯/刪除，存在 localStorage，模式比照現有 `FindingDefinition` 目錄。
- **音韻歷程總覽畫面**:把個案底下所有音對依標籤自動分組，呈現「不送氣化:ㄆ→ㄅ、ㄊ→ㄉ……」這種歸納結果，取代治療師自己手動整理。
- 沿用既有的常駐**免責警語**跟純 `localStorage` 儲存，不另外處理。

## 這次不做的事（範圍外）

- **不接進現有規則引擎**:構音音對/音韻歷程這次不會變成 JsonLogic 的 fact 去觸發 `Rule`/警示系統。治療師有提到一個很實際的後續需求——「母語是國語、在某個月齡出現某些音韻歷程，就該建議構音處置」——這確實是規則引擎的天然使用情境，但需要先補上 `Case` 的月齡/母語欄位，範圍會變大，列為明確的後續 change 候選（見下方「未來想法」），這次先把構音資料模型做穩。
- **不做系統自動判斷音韻歷程**:音韻歷程完全靠治療師手動貼標籤，系統不依構音特徵自動歸類。
- **不做正式構音測驗題本**:範例字詞是自由文字欄位，不是標準化測驗圖卡/題目庫。
- **韻母/聲調不建構音特徵**:這次構音特徵欄位只做聲母，韻母/聲調先只出現在注音參考表裡，不附特徵資料。
- 語言/言語/吞嚥以外的其他治療領域、雲端同步、多治療師協作、帳號系統——沿用 `add-therapist-rule-engine` 既有的範圍限定。

## 未來想法（不是這次的一部分，先記下來）

- 幫 `Case` 加上月齡/母語欄位，讓構音資料可以變成規則引擎的 fact（例如「母語為國語 AND 月齡 ≥ X AND 出現『後置化』歷程 → 建議構音處置」）。
- 音韻歷程總覽畫面的統計數字（例如某歷程出現次數）串進報告草稿的 `{{value:...}}` 替換機制。
- 構音特徵擴充到韻母（展唇/圓唇、舌位高低前後）——等真的有需要時再開。

## 技術方向

沿用 `add-therapist-rule-engine` 已經定案的技術路線:Angular standalone + Signals、Tailwind、單一 `StorageService` 包 localStorage（新增獨立的 key，不動既有的 findings/cases/rules 儲存）、Vitest 測試。不引入新的第三方套件——注音參考表跟音韻歷程目錄都是靜態/半靜態資料，不需要額外依賴。
