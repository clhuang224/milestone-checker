# 提案:add-articulation-rule-conditions

## 為什麼要做

拿一條真實形狀的規則去試現有的規則編輯器，發現寫不出來:

> 四歲以上，還有 ㄓㄔㄕㄖ 以外的構音錯誤，就需要做構音治療。

卡在三個地方:

1. **沒有年齡**:`Case` 只有暱稱跟備註，「四歲以上」無從判斷。
2. **構音資料進不了規則引擎**:`add-articulation-process-tracker` 當初刻意把構音記錄跟規則引擎切開（那份 spec 裡的「獨立於規則引擎」需求），所以 `evaluateCondition()` 只看得到 `CaseProfile.values` 裡的觀察項目。構音表已經知道這個孩子哪些音錯了，規則卻讀不到。
3. **條件只能比大小**:現有條件列是「欄位 × 比較運算子 × 數值」，表達不了「有**某一類**錯誤存在」「但**排除**這幾個音」這種集合判斷。

第 3 點還牽出一個更根本的問題:既有的示範項目 `articulationErrorCount`（構音錯誤音數）跟用它寫的 `> 3` 規則，方向就錯了——嚴重度不是由**錯誤的數量**決定，而是由**錯誤的形式**決定。這次一併把那個項目跟依賴它的規則條件拿掉，不留著誤導後面的人。

## 要做什麼

- **個案改記生日**:`Case` 新增選填的生日欄位，月齡由生日推導而不是直接存——存月齡的話資料會隨時間過期。
- **構音資料變成規則事實**:評估規則時，除了既有的觀察項目，另外餵進個案的年齡與構音錯誤清單。既有規則的寫法完全不受影響。
- **規則編輯器新增「適用條件」**:一種新的條件列，形式是「構音錯誤／音韻歷程」×「包含／排除」× 一組選取的項目。
- **拿掉錯誤音數**:移除 `articulationErrorCount` 示範項目，並把 `rule-speech-intelligibility` 裡依賴它的那一支條件拆掉。
- **新增一條預設規則**:把上面那條「四歲以上仍有捲舌音以外的構音錯誤」寫成預設規則，跟其他示範內容一樣標為佔位待審核。

## 這次不做的事（範圍外）

- **不做母語欄位**:`add-articulation-process-tracker` 的未來想法裡提過「母語為國語 AND ……」，但目前沒有需要它的規則，等真的要用再開。
- **不把構音統計串進報告草稿**:報告範本的 `{{value:...}}` 這次不擴充到構音事實。
- **不做既有資料遷移**:預設資料只在集合為空時才 seed，已經在瀏覽器裡跑過舊版的人，`localStorage` 裡仍留著 `articulationErrorCount` 這個項目跟舊規則，要自己刪。這是實驗專案，不另外寫遷移程式。
- **不做「只算聲母錯誤」的判定**:構音事實裡會帶著目標音的類別欄位，之後要收斂成只看聲母不用改資料結構，但這次的規則一律把聲母、韻母、母音鼻音化都算成構音錯誤。

## 對既有規格的影響

`add-articulation-process-tracker` 的「獨立於規則引擎」需求是**這次要推翻的**——當初的理由是「需要先補上 `Case` 的月齡欄位，範圍會變大」，這次正是來補那一塊。該需求改成:構音記錄會參與規則評估，但音韻歷程的**歸類**仍然只由治療師手動決定，系統不自動判斷。

## 技術方向

沿用既有路線，不引入新套件。集合判斷用 `json-logic-js` 原生就有的 `some`／`in`／`!`，不自訂 operator，這樣匯出的規則 JSON 對其他 JsonLogic 實作仍然通用。
