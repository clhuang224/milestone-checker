# 設計:add-tone-and-case-background

## 一、聲調現在是什麼，缺什麼

### 現況

聲調在資料層其實已經走完一半:

- `ZhuyinCategory` 有 `'tone'`，`ZHUYIN_INVENTORY` 有 `tone1`–`tone5` 五筆，各自有 `label`（「二聲」「輕聲」），因為一個裸的聲調符號讀不出名字。
- 構音格子表的 `sections` 是 `['medial', 'final', 'tone']` 直接跟在聲母後面，所以〈聲調〉那一區已經在畫面上，每個聲調三組「目標詞 ＋ 錯音」，存法跟聲母完全一樣（一筆 `ArticulationProbe`，`targetPhonemeId: 'tone3'`）。
- `probeErrors()` 不分類別，所以聲調的錯誤已經會進 `articulation.errors`，而且已經帶著 `targetCategory: 'tone'`（`errorFacts()` 用 `findZhuyin(id)?.category` 填的）。

**所以「聲調錯誤變成規則讀得到的事實」不需要新的儲存結構。**要補的是三個洞。

### 洞一:聲調正在被當成音韻歷程推導

`deriveProcessIds()` 的規則表裡，八條裡有七條會先問目標音的 `features` 或 `rime`，聲調兩者都沒有，所以自然落空。**只有 `vowelNasalization` 不問目標音**:

```ts
vowelNasalization: (_target, _error, heard) => heard.diacritic === 'nasalized',
```

在聲調列的錯音格插一個 ⁿ，就推導出一條「母音鼻音化」。而 `applicableProcessIds('tone3')` 是拿目標音跟整份注音表配一次推導算出來的，也會因此在聲調列的手動歷程清單裡列出「母音鼻音化」。

這條就是「聲調自成一類」在程式裡的具體落點:**目標音是聲調時，推導一律回空清單，可選歷程也一律是空的。**不是加一條「聲調」歷程，是讓聲調完全不進歷程這個維度——當初移除「聲調混淆」的理由是這個，落實也該是這個。

### 洞二:聲調列的錯音解析取錯符號

`parseHeard()` 取的是文字裡**第一個**注音符號。這在聲母／韻母列是對的（一列比一個目標音）。在聲調列不對:治療師在聲調列寫「ㄆㄠˊ」——一個很自然的寫法，因為聲調不能單獨念——解析出來的 `symbolId` 是 `p`（ㄆ），於是這筆錯誤變成 `tone3 → ㄆ`，`errorLabel()` 顯示「ˇ→ㄆ」。

修法有兩種:

| 做法                                      | 代價                                                                                                                          |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **A. 解析時依目標音的類別挑符號**（建議） | `parseHeard()` 多收一個「要哪一類」的參數，聲調列就找第一個**聲調**符號。自由文字照樣能寫，「ㄆㄠˊ」→ `tone2`                 |
| B. 聲調區的錯音格換成五選一的選單         | 輸入變得沒有歧義，但跟其他區的輸入方式不一致，而且治療師沒辦法寫下他實際聽到的東西（自由文字這個決定在 `ProbeItem` 上有註解） |

選 A，因為自由文字那個決定是刻意的:「解析不出注音符號不是錯誤，治療師寫的東西原樣留著」。A 保住這件事，B 把它拿掉。

A 有一個尾巴，就是 Q7:**一聲沒有標記符號。**「該念二聲、念成一聲」寫「ㄆㄠ」的話，聲調符號一個都找不到，這筆會變成「有錯誤但解析不出錯音」——`isErrorItem()` 只看錯音格空不空，所以它**仍然是一筆錯誤**，`targetCategory` 仍然是 `tone`，「有聲調錯誤」這種規則照樣觸發，只是「錯成哪一聲」不知道。這個行為可以接受，但要不要提供一個插入 `ˉ` 的按鈕（比照 ⁿ 那顆浮動按鈕）是 UX 的事，先問 Q7。

## 二、母語:型別怎麼切

### 張力

`CLAUDE.md` 要求聯集成員與識別字是英文、中文只在顯示層。而「其他，讓治療師自己輸入」的那一項**本質上不可能是聯集成員**——它沒有 id，內容是治療師當場打的字。

### 結論:兩個欄位，不是一個

```ts
/** 內建清單上的語言。自行輸入的語言在 `otherNativeLanguages`，不在這個聯集裡。 */
export type NativeLanguageId = 'mandarinTW' | 'taiwanese' | 'hakka'; /* ⋯ 見 Q2–Q4 */

export const NATIVE_LANGUAGE_LABELS: Record<NativeLanguageId, string> = {
  mandarinTW: '台灣華語',
  taiwanese: '台語',
  hakka: '客語',
  // 其餘待 Q3／Q4 回答後補齊
};

export interface Case {
  // ⋯既有欄位⋯
  /** 內建清單裡被勾選的。未填時 undefined，不是 []——差別見第五節。 */
  nativeLanguages?: NativeLanguageId[];
  /** 治療師自行輸入的語言，原樣保存。規則讀不到這裡。 */
  otherNativeLanguages?: string[];
}
```

**為什麼不是一個陣列。**最直接的理由是型別會失效:`(NativeLanguageId | string)[]` 在 TypeScript 裡就是 `string[]`——聯集被 `string` 吸收，編譯器從此不再檢查任何東西，`'mandrinTW'` 這種打錯的字也照樣過。這不是風格問題，是那個聯集寫了等於沒寫。

第二個理由是**規則只讀得到有 id 的那一半**。分成兩個欄位，「規則能拿什麼寫條件」就是一個型別層次的事實，不是一段要記得遵守的約定。

### 否決掉的做法

| 做法                                                              | 為什麼不                                                                                                                                                                                                                   |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 單一陣列 `({kind:'listed', id} \| {kind:'other', text})[]`        | 型別是誠實的，也保住了「治療師勾選與輸入的先後順序」——但沒有任何畫面需要那個順序，代價是每一個讀它的地方都要先分辨 kind                                                                                                    |
| 每個語言一個布林型評估項目（`FindingDefinition`）                 | 評估項目掛在**課節紀錄**上，一次回診一組值;母語不隨回診改變，掛在那裡等於每次評估都要重填。而且項目 id 是在事實物件**最上層平鋪**的，語言 id 會跟治療師自訂的項目 id 撞名，而沒有程式在擋（`docs/ARCHITECTURE.md` 第三節） |
| 每個語言一個布林事實（`case.nativeLanguage.mandarinTW: boolean`） | 條件列不用改就寫得出來，很誘人——但「沒填過母語」會被組成 `mandarinTW: false`，等於替一個什麼都沒填的個案主張「他不說華語」。要避開就得「至少填過一個才組這個物件」，那個細節很容易在下一次改動時掉，而掉了不會有人看見     |
| 直接存中文字串（`['華語','台語']`）                               | 違反 `CLAUDE.md`;而且規則檔匯出去之後，條件裡會出現中文字面值，換一個語言的介面就沒救了                                                                                                                                    |

### 自行輸入的語言進不進事實

**不進。**`case.nativeLanguages` 只裝有 id 的那些。

依 `docs/畫面說明文字準則.md` 的三問，這件事**不上畫面**:治療師在規則編輯器的母語選單裡本來就只看得到內建清單，自己打的字不在那裡——這是「做了就看得到」的自證級，不是無聲級。

但有一個真的會出事的角落:**如果治療師把一個清單上已經有的語言打進「其他」**，那條語言就悄悄變成規則讀不到的。這不該用一句說明文字解決，該用輸入方式解決——「其他」是清單的**補充**而不是替代（例如打字時就過濾掉清單上已有的項目）。形式是 UX 的事，這裡只定「不能有兩種說同一個語言的方法」。

### 內建清單裡有什麼

**已經由開發者指定的:華語（見 Q2，是否要寫成「台灣華語」）、台語、客語。**

**其餘全部待確認，我不自己填**（`CLAUDE.md`:臨床與領域內容不由模型生成）:

- 「亞洲國家常見的語言」那一段——請開發者給清單，或指定一份現成的清單（Q3）。
- 原住民族語要不要在裡面、要不要分族別（Q4）。

`tasks.md` 的 2.1 因此是**擋住的**:清單沒到位之前，`NativeLanguageId` 只能寫開發者已經講過的那三個。

這份清單不放進 `references/`。`references/` 裝的是臨床知識（辨異徵性、音韻歷程、吞嚥質地），而且每一份都有 `scripts/check-references.mjs` 在比對;母語清單是人口學欄位不是臨床判準，塞進去會讓那個資料夾的定位變模糊。開發者如果認為這份清單需要被別的治療師檢查，那就是另一回事，再說。

## 三、聽力:兩層，這次只做第一層——而且分左右耳

開發者講的是兩個東西，它們的成熟度差很多。問過「治療師自己填一個正常／異常的開關夠不夠」之後，他的回答是:

> 可以，但應該要分左右耳。

所以第一層不是一個開關，是**兩個**。

### 這次做:個案上的兩個欄位

```ts
/** 一耳的聽力狀態。沒有 'unknown' 這個成員——未評估就是那一耳的欄位不存在。 */
export type HearingStatus = 'normal' | 'abnormal';

export const HEARING_STATUS_LABELS: Record<HearingStatus, string> = {
  normal: '正常',
  abnormal: '異常',
};

/** 左右耳分開記。任一耳未填時該欄位 undefined，用到那一耳的規則就不會判斷。 */
export interface CaseHearing {
  left?: HearingStatus;
  right?: HearingStatus;
}

export interface Case {
  /** 兩耳都沒填時整個欄位不存在;只填一耳是合法狀態，不要補另一耳的預設值。 */
  hearing?: CaseHearing;
}
```

事實層投影成**兩個**布林:

```
case: { ageInMonths, correctedAgeInMonths, hearing: { leftNormal, rightNormal } }
```

`leftNormal = hearing?.left === undefined ? undefined : hearing.left === 'normal'`，右耳同理。兩個都放在 `case.` 底下（多一層 `hearing.`;`hasFact()` 走的是點路徑，深度不限，`case.hearing.leftNormal` 走得到）。

### **不做**把兩耳合起來的 `case.hearingNormal`

這是分左右耳之後最容易順手做的一件事，也是這一節真正要擋下來的東西。

合起來就得先決定合的規則:**兩耳都正常**才算正常，還是**至少一耳正常**就算？兩種都是站得住腳的臨床立場（單側聽損對聲調的影響有多大，不是我能替開發者決定的）。而不管選哪一種:

- 決定被埋在 `buildFacts()` 的一行程式碼裡;
- 規則在編輯器裡長成一列「聽力正常 ＝ 是」，**看不出來它指的是哪一種**;
- 匯出去給別的治療師之後，對方讀到的也是同一列，而他手上那個版本的合成規則可能已經不一樣。

這正是本專案在別的地方一再拒絕的形狀:`buildFacts()` 同時給實齡與矯正齡而**不自動挑一個**，理由寫在 `RuleFacts` 的註解裡——「選錯基準是無聲的錯誤，規則照樣觸發，只是結論建立在錯的年齡上」。兩耳合成一個布林是同一種錯誤。

**所以只給兩個布林，要哪一種語意由寫規則的人在條件上寫出來:**兩耳都正常就是兩列 AND，至少一耳正常就是兩列 OR。兩種都用得上既有的比較列與 AND/OR 群組，`condition-mapper.ts` 一行都不用改。

代價是**開發者那條規則的「沒有聽障」現在要寫成兩列**，而且他必須先講明是 AND 還是 OR——那就是 Q10，本案不替他選。

### 為什麼領域型別是聯集，事實是布林

因為 `ConditionRow.value` 的型別是 `boolean | number`——**條件列根本比不了字串**。要讓 `case.hearing.left == 'normal'` 寫得出來，得動 `ConditionOperator`、動 `value` 的型別、動編輯器的值輸入框、動已經匯出的規則檔會長什麼樣。為了兩個欄位做這些不值得。

反過來把領域型別也做成布林（`left?: boolean`）則會在第一次要加第三個值的時候卡住——Q5 問的「配戴助聽器」如果是一個獨立狀態，聯集加一個成員就好，布林要改資料形狀。

代價寫清楚:**投影是有損的。**聯集之後多出來的成員（例如 `'aided'`）不會自動有正確的布林值，加成員的人必須同時決定它在 `leftNormal`／`rightNormal` 這一側算什麼。型別註解要寫這句話。

### 三態不能用兩態的控制項——現在有兩組

「未填／正常／異常」是三個狀態，而一個 switch 只有兩個位置。一個預設在「正常」的開關，會讓**每一個現有個案**都靜靜地主張自己聽力正常——這正是 `docs/畫面說明文字準則.md` 第三問裡「無聲地產生錯判斷」那一級。所以 PM 這邊的要求是**兩耳都不准有預設值**，具體用什麼控制項（三段式、`select` 第一項留白、比照〈出生週數〉的 placeholder）是 UX 的事。

多出來的一項要求:**兩耳要看得出是同一件事的兩半**，而且**只填一耳是合法狀態**，畫面不能逼使用者兩耳都填才存得起來——治療師手上可能真的只有一耳的資訊。UX 決定怎麼排。

### 這次不做:純音聽力檢查評估表

那張表要記左右耳 × 氣導骨導 × 各個頻率的閾值，是一張有自己輸入方式的儀器表，也就是 `FormBody` 要多一個 `kind`。**分左右耳只解決了「哪一耳」這一個維度，其餘維度一個都沒解決**——所以這次分耳並不會讓那張表變得比較接近做得出來。依 `docs/ARCHITECTURE.md` 第二節，**這是程式碼不是資料**——治療師沒辦法自己加，每一次都得寫程式，而且照 `CLAUDE.md` 的範圍紀律，「加一張目前沒有的表」本來就是它自己的 change。

延後的理由不只是工程量，主要是**這張表上幾乎每一格都是這裡沒有的臨床內容**:測哪些頻率、dB 的範圍與級距、要不要記遮蔽、氣導骨導差多少才算傳導性、哪一組門檻算「正常」（要不要用平均？平均哪幾個頻率？切在幾 dB？）、要不要分程度。這些一個都不能猜。現在硬做出來，只會是一張填得下去但沒有任何規則讀得懂的表。

還有一個更難反悔的問題必須先問清楚，**這才是延後真正的理由**:那張表跟這兩個欄位是什麼關係？

- 表**推導**欄位 → 欄位變成推導值，不能手填（比照生日推月齡的做法:推導結果不存）。
- 兩者**並存** → 就會有一個個案的左耳欄位寫「正常」而聽檢資料寫「異常」的情況，那時要聽誰的。

現在先做欄位不會擋住任何一種;現在先猜一種關係才會。所以這次明寫:**`case.hearing.leftNormal` 與 `case.hearing.rightNormal` 的唯一來源是這兩個欄位**，將來那張表要覆寫它們、還是要換掉它們，由那個 change 決定。

## 四、條件列:那條規則寫不寫得出來

把規則拆成三支，逐支對現有的條件列詞彙:

| 支             | 現在寫得出來嗎               | 要動什麼                        |
| -------------- | ---------------------------- | ------------------------------- |
| 聽力正常       | **可以**（新增事實與欄位後） | 加兩個 `RuleField`，mapper 不動 |
| 有聲調錯誤     | 勉強，而且很脆               | 新增一種 `subject`              |
| 母語含台灣華語 | **不行**                     | 新增一種 `subject` ＋ 集合對照  |

### 聽力正常

`{"==": [{"var": "case.hearing.leftNormal"}, true]}` 就是一個普通的比較列，右耳同理。`hasFact()` 已經會走點路徑（深度不限），所以那一耳未填的個案自動不觸發，跟沒填生日一樣。要做的只有在 `CASE_FIELDS` 加兩筆:

```ts
{ id: 'case.hearing.leftNormal', label: '左耳聽力正常', kind: 'boolean' },
{ id: 'case.hearing.rightNormal', label: '右耳聽力正常', kind: 'boolean' },
```

**沒有第三筆「聽力正常」。**理由在第三節:合成的那一個布林會把「單側異常算不算正常」這個臨床判斷藏進事實層，而規則在編輯器裡長得跟原來一模一樣。要兩耳都正常就寫兩列 AND，要至少一耳就寫兩列 OR——AND/OR 群組本來就在，`condition-mapper.ts` 一行都不用改。

**只填一耳的個案**依守門的既有行為處理:用到那一耳的比較列讓整條規則不成立。所以「兩耳都正常」寫成 AND 的規則，對只填了左耳的個案不會觸發——這是對的，我們確實不知道右耳。

### 有聲調錯誤

**今天的寫法**:一列 `set` 條件，對象「構音錯誤目標音」、模式「包含」、把 `tone1`–`tone5` 五個全部勾起來。它會動，但有兩個毛病:

1. 條件編輯器的選項標籤用的是 `s.symbol`，聲調那一組就是五個沒有名字的 `ˉ ˊ ˇ ˋ ˙`（格子表那邊是特地用 `label` 才讀得出來的）。
2. 它把「聲調這一類」表達成「這五個 id」。之後只要清單有任何變動，這條規則就靜靜地少涵蓋一個，而規則長得跟原來一模一樣。

**要做的**:`ConditionSubject` 加一個 `'articulationCategory'`，比對每一筆錯誤的 `targetCategory`:

```json
{ "some": [{ "var": "articulation.errors" }, { "in": [{ "var": "targetCategory" }, ["tone"]] }] }
```

`ArticulationErrorFact.targetCategory` 已經存在，**不用改資料結構**——這正是 `add-articulation-rule-conditions` 當初寫「之後要收斂成只看聲母不用改資料結構」時預留的那一格，只是第一個用到的是聲調不是聲母。順帶地，「只算聲母錯誤」從此也寫得出來了。

### 母語含台灣華語

寫不出來，兩條路都不通:比較列只比純量、而且只吃 `boolean | number`;`set` 列的集合是寫死的 `articulation.errors`。

**要做的**:讓 `set` 列的集合**由 subject 決定**，並加一個 `'nativeLanguage'`:

```ts
const SUBJECT_COLLECTION: Record<ConditionSubject, string> = {
  articulationTarget: 'articulation.errors',
  articulationProcess: 'articulation.errors',
  articulationCategory: 'articulation.errors',
  nativeLanguage: 'case.nativeLanguages',
};
```

編出來的形狀沿用 `processIds` 已經在用的「純量陣列」寫法（`{"var": ""}` 是 json-logic-js 對當前元素的稱呼）:

```json
{ "some": [{ "var": "case.nativeLanguages" }, { "in": [{ "var": "" }, ["mandarinTW"]] }] }
```

**為什麼是加 subject 而不是新開一個列型別。**`ConditionTrialRow` 之所以自成一型，理由寫在型別註解裡:trial 的每個子句都在**收窄同一筆嘗試**，是單一項目上的合取，跟 set 列的成員判定不是同一種東西，而且共用型別會硬拖進 `mode: 'excludes'` 那個在吞嚥情境沒有意義的存在型語意。母語列**不是**這種情況——它就是一個集合上的成員判定，跟 set 列一模一樣。既然語意相同，多一個型別只會多一份要維護的來回轉換。

**但母語列只提供「包含」。**`excludes` 在集合上是存在型:`{"some": [langs, {"!": {"in": [item, ["mandarinTW"]]}}]}` 讀作「母語裡有一個不是台灣華語」，也就是「母語不只有華語」。這是一個合法的句子，但目前沒有任何規則需要它，而「排除」已經是整個編輯器最容易被誤解的控制項——為了一個沒人要的句子把誤解面積放大一倍不划算。型別上留著 `mode`，UI 上母語列不給那個選項，之後要開隨時可以開。

### 來回轉換的一個約束

`fromJsonLogic()` 目前靠 `some` 的**集合**分辨 trial 與 set，再靠**內層述詞的欄位名**分辨 target 與 process。母語列的內層述詞是 `{"in": [{"var": ""}, [...]]}`，沒有欄位名可看，跟 process 的內層長得像。所以反解時**必須先看集合再看述詞**:集合是 `case.nativeLanguages` 就是母語列，不必看述詞。實作時這是 `setRowFrom()` 的第一件事，不是最後的 fallback。

### 完整的規則長這樣

以下寫的是「**兩耳都正常**」那一種讀法，因為分耳之後「沒有聽障」有兩種讀法，而選哪一種是 Q10，不是這裡決定的:

```json
{
  "and": [
    { "some": [{ "var": "case.nativeLanguages" }, { "in": [{ "var": "" }, ["mandarinTW"]] }] },
    { "==": [{ "var": "case.hearing.leftNormal" }, true] },
    { "==": [{ "var": "case.hearing.rightNormal" }, true] },
    {
      "some": [{ "var": "articulation.errors" }, { "in": [{ "var": "targetCategory" }, ["tone"]] }]
    }
  ]
}
```

「至少一耳正常」的話，中間那兩列改成一個 `or` 群組，其餘不變。

全部是 JsonLogic 原生運算子，沒有自訂的東西，匯出去對別的實作照樣成立。

## 五、未填欄位的守門要延伸到母語列

`evaluateCondition()` 的守門**只走比較列**，`set` 與 `trial` 刻意跳過，理由在 `docs/ARCHITECTURE.md` 第三節寫得很清楚:它們跑在一個清單上，而**空清單是「沒有記錄到」這個合法答案**。

母語不是這種東西。「這個孩子沒有母語」不是一個臨床答案，那只是欄位還沒填。而 `some` 對空陣列回 `false`，於是:

- 沒填母語 → 規則不觸發
- 填了母語、但不含台灣華語 → 規則不觸發

兩者長得一模一樣，而它們的意思差很多。所以:

1. **`case.nativeLanguages` 未填時是 `undefined`，不是 `[]`。**這樣兩種狀態在事實層是分得開的。
2. **母語列要參與守門**:`comparisonFieldIdsIn()`（名字屆時要改，它不再只收比較列）對 `subject === 'nativeLanguage'` 的 set 列回 `['case.nativeLanguages']`。構音那三種 subject 維持跳過，理由不變。

這是本案唯一一處推翻既有註解裡的通則的地方，所以理由要寫進程式碼的註解:**跳過守門的理由是「空清單是合法答案」，不是「set 列一律跳過」。**母語不滿足那個前提。

### 這會讓 6.4 那個缺口多兩個入口

`docs/畫面說明文字準則.md` 6.4 記著:警示頁的「目前沒有規則被觸發」同時代表「都判斷過而沒對上」與「有規則因為缺資料而根本沒判斷」，而畫面上分不出來。本案新增三個會落進後者的欄位（母語、左耳、右耳），而且左右耳分開之後，「只填了一耳」是一個新的、很容易發生的落點。

補那個機制是它自己的 change（見 proposal 的範圍外）。這次做兩件小的:

- 個案頁那一行「沒填生日的話，用到年齡的規則不會判斷」改成講**機制**而不是講**生日**——`docs/畫面說明文字準則.md` 例二已經判定過「要講的是那個機制不是那個欄位」，本案正好是那句話預言的第二、第三、第四個欄位。
- 不新增別的畫面文字。母語與兩耳各自的行為都被這一行蓋住了。

## 六、儲存升版:會毀掉什麼

`Case` 新增的欄位（母語兩個、聽力一個巢狀物件）都是選填的，舊資料讀出來就是 `undefined`——而 `undefined` 的意思正好就是「未填」，包含「只填一耳、另一耳缺席」這種情況，這都是正確的意思。**所以只為了這些欄位不需要升版。**

會逼出升版的只有一件事:**種子只在集合是空的時候才跑。**所以

- 要讓示範個案帶上母語／聽力 → 得升 `CASES_KEY`。
- 要把那條規則當成 starter rule 出貨 → 得升 `RULES_KEY`。

而**升版是作廢不是遷移**，這是 `storage.ts` 最上面寫明的 PoC 取捨。還有一個沒寫在那裡但這次必須講的:**升版必須所有 key 一起升。**各集合分開存，只升 `CASES_KEY` 的話個案沒了，但課節紀錄、填答值、構音音對、音韻歷程覆寫、吞嚥嘗試、報告草稿全部留著，指著一堆不存在的個案 id——`removeCase()` 的連動刪除不會被升版觸發。所以既有的 key 才會全部一致停在 `:v7`。

一起升到 `:v8` 會歸零的東西，講白話:

- 所有個案，以及他們的所有課節紀錄
- 每一張表填過的值、每一格構音音對、每一筆音韻歷程覆寫、每一筆吞嚥嘗試
- 每一份報告草稿
- **治療師自己新增的評估項目、自己新增的音韻歷程、自己寫的規則**（這一項最貴，因為那是使用者自己產出的內容，不是示範資料）

規則可以匯出成檔案再匯回來，其他的不行。

**建議:預設不升版**（Q11）。那條規則的價值在於「寫得出來」，而不在於「內建好了」;治療師在編輯器裡建一次的成本，遠低於所有人資料歸零。要出貨的話，`tasks.md` 6.2 就是那一版一起做，而且它排在最後，前面 1 到 5 節都不受影響。

## 七、事實物件不變量

新增的三個事實都在 `case.` 底下:

```
{
  ...profile.values,          // 項目值仍然平鋪在最上層，一個字沒動
  case: {
    ageInMonths,
    correctedAgeInMonths,
    nativeLanguages,
    hearing: { leftNormal, rightNormal }   // 沒有合起來的 hearingNormal，見第三節
  },
  articulation: { errors: [ { targetPhonemeId, targetCategory, errorPhonemeId, diacritic, processIds } ] },
  swallowing: { trials: [ ⋯ ] }
}
```

沒有新增任何最上層的 key，所以項目 id 全域唯一且平鋪的那個不變量不受影響，已經匯出的規則檔（`{"var": "drooling"}` 那種）一條都不會壞。`case.hearing.` 多了一層巢狀，這不影響 `hasFact()`（它逐段走點路徑，深度不限），也不影響 `{"var": "case.hearing.leftNormal"}` 在 json-logic-js 裡的解析。

`articulation.errors` 裡每一筆的形狀也沒有改——`targetCategory` 本來就在。這次是讓條件列指得到它，不是加東西進去。
