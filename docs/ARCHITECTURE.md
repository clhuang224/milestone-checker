# 架構

這份文件寫的是**為什麼是現在這個形狀**。程式碼本身說得出「是什麼」，說不出「當初否決了什麼」——後者才是改動時會踩到的東西。

決策的原始脈絡在 `openspec/changes/*/proposal.md` 與 `design.md`;這裡是收斂後的結果，跟目前的程式碼對得起來。操作面看 [`user-guide.md`](user-guide.md)，開發流程看 [`CONTRIBUTING.md`](CONTRIBUTING.md)，這些決策是怎麼被做出來的看 [`development-notes.md`](development-notes.md)。

## 一、領域模型

```
Case（個案）
 └── SessionRecord（課節紀錄，一次回診）
      ├── formIds[] —— 這次掛了哪幾張表
      └── 各表的內容各自存一個集合，用 recordId 當外鍵
           ├── RecordProfile        itemList 表的填答值
           ├── ArticulationProbe    構音格子表，一個目標音一筆、固定三格
           ├── PhonologicalSummary  音韻歷程的「覆寫」，沒有這筆就等於用推導的
           ├── SwallowTrial         吞嚥嘗試（型別與計算已具備，尚未接上儲存，見第七節）
           └── ReportDraftRecord    報告草稿
```

**個案存生日，不存月齡。** 月齡存下來當天就開始過期，三個月後同一筆資料會讓「四歲以上」給出錯的答案。生日只填一次，月齡是評估時才算的推導值（`core/age.ts`）。

**課節紀錄上沒有「評估／治療」欄位。** 那個區分由掛了哪些表表達：掛 SOAP 就是治療紀錄，掛構音評估表就是評估，兩張都掛就是同一次做了兩件事——這是常見情境，這樣不用特別處理。少一個欄位，也少一組必須跟表單同步的規則。

**各表的內容不折進紀錄本身。** 構音音對跟 SOAP 段落沒有共同形狀，硬塞進一個欄位只會變成一包 `unknown`。

### 反正規化的 caseId

`ArticulationProbe` 與 `SwallowTrial` 同時帶 `caseId` 與 `recordId`。前者在正規化的角度是多餘的，但「依個案篩選」是最常見的讀取，全部改成 join 沒有好處。

代價是兩個欄位可能不一致。防線是**寫入一律走 `Storage.upsertProbe()`**，由它從 `recordId` 反查填上 `caseId`;元件不自己組這個欄位。型別註解上寫了這件事。

### 推導結果一律不存

`derivedProcessGroups(probes)` 是格子表的函數。存下來只會讓兩邊有機會不一致，所以只存**覆寫**：`PhonologicalSummary` 只在 `useDerived === false` 時有意義，而**沒有這筆記錄就代表「用推導的」**——預設值不佔任何儲存空間，也不必在建立紀錄時先寫一筆。

## 二、`body.kind`:哪些表是資料，哪些是程式碼

`AssessmentFormDefinition.body` 是一個判別聯集，決定這張表用哪個畫面、貢獻哪些事實：

| `body.kind`        | 誰做出來的        | 治療師能設定的       |
| ------------------ | ----------------- | -------------------- |
| `itemList`         | 治療師，在 app 裡 | 整份項目清單         |
| `articulationGrid` | 程式碼            | 音韻歷程目錄         |
| `swallowTrials`    | 程式碼            | 質地／標記／單位目錄 |
| `soapNote`         | 程式碼            | （待該 change 決定） |

新增一張打勾／填分數形態的表是**資料**，治療師自己就能加。新增一個有自己的輸入方式與推導邏輯的儀器是**程式碼**，每次都是。

這個切法的代價寫在型別註解裡，值得原文照抄：**不要把 `itemList` 長到足以表達構音格子表——那是這個設計失敗的方式。** 通用表單建構器一旦能表達六欄部位排列與注音解析，就同時失去了兩邊的好處：治療師編不動它，程式碼也不能再假設格子表的形狀。

目前只有 `articulationGrid` 真的接上（`STARTER_FORMS` 只有一張）。

## 三、規則引擎

### 為什麼是 JsonLogic

`Rule.condition` 直接存 JsonLogic JSON，用 `json-logic-js` 評估。理由是**規則要能匯出成檔案、在治療師之間傳**——純 JSON、跟框架無關，換平台也讀得懂。所以集合判斷只用原生的 `some`／`in`／`!`，**不自訂 operator**;自訂了，匯出的 JSON 對別的 JsonLogic 實作就沒有意義了。

編輯器 UI 是自己刻的（條件列 ＋ AND/OR 群組）。`core/rule-engine/condition-mapper.ts` 負責內部模型 ⇄ JsonLogic 互轉，兩個方向都要能走：讀回來時 `fromJsonLogic()` 要認得出自己寫出去的形狀。

### 事實物件

`buildFacts()` 組出來的形狀：

```
{
  ...profile.values,          // 項目值平鋪在最上層
  case: {
    ageInMonths, correctedAgeInMonths,
    nativeLanguages,          // 只放內建清單的 id，沒問過時整個 key 不存在
    hearing: { leftNormal, rightNormal, betterEarNormal }
  },
  articulation: { errors: [ { targetPhonemeId, targetCategory, errorPhonemeId, diacritic, processIds } ] },
  swallowing: { trials: [ { consistencyId, volumeCc, successPercent } ] }
}
```

**項目 id 維持全域唯一、且在事實物件最上層平鋪，是這個專案最該保護的不變量。** 已儲存與已匯出的規則檔寫的是 `{"var": "drooling"}`。如果項目改成表限定的路徑（`forms.swallowing.drooling`），所有既有規則、以及治療師之間分享出去的規則檔全部失效，而 `condition-mapper` 沒有遷移路徑。項目屬於哪張表，是編輯與顯示層的事，不是事實層的事。

代價很清楚：**兩張不同的表不能有同名的項目 id**，這個約束沒有程式在擋。

新事實放在 `case.`、`articulation.` 與 `swallowing.` 三個命名空間底下，跟項目 id 撞不到名。

年齡一律用**該筆課節紀錄的日期**算，不是今天——報告兩週後才寫，不能把個案推過一條當天還沒跨過的門檻。實齡與矯正齡兩個都放進事實裡，**不自動幫使用者選**：選錯基準是無聲的錯誤，規則照樣觸發，只是結論建立在錯的年齡上。

音韻歷程取的是**現行的歸納**（`effectiveProcessGroups()`），不是推導結果本身。治療師覆寫過的分組，規則就該按他寫的觸發。

#### 母語：沒問過與答了「都不是」要分得開

`case.nativeLanguages` 有三種狀態，而且三種都有意義：

| 個案上的資料                   | 事實                    | 規則怎麼看       |
| ------------------------------ | ----------------------- | ---------------- |
| 什麼都沒勾、也沒在「其他」輸入 | key 不存在              | 沒問過，不判斷   |
| 只在「其他」輸入了清單外的語言 | `[]`                    | 答過了，照常判斷 |
| 勾了清單上的語言               | 勾選的 id，依清單順序排 | 照常判斷         |

**事實裡只有 id。** 治療師自行輸入的語言存在 `Case.otherNativeLanguages`，原樣保存，但不進事實：規則只能針對一份已知的清單寫，一段自由文字沒有東西可以比對。兩個欄位分開存而不是合成 `(NativeLanguageId | string)[]`，因為那個聯集會塌成 `string[]`，型別就不再檢查任何東西。為了不讓同一個語言被記成兩種形式（一次是規則讀得到的 id，一次是讀不到的文字），「其他」裡輸入清單上已有的語言會被擋下來，請治療師直接勾選。

`buildFacts()` 用展開而不是賦值放進這個 key，就是為了讓「沒問過」在事實層**連 key 都沒有**——下面的守門要靠這一點分辨。

#### 聽力：兩耳各一個事實，再加一個合成的優耳

個案上存的是 `Case.hearing.{left, right}`，每一耳是 `'normal' | 'abnormal' | 'aided'` 之一或不存在；沒有 `'unknown'` 這個成員，沒評估過的耳朵就是欄位不存在。`'aided'` 同時涵蓋助聽器與人工電子耳，因為目前沒有任何規則需要分辨，分開反而會帶出一個要臨床回答的問題。

事實層把它投影成三個布林：

- **`leftNormal`／`rightNormal`**——那一耳沒填就是 `undefined`，否則只有 `'normal'` 是 `true`。**配戴輔具投影成 `false`。**
- **`betterEarNormal`**——任一耳正常就是 `true`；兩耳都填了而且都不是正常（異常與配戴輔具任意搭配）才是 `false`；其餘一律 `undefined`。

「一耳非正常、另一耳未填」是 `undefined` 而不是 `false`，這一格最容易寫錯：優耳是兩耳裡**比較好**的那一耳，沒填的那一耳可能才是優耳，填一半就下結論等於替它假設也不正常。`undefined` 交給下面的守門，所以不管規則寫的是「是」還是「否」都不會觸發。

配戴輔具在優耳判定裡算非正常，是開發者的裁定。單耳事實跟著算 `false` 則是推論出來的：若單耳把配戴輔具算成正常，同一個個案會同時成立「左耳聽力正常 ＝ 是」與「整體聽力正常 ＝ 否」，誰都解釋不了。

這個投影是**有損的**：`HearingStatus` 多一個成員，就得在 `earNormal()` 與 `betterEarNormal()` 兩處都決定它算什麼，只改一處會靜靜地讓兩種事實對不上。型別註解上寫了這件事。

**這一項推翻了原本的決定。** 這個 change 一開始明寫**不做**合成的整體聽力事實，理由是：把兩耳合成一個值，就得決定單側異常算不算正常，那是臨床判斷，而它會藏在 `buildFacts()` 的一行裡，規則在編輯器裡、在匯出檔裡都看不出指的是哪一種讀法——跟實齡／矯正齡兩個都給、不自動挑一個是同一種顧慮。後來這個理由不再成立，原因有二：

1. **判斷不再是程式這邊做的。** 開發者定案整體看優耳，依據是台灣身心障礙鑑定採優耳認定。合成的那一行不再是一個藏起來的猜測，而是一個有名字、有出處的決定。
2. **「看不出指的是哪一種」修在名字上。** 欄位標籤是「整體聽力正常（優耳）」，事實路徑是 `case.hearing.betterEarNormal`——後者會跟著匯出的 JSON 走，收到檔案的人沒有這個 app 也讀得出是優耳。原本反對的其實是一個**沒有名字**的合成。

實齡與矯正齡的類比也在這裡斷掉：那兩個年齡沒有任何外部慣例指定該用哪一個；優耳有。左右耳兩個事實照樣保留，合成是加上去的，不是取代——要寫「兩耳都正常」的人照樣寫得出兩列 AND。

標籤裡的「（優耳）」只說出依據，說不出配戴輔具算非正常、也說不出只填一耳時可能不判斷，所以條件編輯器在選到這個欄位時，底下多一行常駐的說明（`condition-editor.ts` 的 `FIELD_HINTS`），其他欄位沒有這一行。載體刻意是常駐的文字而不是 tooltip：滑過去才看得到的字，掃視時與觸控裝置上都不存在，匯出成檔案之後更不存在。（設計階段提過的 tooltip 目前沒有做，畫面上只有標籤與這一行。）

### 未填欄位的守門

`evaluateCondition()` 先用 `fromJsonLogic()` 把條件讀回內部模型（讀不回來的條件一律不成立），再由 `guardedCondition()` **逐個節點**重新編譯：用到沒有值的欄位的那一列，換成一個永遠為假的子句（`{"==": [1, 0]}`），其餘照常，`and`／`or` 照常組合，最後才交給 `jsonLogic.apply()`。「有沒有值」由 `hasFact()` 沿著點路徑逐段走，key 不存在、值是 `undefined` 或 `null` 都算沒有值。

擋的是這個 bug:json-logic-js 對缺少的 `var` 回 `null`，而 JS 裡 `null < 40` 是 `true`。沒有這道守門，`oralMotorScore < 40` 這種門檻規則會對**根本沒填過這個分數**的個案觸發。同一道守門也讓沒填生日的個案不會誤觸年齡規則——不知道年齡時不該亂給建議。

**為什麼是逐個節點，而不是先蒐集整條規則用到的欄位、缺一個就整條不判斷。** 早先的做法是後者，它錯在兩個方向：一個「四歲以上 或 流口水」的 `or`，會因為沒填生日而對一個流口水的個案整條不成立，即使另一個分支自己就足以決定；反過來，若讓它照樣算，沒填的分數又會因為 `null < 40` 而讓 `or` 觸發。把單一子句換成假，兩個方向都對了，`and`／`or` 也不需要各自的判定規則。實際效果是：**沒有值的那一列一律不成立**——在 `and` 裡等於整條不成立，在 `or` 裡則交給其他分支決定。

**適用條件列要不要守門，取決於一個前提：空清單或沒有清單，是不是一個合法的答案。**

- **構音錯誤（`set` 列的三種構音對象）與吞嚥嘗試（`trial` 列）——是。** 沒記錄到錯誤就是沒有錯誤，所以這些列一律照常判斷，`some` 對空陣列回 `false`，語意正確。`trial` 列自己的缺值在編譯出來的述詞裡守（見下面 `!= null` 那一段），因為這道守門看不進 `some` 裡面。
- **母語——不是。** 「這個孩子沒有母語」不是一個臨床答案，只是還沒問。若沿用跳過，「沒填母語」與「填了但不含這個語言」都會靜靜地不觸發，兩者長得一樣、意思差很多。所以 `subject === 'nativeLanguage'` 的 `set` 列要檢查 `case.nativeLanguages` 有沒有值：沒問過的個案上，這一列不論「包含」或「排除」都換成假；答過的個案，即使是 `[]`，照常判斷。

這是唯一一處 `set` 列不跳過守門的地方。**跳過的理由是「空清單是合法答案」，不是「`set` 列一律跳過」**——之後新增的清單型對象，要先問它滿不滿足這個前提。

老實說，母語這一支**今天不改變任何結果**：json-logic-js 的 `some` 遇到不存在的清單本來就回 `false`。留著它是為了把「沒問過就不判斷」這個意思寫明，而不是借用某一個函式庫對 `null` 的處理方式；換一個 JsonLogic 實作，或者之後加了全稱否定的寫法，這一支才會真的擋下東西。`guardedCondition()` 的註解寫了同一件事。

（`openspec/changes/add-case-background-conditions/design.md` 與 `add-score-band-conditions` 的文件提到的 `comparisonFieldIdsIn()` 已經不存在，守門就是上面描述的 `guardedCondition()`。）

### 適用條件列

兩種，形狀不同所以是兩個型別：

- **`set`（構音、母語）**——「有／沒有這一組音的錯誤」，或「母語有沒有這幾個語言」。`mode: 'excludes'` 是**存在型，不是全稱型**：「排除 ㄓㄔㄕㄖ」的意思是**扣掉那幾個音之後仍然有別的錯誤**，不是「完全沒有 ㄓㄔㄕㄖ 的錯誤」。這是整個編輯器最容易誤解的一點，所以 UI 旁邊直接寫白話語意，不只放「包含／排除」兩個詞。
- **`trial`（吞嚥）**——「清水 3cc 以下會嗆咳」。每個子句都在**收窄同一筆嘗試**，是單一項目上的合取；set 列則是清單上的成員判定。共用型別還會硬拖進 `mode: 'excludes'`，那個存在型語意在這裡沒有意義。

`set` 列的 `subject` 決定它跑哪一個清單、比對什麼：

| `subject`              | 跑的清單               | 比對的東西                                                 |
| ---------------------- | ---------------------- | ---------------------------------------------------------- |
| `articulationTarget`   | `articulation.errors`  | 每筆錯誤的 `targetPhonemeId`                               |
| `articulationCategory` | `articulation.errors`  | 每筆錯誤的 `targetCategory`（聲母／介音／韻母／聲調）      |
| `articulationProcess`  | `articulation.errors`  | 每筆錯誤的 `processIds`（本身是清單，所以再套一層 `some`） |
| `nativeLanguage`       | `case.nativeLanguages` | 清單裡的每個 id 本身（`{"var": ""}`）                      |

**`articulationCategory`** 存的是整個類別而不是一串符號，所以注音表將來變動，這一列照樣涵蓋該類別的每一個音。它讓「只看聲母」或「有聲調以外的構音錯誤」寫得出來——後者是「類別 排除 聲調」，存在型的排除在這裡剛好讀成要的意思。系統本身仍然不對聲調做任何判斷；這個對象給的是治療師寫規則的能力，不是系統的判斷。

**`nativeLanguage`** 在編輯器裡只提供「包含」。存在型的「排除 華語」對一個華語＋台灣台語的雙語孩子**成立**（他有一個不是華語的母語），而那是台灣最常見的情況，幾乎不會是寫規則的人想要的；真正的「完全不含」是全稱否定，是另一種形狀，目前沒有做。從檔案匯入的規則若已經帶著「排除」，編輯器會照實顯示它，換成「包含」之後這個選項就消失。

**`fromJsonLogic()` 讀 `set` 列時，先看清單、再看述詞。** 母語列的述詞是 `{"in": [{"var": ""}, [...]]}`，不指名任何欄位，跟音韻歷程列最內層那一段長得一模一樣——只看述詞分不出兩者，看 `some` 的第一個參數是 `articulation.errors` 還是 `case.nativeLanguages` 才分得出來。吞嚥列也一樣是靠清單（`swallowing.trials`）認出來的。

兩種空列的預設**方向相反**，這是刻意的：空的 `set` 列什麼都不匹配（還沒選音）;`trial` 列的 `consistencyIds` 空代表**不限質地**，該子句直接省略。UI 有寫出來。另外 `and: []` 在 JsonLogic 裡是 truthy，會匹配到每一筆嘗試，所以完全空的 trial 列會補上 `{"==": [1, 0]}` 讓它什麼都不匹配。

### `!= null` 那道守門為什麼是承重牆

`trialClauses()` 在每個 volume 比較前面多送一句 `{"!=": [{"var": "volumeCc"}, null]}`。這不是防禦性的贅句：

`volumeCc` 是選填的，因為**出院個案的那筆嘗試量不出來**——「以湯匙進食醫院果泥不嗆咳」是一筆真實的嘗試，沒有 cc 數。而 json-logic-js 把缺少的 `var` 解析成 `null`，`null <= 3` 在 JS 裡是 `true`。少了這道守門，那筆沒有量的果泥嘗試會滿足「3cc 以下」，於是**在最不需要警示的那個個案身上**觸發一則「還在治療中」的警示。

第三節的未填欄位守門蓋不到這裡：它只檢查比較列與母語列的欄位有沒有值，看不進 `some` 的內部。所以守門必須寫在編譯出來的述詞裡面。

讀回來時 `trialRowFrom()` 會忽略這一句——它不帶任何使用者意圖，是編譯產物。

## 四、構音推導

三個檔案，責任分開：

**`parse-heard.ts`** —— 錯音欄是自由文字，治療師照聽到的寫（「ㄆㄠ」）。只取**第一個**注音符號：格子表一列記一個目標音，那才是被比較的對象。上標 `ⁿ` 只有**緊接在第一個符號後面**才算在它頭上——「ㄉㄭⁿ」裡那個 ⁿ 屬於 ㄭ，算給 ㄉ 就是無中生有一個治療師沒記錄的錯誤。**解析不出注音符號不是錯誤**：治療師寫的東西原樣留著，只是沒東西可推導。

**`derive-processes.ts`** —— 拿目標音與錯誤音的辨異徵性比對，回傳所有命中的歷程 id。**一筆錯誤可以中多條**（ㄙ→ㄉ 同時改了部位與方式），沒有任何東西在挑贏家——挑了就是在替治療師做臨床判斷。

`applicableProcessIds()`（手動挑選時要列出哪些歷程）不另外維護一張對照表：直接拿目標音去跟整份注音表配對跑一次推導。「ㄅ 不該出現塞音化」於是從同一套規則掉出來，而不是靠兩份東西維持同步。

**兩條刻意推導不出來的歷程：**

- **前置化／後置化不推導。** 查過的每一份文獻都是列舉「目標音集合 → 錯誤音集合」的查找表，沒有一份先定義部位座標再算差值；前置化的目標音只有六個、後置化十一個，兩者不對稱，本來就不是同一條軸的正負兩向。鄭靜宜（2011）明確警告放寬範圍會膨脹發生率。所以**程式碼裡沒有 `PLACE_ORDER` 這個常數**——部位排序只用在格子表的欄位排列。這兩條維持手動貼標籤。（早期的 `add-articulation-grid/design.md` 曾寫要用索引比大小，後來被 `references/taiwan-mandarin-consonants.md` 推翻；那份 design 沒有回頭改。）
- **介音省略推導不出來。** 它是音節層次的現象（ㄧㄠ→ㄠ），而目前的記錄單位是單一符號對單一符號，這裡根本沒有東西可以偵測它。要能推導，記錄單位得改成整個音節。

其餘未決的臨床問題（聲調、邊音化、擦音化的例子）記在 `references/open-questions.md`，不是忘了，是知道還沒決定。

## 五、儲存

`core/storage/storage.ts` 是**唯一碰 `localStorage` 的地方**。對外是 signals（`computed` 讀、`upsert*` 寫），元件不自己維護一份本地狀態，所以不會有畫面跟儲存不同步的情況。

key 帶命名空間與版號，目前一律 `:v8`。分開存而不是一包大 JSON，避免每次寫入都重新序列化全部資料。

**升版是作廢，不是遷移。** 這是 PoC 階段的取捨，寫在檔案最上面。理由是 seed 只在集合為空時才跑，所以不升版的話，starter 內容的改動對已經開過 app 的人完全看不見。**代價是每次升版所有人的資料歸零**——實驗專案接受這個代價，真的要給人用的話這裡得換成遷移。

**連動刪除**（不留孤兒資料）:

- `removeCase()` → 該個案的課節紀錄、profile、構音音對、吞嚥嘗試、音韻歷程覆寫、報告草稿
- `removeRecord()` → 該筆紀錄的 profile、音對、嘗試、覆寫、報告草稿
- `removeArticulationProcess()` → 把該歷程從所有**手動**分組裡拔掉；推導的分組不用清，它們是重算出來的，自然就不再產出那條
- `setRecordForms()` → 拿掉一張表時，丟掉那張表在這筆紀錄上的內容（構音與吞嚥;`itemList` 與 `soapNote` 尚未處理，見 `docs/todo.md`）

**升版不跑連動刪除。** key 的版號一跳，舊資料是整批被無視而不是被清理，所以版號必須**所有 key 一起跳**——只跳 `CASES_KEY` 會讓課節紀錄、音對、profile、草稿全部變成讀不到主體的孤兒。

## 六、`references/` 與同步檢查

臨床內容（辨異徵性、音韻歷程、吞嚥質地）**同一份資料放在兩個地方**：

- `references/*.md` —— 給人看的。可以直接貼給另一位治療師請他挑錯，也可以在 git 裡看出哪一格什麼時候被改成什麼。
- `src/app/data/*.ts` —— 程式讀的。

這是刻意的重複，因為兩邊的讀者不同：治療師不會為了查「系統憑什麼判斷 ㄉ→ㄍ 是後置化」去讀 `.ts`。重複的代價是會漂移，而**漂移掉的文件比沒有文件更糟**——查到的人會相信它。

`scripts/check-references.mjs` 就是為此存在：把兩邊都當**純文字**讀（markdown 抓表格列，`.ts` 用 regex 抓欄位），逐項比對 id、符號與各欄的值，不一致就 exit 1。當純文字讀是為了不依賴 Angular build，所以 pre-commit hook 跑得起來。

檢查的**範圍有限，知道就好**：聲母比全部四個辨異徵性欄；韻母只比 id 與符號（它們的徵性在巢狀物件裡，regex 讀得很差），值由 `src/app/data/articulation-content.spec.ts` 的單元測試斷言。這樣切是因為 script 要抓的是**實際會發生的錯**——在其中一邊加了或改了一個符號。

改的時候**先改 `references/`**，再同步 `src/app/data/`。只改 `.ts` 會讓文件過期，下一個查的人查到的就是錯的。

## 七、版面是臨床語意的一部分

構音格子表的六欄不是排版選擇：

```
ㄅ ㄗ ㄉ ㄓ ㄐ ㄍ
ㄆ ㄘ ㄊ ㄔ ㄑ ㄎ
ㄇ ㄙ ㄋ ㄕ ㄒ ㄏ
ㄈ    ㄌ ㄖ
```

**由左至右是構音部位由前到後**：雙唇／唇齒 → 舌尖前 → 齒槽 → 舌尖後 → 舌面 → 舌根。順序由治療師給定，記在 `references/taiwan-mandarin-consonants.md`。

這**不是**注音的傳統背誦順序（ㄅㄆㄇㄈ／ㄉㄊㄋㄌ／ㄍㄎㄏ⋯⋯）——那個順序把舌根排在第三欄然後又往前跑，本來就不是部位排列。ㄈ 跟 ㄅㄆㄇ 同欄雖然它是唇齒，因為拆開就要第七欄，而第七欄塞不進畫面。

由左到右讀出來的東西就是那個排序；讓它 wrap，最右邊的舌根那一欄掉到下一行，這個資訊就沒了。所以：

- app shell 是 `max-w-6xl`——六欄剛好塞得下。
- 格子表外面包 `overflow-x-auto`，而不是 `flex-wrap`。視窗真的太窄時**寧可橫向捲動也不重排**。
- 聲母格子裡的辨異徵性放在 `title` tooltip，不寫在符號底下：寫出來格子就寬到六欄塞不進 `max-w-6xl`。韻母／介音／聲調那幾區沒有部位排列，可以 wrap、也有空間直接把名稱寫出來（一個光禿禿的聲調符號沒有名稱是讀不出來的）。
- 課節紀錄頁的頁首與頁籤列**只能佔垂直空間，不能有側欄**——側欄一加，格子表就沒有那個寬度了。

一句話：改這一區的版面之前，先確認改完之後由左至右還讀得出部位順序。

### 為什麼不用 UI 元件框架

評估過，結論是**不採用**，理由不是品味而是盤點:畫面上需要的十六種元件裡，十二種已經存在而且比
任何框架的預設值更貼這個 app——`.btn-danger` 平時去飽和、hover 才填滿，`.chip` 表達的是「這個值
被選了」而不是「這是一顆按鈕」，`.probe-box` 用 `:not(:placeholder-shown)` 讓填過的格子變白。兩種
（六欄格子表、巢狀 AND/OR 條件樹）任何函式庫都做不出來。真正的缺口只有行內確認與 tooltip 兩種，
而且是行為不是樣式，Angular CDK 的 overlay 就夠。

還有一個硬理由:上面那 34px 的餘裕。任何對輸入框多加幾個 pixel 水平內距的元件庫都會把第六欄擠掉。
