# 畫面說明文字準則

這份文件回答一個問題：**畫面上應該解釋多少？**

起因是構音格子表上那一行「同一欄是同一個構音部位，由左至右部位由前到後」被拿掉，開發者同時表示畫面上不需要解釋太多。這個方向如果照字面執行，會連「排除」那一行白話重述、「重新產生會蓋掉」那一行橘字一起砍掉，那是災難。所以要把界線畫出來，而不是留一句語氣。

以下內容由 PM 與 UX 共同定案。兩邊立場不一致的地方，下面會寫出兩邊怎麼說、以及這裡採哪一邊。

---

## 一、規則

### 1.1 一句話版本

> **畫面上的說明文字，只為了補「這個工具自己的行為」而存在，不為了補臨床知識而存在。**

這個工具的使用者是語言治療師。構音部位由前到後怎麼排、送氣不送氣怎麼分、哪些歷程屬於替代型，這些是他的專業，不是他來這裡學的東西。畫面上教他這些，是在浪費他的時間，同時暗示我們覺得他不會。

但他**不可能知道**這個工具內部怎麼運作。沒填生日會讓整條規則直接不觸發，「排除」是存在型不是全稱型，錯音格留白就被算成構音正確——這些是我們自己做的實作決定，猜不到，而且猜錯了會安靜地產生錯的結果。這些一定要講。

### 1.2 三問

一句話不夠拿來驗收，所以拆成三個問題。任何一句要放上畫面的文字，依序問：

**問一：這句話補的是臨床知識，還是工具行為？**

補臨床知識的，一律不上畫面。這是被刪掉的欄位順序說明落敗的地方——它在第一問就出局了，不需要進到第二問。

灰色地帶的判準是：**這句話換一個工具、換一張紙本評估表，還成不成立？**成立的話它是領域知識，不是我們的事。「構音部位由前到後」在任何一張構音評估表上都成立，所以不是我們的事。「錯音格留白會被算成構音正確」只在這個工具裡成立，所以是我們的事。

**問二：不講的話，使用者會不會自己發現？**

分成三級，處理方式不同：

| 級別       | 定義                                               | 處理                             |
| ---------- | -------------------------------------------------- | -------------------------------- |
| **自證的** | 做了就看得到結果，畫面自己會回答                   | 不上畫面                         |
| **可疑的** | 做了看得到結果，但那個結果看起來像故障             | 上畫面，只陳述事實，不辯護設計   |
| **無聲的** | 做了看不到結果，而且畫面長得跟「一切正常」一模一樣 | **一定要上畫面**，這是準則的核心 |

無聲那一級是這份準則真正存在的理由。個案一覽的〈重點〉欄是空的、警示頁寫著「目前沒有規則被觸發」——這既可能是「規則都判斷過而沒對上」，也可能是「有規則因為缺資料而根本沒判斷」。兩者在畫面上目前長得完全一樣。這種東西不講，工具就是在騙人。

**問三：猜錯的後果是什麼？**

- **沒有後果** → 不上畫面，不管它多不直覺。
- **產生錯的資料或錯的判斷，而且看不出來** → 上畫面，而且要在錯誤還來得及避免的時候上。
- **不可逆的破壞**（刪除、覆蓋、取代） → 上畫面，而且要**擋路**——`confirm` 這種必須主動按過去的形式，不是旁邊一行小字。

第三問是第一問的救援機制：某件事就算是臨床知識，只要工具處理它的方式會安靜地產生錯結果，還是要講。反過來也成立——某件事就算再怎麼不像常識，只要猜錯了什麼事都不會發生，就不上畫面。構音格子的欄位順序落在後者：它不進規則、不影響推導、看錯了不會算錯任何東西。

### 1.3 份量的上限

**畫面文字的目標是「不被騙」，不是「學得會」。**

上限是一句話，說工具會做什麼。超過一句話，或者開始寫「為什麼這樣設計」，就代表這段內容該搬到《使用說明》。

具體來說，這些**不進畫面**：

- 為設計辯護的理由（「一個你沒有真的寫下來的歸類，比一個看得出來是空的框更糟」）
- 完整的規格與例外表（錯音只比對第一個符號、非注音字不算錯誤、聲調符號不影響比對）
- 教學用的舉例（「例如 ㄅ 本身是塞音，就不會出現塞音化」）
- 臨床依據與出處

### 1.4 不受這條準則管轄的東西

刪文字的時候很容易連這些一起刪，先圈出來：

- **免責聲明**（畫面最上方那條橘帶）。它是常駐聲明不是說明文字，`CLAUDE.md` 明文要求它保持可見。任何精簡都不准動它。
- **資料**。構音符號 tooltip 顯示的辨異徵性、年齡與矯正齡、警示數量——它們回答「這個東西是什麼」，來源是 `references/`，刪掉等於刪功能。辨異徵性 tooltip 特別容易被誤認成說明文字，它不是。
- **介面標籤**。label、placeholder、按鈕名、頁籤名、選項名。它們受命名準則管，不受份量準則管。placeholder 寫「錯音」是命名，寫「錯音照聽到的寫」就變成說明文字了，那時才進這條準則。
- **一句話的頁面定位**（〈評估表一覽〉底下那句「設定每張表要填什麼、以及什麼情況要示警」）。它是標題的延伸，回答「我到了哪裡」，屬於資訊架構不是說明。上限同樣是一句。

## 二、職責分工

PM 與 UX 在這件事上都有立場，界線是**「要不要講」跟「怎麼講」**。

### PM 決定

- **這個行為算不算不可預測。** 也就是三問的答案。這是產品判斷：使用者的心智模型長什麼樣、偏離的代價多大。
- **講的份量上限。** 一句、一段、還是不講。
- **哪些內容不進畫面而進《使用說明》**，以及《使用說明》在產品裡是不是一等公民（見第四節）。
- **揭露是功能的一部分。** 新功能如果帶了一個無聲行為，那個揭露就是 `tasks.md` 上跟功能同一項的東西，不是之後補的文案工作。這一條是 PM 的，因為它是範圍問題。

PM **不決定**：形式、位置、時機、以及「這裡塞不塞得下」。

### UX 決定

- **形式。** inline 一行小字、tooltip、placeholder、空狀態、`confirm`、disabled 按鈕加 `title`——或者根本不用文字，改用介面結構把話講完。
- **位置。** 原則是**貼著後果現形的地方，不是貼著設定的地方**。這一條在下面〈沒填生日〉那個例子裡是決定性的。
- **時機。** 常駐，還是只在該狀態出現。能不常駐就不常駐——只在出事的時候出現的字，不佔平時的注意力。
- **能不能不用文字。** 這是 UX 的第一選擇，不是備案。

UX **不決定**「要不要講」。版面塞不下不是不講的理由——塞不下要退回給 PM，由 PM 決定是降級（挪去《使用說明》並改用別的形式提示）還是改設計。構音格子表的六欄硬約束就是這個流程的實例：那裡真的塞不下常駐文字，所以辨異徵性走 tooltip，而不是砍掉。

### 兩邊真的會吵的地方

**衝突一：UX 立場書寫著「語意容易被誤解的地方，在旁邊用一句白話重述」，這是無條件的。PM 的立場是每一句畫面文字都要為它佔的空間辯護。**

在「排除」上兩邊結論相同，不構成衝突。真正衝突的是「只列出對該音可能發生的歷程——例如 ㄅ 本身是塞音，就不會出現塞音化」這種**前半是揭露、後半是教學**的句子。UX 想留整句因為讀起來才懂；PM 要砍例子因為那是教學。

**這裡 PM 贏一半：留前半，砍破折號後面的例子。**理由是前半揭露的是「清單為什麼比你預期的短」——這是可疑級，不講會讓人以為工具漏了東西；後半的例子則是拿治療師本來就知道的事來解釋，是第一問的出局項。

**衝突二：UX 立場書寫著「『沒有觸發』不等於『沒有問題』，畫面上要讓人看得出這個差別」。PM 認為那句話是臨床提醒，屬於免責聲明的範圍，而免責聲明已經釘在最上面，在警示頁再寫一次是重複。**

**這裡 PM 贏，但 UX 贏了更重要的一半。**警示頁不該再寫一次免責聲明——那是拿倫理話術填空白。但 UX 指出的差別確實存在，而且是工具行為不是臨床提醒：**「規則都判斷過而沒對上」跟「有規則因為欄位沒資料而根本沒判斷」是兩件事，目前畫面上完全分不出來。**前者是「沒有問題」的合理證據，後者不是。這是三問裡的無聲級，一定要講。

換句話說，UX 的直覺是對的，但寫在立場書裡的理由（臨床提醒）是錯的理由。用對的理由（工具行為揭露）重寫之後，它是全案優先度最高的一個缺口。

## 三、逐例判定

### 例一：「排除」是存在型，不是全稱型

現況：選了模式之後，底下顯示「扣掉勾選的項目後，個案身上仍然有其他構音錯誤時成立」。

- 問一：**工具行為。**「排除」不是臨床術語，是我們自己取的 UI 詞彙，而且我們給它的意思跟這個詞的日常意思相反——日常的「排除 ㄓㄔㄕㄖ」聽起來像「沒有 ㄓㄔㄕㄖ 的錯誤」，實際上是「扣掉它們之後還有別的錯」。換一個工具不成立。
- 問二：**無聲。**規則寫錯了照樣存得下去、照樣跑，只是安靜地在不對的個案身上觸發或不觸發。
- 問三：產生錯的判斷，而且看不出來。

**判定：保留，一字不改，位置也不動。**它跟著模式下拉選單即時變，這正是「貼著後果現形的地方」。

這個例子順帶證明了「畫面上不需要解釋太多」不能照字面執行——同一句指示如果殺得掉欄位順序那一行，也殺得掉這一行，但這一行絕對不能死。

### 例二：個案沒填生日，所有年齡規則靜靜地不觸發

現況：個案頁的〈基本資料〉展開後，會出現一行灰字「沒填生日的話，用到年齡的規則不會判斷」。

- 問一：**工具行為。**這是 `evaluateCondition()` 裡的一個實作決定——缺值不當成 0 去比大小，而是整條規則判定不成立。完全猜不到。
- 問二：**無聲，而且是最壞的一種。**警示頁會寫「目前沒有規則被觸發」，跟「規則都判斷過而沒對上」長得一模一樣。
- 問三：治療師可能因此認為個案沒有觸及任何年齡門檻。

**判定：文字保留，但位置錯了，而且揭露的範圍太窄。**

位置錯在哪：〈基本資料〉**預設是收起來的**。使用者不展開就看不到那一行，而最可能沒填生日的人，正是那個沒去展開基本資料的人。這行字目前掛在「最不會被看到的地方」。

範圍太窄在哪：缺生日只是這個機制的一個特例。**任何**沒填的比較欄位都會讓整條規則不成立；切到〈自己選〉但還沒點任何歷程，也會讓讀歷程的規則看到空清單。生日只是目前唯一會發生的情況，因為目前只有年齡欄位。

這是 PM／UX 分工的教科書例子：PM 說「這件事一定要講，而且要講的是那個機制不是那個欄位」，UX 說「那就不能只掛在一個預設收起的摺疊區裡，要掛在後果現形的地方」——也就是**警示頁**。

**要補的東西：**警示頁在沒有任何規則觸發時，要分得出「都判斷過了」跟「有規則沒判斷」，並且在後者列出是缺了什麼。個案頁那一行留著沒關係，它在展開時是對的提示。

### 例三：〈自己選〉切過去是空白的

現況：切到〈自己選〉之後，上方生效清單顯示「還沒有指定任何音韻歷程，從下面挑。」

- 問一：工具行為（而且是一個刻意的設計決定）。
- 問二：**可疑級。**使用者可能讀成「推導結果不見了 / 壞了」，然後切回〈使用推導結果〉，等於這個功能白做。
- 問三：不至於產生錯資料，但會讓人不信任工具。

**判定：已經處理對了，不用改。**

那句「還沒有指定任何音韻歷程，從下面挑。」正好落在準則要的位置上——它只**陳述事實**（現在是空的、要你自己挑），沒有**辯護設計**。設計理由那句「一個你沒有真的寫下來的歸類，比一個看得出來是空的框更糟」只寫在《使用說明》裡，畫面上一個字都沒有。這就是 1.3 想要的分工，現況已經是對的。

值得記一筆的是：這個例子說明「可疑級」的正確劑量比想像中小。使用者不需要知道我們為什麼這樣做，只需要知道這是空的、而且該由他填。

### 例四：構音格子表的欄位順序（已刪的那一句）

原文：「同一欄是同一個構音部位，由左至右部位由前到後」。

- 問一：**臨床知識，第一問就出局。**這句話在任何一張構音評估表上都成立，換個工具照樣成立。使用者是語言治療師。
- 問二：**自證的。**掃一眼 ㄅㄆㄇㄈ ／ ㄗㄘㄙ ／ ㄉㄊㄋㄌ ／ ㄓㄔㄕㄖ ／ ㄐㄑㄒ ／ ㄍㄎㄏ 就看得出那是什麼排法。
- 問三：**沒有後果。**欄位順序不進規則、不影響推導、看錯了不會算錯任何東西。

**判定：刪除正確，準則追認這個決定。**三問全部指向刪。

兩個要一起講清楚的邊界：

**第一，tooltip 不能跟著砍。**符號上那個虛線底線的辨異徵性提示不是說明文字，是**資料**——它顯示的是這個符號的辨異徵性本身，來源是 `references/taiwan-mandarin-consonants.md`。它跟「解釋怎麼看這張表」是兩回事。同理，非部位排序的區塊裡符號旁邊那個中文名（聲調那類）也是資料，一個裸的聲調符號沒有名字讀不出來。

**第二，這個順序裡確實有一個不自證的部分**——ㄈ 是唇齒卻放進雙唇那一欄，這是我們的合併決定不是臨床事實。但它止步於第三問：合併與否不影響任何計算。**沒有後果的事不上畫面。**它已經寫在《使用說明》的表格裡，那是它該待的地方。

`articulation-table.html` 裡那段解釋為什麼不能 wrap 的 HTML 註解要留著——它是給下一個改這個檔案的人看的，不是給使用者看的，不受這條準則管。

### 例五：「錯音留白就是構音正確」

現況：構音表最上方一行灰字「每個音三組「目標詞 ＋ 錯音」。錯音照聽到的寫（例如「ㄆㄠ」），構音正確就留白。」

這一句要拆成兩半判，因為兩半的答案不一樣。

**前半「每個音三組『目標詞 ＋ 錯音』。錯音照聽到的寫（例如「ㄆㄠ」）」**

- 問一：介於輸入格式與教學之間。三組並排、兩個小格子——這是**自證的**，看到格子就知道要填什麼，而且 placeholder 已經寫了「詞」跟「錯音」。「照聽到的寫（例如「ㄆㄠ」）」則是格式規範，但它的完整版（只比對第一個符號、非注音字不算錯誤、聲調符號不影響）在《使用說明》裡，畫面上這半句只是掐頭去尾的摘要。
- 問三：格式寫錯的後果是推導不出東西——而**推導不出東西是看得見的**，音韻歷程區塊就在同一頁下方，會顯示「目前的構音記錄推導不出任何音韻歷程」。自證。

**→ 前半刪，移到《使用說明》（已經在了）。**

**後半「構音正確就留白」**

- 問一：**工具行為，而且是判準。**我們用「格子空不空」當作「對不對」，這是實作決定。
- 問二：**無聲，而且後果最重。**治療師如果以為要在正確的音填「○」或「正確」，他打下去，那一格就變成一筆構音錯誤，畫面不會抗議，然後他會拿到一整排假的構音錯誤跟一堆假的音韻歷程。

> **這裡原本多寫了一句「空白同時代表『測了，是對的』跟『還沒測』，工具分不出這兩件事」，那句是錯的，訂正如下。**
>
> 在**格子表這一層**分得出來：只要〈目標詞〉有填，這個音的記錄就會留著（三格全空——詞跟錯音都空——才會整筆丟掉，見 `articulation-table.ts` 的 `updateItem`）。所以「填了詞、錯音留白」＝測過而且正確，跟「整個音沒碰過」是兩種不同的儲存狀態。
>
> 分不出來的是**規則那一層**：`buildFacts()` 只送出 `articulation.errors`，沒有任何事實代表「測過而且正確」。所以一條寫「排除 ㄓㄔㄕㄖ 之後仍有錯誤」的規則，面對「ㄗ 沒測」跟「ㄗ 測了是對的」會得到一模一樣的答案。
>
> 這個差別會改變結論：前者是**格子表的說明文字**要處理的事（而它不必處理，因為分得出來），後者是**事實模型的缺口**，寫再多畫面文字也補不起來。它屬於下面第五節那類「機制層級的漏」，記進 `docs/todo.md`。

- 問三：產生錯的資料，看不出來。

**→ 後半留，而且優先度很高。**但它現在跟前半黏在同一行、常駐在整張表最上面，被前半稀釋掉了。位置上它應該貼著〈錯音〉欄——UX 決定用哪種形式（縮短後的單行、`title`、或改寫 placeholder），PM 只要求判準本身不能消失。

這一例是整份準則最好的示範：**同一行字裡，一半是該刪的教學，一半是絕對不能刪的揭露。**逐行砍文字必然會砍錯，要逐句判。

## 四、不上畫面的那些話去哪裡

### 4.1 分工

**畫面承接猜不到的，《使用說明》承接其餘全部。**

《使用說明》（`docs/使用說明.md`）已經寫得很完整，三問判出來要刪的東西，幾乎每一項在裡面都找得到對應段落——欄位順序有一整張部位對照表，錯音格式有完整的例外規則，〈自己選〉為什麼空白連理由都寫了。所以「移到《使用說明》」目前多半不是搬運工作，而是**確認**。

但要當成硬規定：

> **刪一句畫面文字之前，先確認《使用說明》裡有對應段落。沒有就先補，再刪。**

這是刪除的**前提條件**，不是後續清理。否則每一次精簡都在淨損資訊。

兩份文件的語氣也不同：畫面上是**陳述**（「這是空的」），《使用說明》裡才是**解釋**（「為什麼是空的、我們為什麼這樣做」）。同一件事在兩邊都出現不算重複，是不同深度。

### 4.2 使用者怎麼找到《使用說明》

**目前找不到——畫面上沒有任何地方連到它。**這讓上面整套分工變成一半是虛構的：我們把內容移去一個使用者到不了的地方。

PM 的決定：**《使用說明》是一等公民，必須有入口。**這不是文件整理工作，是產品範圍的一部分——沒有入口的話，這份準則的另一半不成立。

UX 的決定：**入口放在頁首導覽列**，跟〈個案一覽〉〈評估表一覽〉並列。理由：

- 《使用說明》講的是整個工具，不是某一頁，所以它屬於全域導覽這一層。
- **不要做每頁一個「？」按鈕。**那會把這份準則好不容易清掉的逐頁說明，換一個形式再長回來——而且會誘使我們把該上畫面的揭露降級成一個要點開的問號。
- 課節紀錄頁有硬約束（頁首與頁籤列不能有側欄），任何逐頁求助面板在那一頁都不可行。
- 動線上這樣是對的：畫面上留的是**做事當下需要的**（「排除」的白話重述必須在下拉選單旁邊，不能是「去看說明」），《使用說明》裝的是**讀一次就好的**。讀一次就好的東西，值得使用者離開當前頁面去找。

實作形式（新路由 vs 外連 Markdown vs 內嵌）留給後續 change 決定，這裡只定案「必須有，而且在頁首」。

## 五、檢查表

要在畫面上加一句話，或者要砍一句，照這個順序過：

1. **這句話補的是臨床知識，還是這個工具自己的行為？** 換一張紙本評估表還成立的話，它是臨床知識 → 不上畫面。
2. **不講的話，使用者會不會自己發現？** 做了就看得到 → 不上畫面。
3. **猜錯的後果是什麼？** 沒有後果 → 不上畫面。無聲地產生錯資料或錯判斷 → 一定上。不可逆的破壞 → 一定上，而且要擋路。
4. **這一句裡有沒有混著兩種東西？** 有的話拆開，分開判（見例五）。
5. **它能貼著後果現形的地方嗎？** 不能的話換位置，不要換成更長的文字（見例二）。
6. **它能不常駐嗎？** 能做成空狀態或條件顯示，就不要做成常駐說明。
7. **砍到只剩「工具會做什麼」，還剩幾個字？** 「我們為什麼這樣設計」的部分刪掉，進《使用說明》。
8. **刪之前，《使用說明》裡有對應段落嗎？** 沒有就先補再刪。
9. **它是免責聲明、資料、介面標籤或頁面定位嗎？** 是的話不受這套準則管，別動。

判定不同意的時候：**要不要講是 PM 的**，**怎麼講、擺哪、什麼時候出現是 UX 的**。UX 不能因為塞不下就不講，要退回 PM 重新決定。
