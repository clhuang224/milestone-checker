# 開發方式紀錄

這個專案的另一半實驗，是**開發方式本身**：用 Claude Code 搭配 subagents 驅動一個需要專業領域知識的產品。這份文件記錄實際的分工、踩過的坑、以及最後訂出來的規矩。

## 分工

開發者（語言治療師本人）是**臨床權威與產品決策者**。Claude Code 是助理，也是唯一跟開發者對話的窗口。其餘角色都是 subagent，成果經由 Claude Code 彙整回報：

| 角色       | 做什麼                                                             |
| ---------- | ------------------------------------------------------------------ |
| 文獻查證   | 任何需要依據的臨床主張。回報文獻怎麼說，**以及文獻沒有定論的部分** |
| 質疑／辯論 | 在不好回頭的設計拍板之前，負責講反面                               |
| UI/UX      | 畫面與動線，特別是排版本身帶有臨床意義的地方                       |
| Angular/TS | 資料模型與架構決策                                                 |

subagent 一律跑 Opus 5，不使用更大的層級。

## 最重要的一條規矩：臨床內容不能編

**這條是踩過坑才訂的。** 專案早期，21 個聲母的辨異徵性、12 條音韻歷程、「四歲以上」的年齡門檻、矯正年齡的常數，全部是模型生成的——看起來很像真的，錯了卻沒有任何跡象。

當時的緩解方式是把它們標記成「佔位、待治療師審核」。後來這個標記被拿掉了，因為審核的人就是開發者本人，標記只是噪音，被標記的內容照樣是編的。

現在的規矩是：**不確定就拆成小問題逐項問，不自己填**。而且臨床資料放在 `references/` 的 markdown 表格裡，可以查、可以交給另一位治療師校對，有 pre-commit 檢查確保它跟程式碼一致。

### 這條規矩實際擋下了什麼

- **ㄙ→ㄉ 的分類**。模型用「部位由前到後」的排序機械推導，得出「後置化」。文獻查證發現：沒有任何來源這樣推導，每一份都是列舉「目標音集合 → 錯誤音集合」的查找表；而且鄭靜宜（2011）明文警告過這種擴張會膨脹發生率。整個部位推導因此移除。
- **不捲舌化**。模型主張它是「前置化的多餘特例」而建議刪除——正好是文獻警告過的錯誤。（最後仍然不列入，但理由是開發者說的「台灣華語的不捲舌是方言性變異，不算異常」，不是模型當初給的理由。）
- **ɿ／ʅ 的舌位**。文獻本身沒有定論（各家轉寫成 [z̩]、[ɹ̩]、[s͡ɯ]），所以欄位留空並標記為舌尖元音，不代為決定。
- **果凍**。IDDSI 把明膠果凍歸為「過渡期食物」——不是編號等級，是另一個軸。而「果凍」兩個字蓋住了相反的東西：明膠果凍會融，蒟蒻果凍不會且是窒息危險物。

## 版權

臨床工具的內容很多有授權限制，這件事比預期的更常擋路：

- **標準化測驗不能抄。** 音韻歷程的定義因此改成開發者依自己的臨床經驗寫，不引用任何測驗。
- **IDDSI 是 CC BY-SA 4.0，而且明文禁止改作**（`Derivative works extending beyond language translation are NOT PERMITTED`，理由是改寫曾導致窒息與死亡事件）。所以只使用等級數字與短標籤——那屬於事實與短標題——完整描述詞用連結指向原始出處。

## 驗證要看真的東西

測試全過不等於功能會動。這個專案至少有兩次是這樣：

- **吞嚥條件曾經永遠不會觸發。** 模型、規則條件、成功率推算都有測試，但 `buildFacts()` 從來不產生 `swallowing.trials` 這個命名空間。測試之所以綠，是因為它們自己捏造事實物件。
- **構音格子表第一次做出來 wrap 成兩欄**，ㄍ 掉到 ㄅ 底下——那正好毀掉「由左至右部位由前到後」這個唯一的重點。是在瀏覽器實際量過欄位座標才發現的。

所以會動到畫面或資料流的改動，一律在瀏覽器裡跑一次，量實際的數字，不靠推論。守門測試也要**先把它弄壞一次**，確認它真的會紅。

## 模型會弄錯的其他事

誠實記下來，這些都發生過：

- **在 commit 訊息裡寫錯自己的模型名稱**（照抄 `CLAUDE.md` 的範例，而 session 中途用 `/model` 換過）。
- **把還沒做的 task 打勾**。發現後在下一個 commit 訊息裡寫明更正。
- **把「核心層完成、畫面還沒」講得像排程問題**，實際上是功能不完整。
- **參考文件與程式碼不同步**（`references/README.md` 把已完成的韻母表列成「尚未提供」好幾個 commit）。

## 流程

規格用 [OpenSpec](https://github.com/Fission-AI/OpenSpec):先寫 proposal／design／tasks，再照 `tasks.md` 逐項做。commit 切得小，一個邏輯改動一個——因為沒有人逐行 review，出問題時要能 bisect 回一個小改動。

品質關卡是 `pnpm lint` / `pnpm test` / `pnpm build` / `pnpm check:references` 全過，不是「跑起來看起來對」。
